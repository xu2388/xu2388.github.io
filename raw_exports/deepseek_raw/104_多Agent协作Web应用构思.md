## 应用名称：**「调解者」—— 多方利益冲突模拟与最优谈判方案生成器**

### 核心价值
用户输入一个**需要多方达成共识的商业/社会场景**（例如：劳资谈判、土地征收补偿、跨国供应链利润分配）。系统启动多个**具有独立利益函数和底线策略的Agent**自动模拟谈判，最终输出一个**可执行的、帕累托最优的综合方案**。单个Agent无法同时扮演多个对立角色并产生真实的博弈动态。

### 为什么必须用多Agent协作？
- 每个Agent拥有**隐藏的私有利益函数**（例如：工会Agent要求最低工资增幅≥8%，否则罢工；资方Agent要求增幅≤3%，否则关厂）。这些利益相互冲突。
- 单Agent如果同时编写多方立场，必然会**自我矛盾**或**和稀泥**，无法模拟真实的**博弈树搜索**与**逐轮让步**。
- 多Agent通过**独立推理 + 结构化通信**（报价、反报价、威胁、妥协）动态逼近均衡解。用户可观察每个Agent的内心独白和交互日志，证明每个Agent是独立运行的。

## 功能设计

### 1. 场景配置界面（用户输入）
- 问题名称：如“高科技公司股权激励谈判”
- 参与方数量：2～5个（每个对应一个Agent）
- 为每个参与方定义：
  - 角色名称（如创始人、早期员工、风险投资方）
  - 利益目标（量化维度：股权比例、行权价、锁定期）
  - 底线（低于此值宁可谈判破裂）
  - 让步速度（激进型/保守型）

### 2. 谈判引擎（多Agent协作核心）
运行一个**回合制谈判协议**，每轮：
1. 每个Agent独立生成**报价**（基于自身利益模型和对手历史行为预测）。
2. **协调Agent**收集所有报价，检测距离（是否所有报价的交集不为空）。
3. 若无交集，协调Agent生成一个**反事实建议**（例如“如果A让步5%，B能让步2%吗？”），发给相关Agent进行**内部重算**。
4. Agent们更新信念并产生新报价，重复直到：
   - 达成一致 → 输出最终合同。
   - 超过轮次上限 → 输出“谈判破裂”及各自最后一次报价差距。

### 3. 可视化协作面板（体现多Agent）
- **网络图**：展示Agent之间的消息流向（报价、威胁、提议）。
- **时间线**：每一轮各个Agent的报价变化曲线。
- **日志窗口**：可展开查看每个Agent内部推理过程（例如：“工会Agent：本轮对方让步0.5%，我预计再坚持一轮可以拿到6%”）。
- **最终报告**：列出每个Agent的初始/最终诉求、让步记录、是否满足底线。

### 4. 用户介入（可选）
允许用户在任意轮次“外派指令”给某一个Agent（例如：“劳工Agent，提高威胁等级”），看系统如何动态反应——这进一步证明Agent是真实独立运行的。

## 技术实现要点（可落地）

### 框架选型
- **后端**：FastAPI + **LangGraph** 或 **AutoGen**（微软框架，原生支持多Agent对话与状态持久化）
- **Agent实现**：每个Agent是一个LLM调用（GPT-4o / Claude / 本地Llama3），带独立**系统提示词** + **工具调用**（例如计算报价是否符合底线）。
- **状态管理**：Redis存储每个Agent的私有数据（利益函数、让步历史）和共享的谈判历史。

### 防作弊（避免单Agent模拟）
- 每个Agent在每次报价时，必须**重新加载自己的私有利益函数**（作为prompt的一部分），并且**不能访问其他Agent的私有参数**。
- 后端为每个Agent分配**独立的LLM会话**（不同temperature, 不同system message），甚至可以调用**不同的LLM服务商**来强化独立性。
- 提供**Agent心跳日志**：每次生成报价的耗时、token消耗、API endpoint——让用户确信不是同一个LLM瞬间写出所有发言。

### 简化MVP的替代方案（若不想太复杂）
用**CrewAI**框架，定义两个角色：
- `Proposer`（提议方） 
- `Critic`（批评方）
让它们就一个涨价方案进行辩论。但上述“谈判破裂”场景更能体现协作必要性。

## 为什么单Agent无法模仿？
- **自我博弈崩溃**：单Agent如果同时扮演谈判双方，它的输出会被自己“知道对方在想什么”所污染，永远无法复现真正的**不完全信息博弈**（例如隐藏真实底线）。
- **可验证的独立性**：您可以用**不同LLM**（GPT-4 vs Claude）分别驱动两个Agent，它们的推理路径天然不同，单Agent无法复制。
- **并行状态隔离**：每个Agent内部有自己的记忆和状态更新，单Agent模型无法在不使用外部存储的情况下维持两个独立的状态机。

## 扩展：更轻量的思路（如果您想更快展示）
做一个 **「多Agent代码审查委员会」**：
- 用户提交一段Python代码。
- 启动3个Agent：风格检查员、安全审计员、性能分析员。
- 每个Agent独立运行静态分析工具（或调用LLM分析），产生报告。
- 最后由主席Agent汇总并解决冲突（例如：风格员要求改名，但安全员认为改名会导致安全补丁失效——需要协商出最终修改方案）。
- **不可替代点**：安全审计员需要实际调用Bandit工具，性能员需要运行基准测试，这些是独立外部动作，单Agent无法同时执行并协调结果。
