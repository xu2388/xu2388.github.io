操作系统/Linux · 用户权限与 ACL

一、概述：权限模型回答的三个问题

权限系统只回答三件事：谁（身份）、对什么（对象类型）、能做哪一类操作（读、写、执行）。Linux 传统模型把身份压缩成三类——属主、属组、其他，把操作压缩成三位——r、w、x，因此表达力有限；ACL 是在不推翻这三类槽位的前提下，给单个用户或单个组加例外，并用 mask 给例外封顶。本文按「解码权限串 → 推导默认权限 → 特殊位与进程身份 → ACL → 继承与最小权限」的顺序展开。

与已有笔记的分工需要先讲清。《操作系统与 Shell 脚本》给的是命令清单与题目层面的特殊位速算，重点在「会敲、会判」；本文补的是模型、匹配顺序与可复核的推导，重点在「为什么这样判」。《Linux 本地存储管理》讲磁盘、分区、LVM 到挂载，本文只讲挂载点之上的访问控制，不重复 inode、分区表与 fstab。

先给一张总表，后文逐项展开：

二、权限串怎么读

2.1 十位不是十位

ls -l 第一列是十个字符：一个类型位加三组三位。类型位 - 表示普通文件，d 表示目录，l 表示符号链接，c 表示字符设备，b 表示块设备，s 表示套接字，p 表示管道。类型位不参与八进制计算。第九位之后还可能出现一个字符：. 表示有 SELinux 安全上下文，+ 表示有 ACL。两者都不是权限位，不能读进 rwx。

ls -ld 项目目录
stat -c '%A %a %U %G %n' 项目目录
getfacl 项目目录

stat 的 %A 是人类可读权限串，%a 是八进制值。两者对照可以避免手读出错；权限题里最常见的错误不是不会算，而是把 rws 看成 rwx、把 r-t 看成 r-x。

2.2 rwx 对文件与目录的不同含义

同一个字母，作用在文件与目录上不是一回事。这是权限部分最该先记牢的一张表：

位对普通文件对目录
r读文件内容，如 cat、cp 源文件列目录项，如 ls，拿到文件名列表
w改文件内容，包括写入、截断、追加在目录内创建、删除、重命名条目，即改目录项
x把文件交给内核执行，即 execve进入目录、访问目录内条目的 inode，如 cd、cat 目录/文件

三条推论必须记住。

第一，目录的 w 不等于能改目录内文件的内容，它管的是目录项本身。删一个文件看的是父目录的 w+x，不是文件自己的 w。所以一个 444 的文件放在 777 的目录里，仍然可能被别人删掉。

第二，目录的 x 是通行证。只有 r 没有 x，能列出名字但 stat 不到条目，也进不去；只有 x 没有 r，知道确切路径就能访问，但列不出目录。

第三，文件的 x 只对可执行文件有意义。普通文本文件即使有 x，内核也要看文件头能否识别为可执行格式；脚本还要有可用的解释器。

把常见目录权限与「能否 cd、能否 ls、能否删文件」列成表，比背结论可靠：

目录权限八进制能否 cd能否 ls能否删/建条目
rwx7能能能
r-x5能能不能
rw-6不能能不能
--x1能不能不能
r--4不能能不能
---0不能不能不能

2.3 身份匹配是「首次命中」，不是「取并集」

判定顺序固定为：先比较进程的 EUID 与文件 uid；命中就用属主三位；否则比较进程的 EGID 以及附加组与文件 gid；命中就用属组三位；都不命中才用其他三位。一旦命中就停止，不会把属主、属组、其他的权限相加。

这条规则解释了两个常见现象：

  • 文件属主即使被属组位给了更多权限，也只看属主位；属主位是 --- 时，属主本人也不能读写。
  • 一个用户同时在多个附加组里，只有文件 gid 命中的那个组位生效；不存在「把多个组的权限并起来」的算法。

ACL 把这条规则扩展成：属主条目 → 具名用户条目 → 属组与具名组条目（受 mask 限制）→ 其他条目，同样是首次命中。详见第六节。

2.4 用一条实例走完判定

设文件 项目目录/数据.csv 属主为 acct_a、属组为 lab，权限 -rw-r-----，即 640。三个账户的组成员关系是：acct_a 主组 lab；acct_b 主组 staff，附加组含 lab；acct_c 主组 staff，不在 lab。逐个身份推：

身份进程 EUID / EGID命中槽位有效权限能读能写
acct_a自己的 uid / lab属主位 rw-rw-能能
acct_b自己的 uid / staff，附加组 lab属组位 r--r--能不能
acct_c自己的 uid / staff其他位 ------不能不能
root0 / 0不适用绕过读写在内的自主访问检查能能

acct_b 之所以走属组位，是因为判定看的是进程的 EGID 与附加组集合，而不是账户名是否出现在文件上。若给 acct_b 单独加一条 u:acct_b:rwx 的 ACL，他命中的就是具名用户条目，反而不再看 lab 的组位；这正是「首次命中」在多身份下的表现：具名条目更靠前，既可能给他更多，也可能给他更少。

root 那一行要加限定：root 绕过 r、w 检查，但执行一个文件仍要求该文件至少有一个 x 位；对目录，root 可以进入任意目录，不需要 x。所以「root 什么都能做」在「执行无 x 位的文件」这一项上不成立。

2.5 身份从哪里来

权限判定用的三个量——uid、gid、附加组集合——都来自账户数据库。/etc/passwd 每行七个字段，依次是用户名、口令占位符、uid、主组 gid、注释、家目录、登录 Shell。口令并不在这个文件里，第二字段通常只是一个 x，真正的散列在 /etc/shadow，后者只有 root 可读。/etc/group 每行四个字段：组名、口令占位、gid、成员列表；成员列表记的是附加组，主组关系记在 /etc/passwd 的第四字段。

id
id acct_b
groups acct_b
getent passwd acct_b
getent group lab

id 输出里的 groups= 是当前进程实际携带的组集合，这是判定时真正用的东西。把用户加入新组后，已登录的 Shell 不会自动获得新组，因为组集合在登录时确定；要么重新登录，要么用 newgrp lab 开一个带新组的新 Shell。排查「明明加了组还是没权限」时，先比 id 与 getent group，再看文件权限，顺序不要颠倒。

提权有两条路。su 切换到另一个账户，需要目标账户的口令，并启动一个新的 Shell，环境变量默认也换成目标账户的；su - 还会模拟完整登录。sudo 不切换 Shell，只按 /etc/sudoers 的规则授权单条命令，默认要求输入自己的口令，因此可以做到「不给 root 口令也能干指定的活」。sudo -u acct_b 命令 以指定用户身份执行，sudo -l 列出当前账户被允许的命令。改 sudo 规则要用 visudo，它会在保存前做语法检查；直接编辑 /etc/sudoers 写坏一行，可能让所有提权入口失效。

三、chmod：数字与符号

3.1 数字写法

三位数字分别对应属主、属组、其他，每位是 r=4、w=2、x=1 的和。四位数字时最高位是特殊位：SUID=4、SGID=2、粘滞位=1。

权限串八进制说明
rwxr-xr-x755属主全权，组与其他读加执行
rw-r--r--644属主读写，其余只读
rw-rw----660属主与属组读写，其他无
rwxrwx---770属主与属组全权，其他无
rwx--x--x711属主全权，其他只能进入
rw-------600仅属主读写

数字写法是整体赋值：chmod 640 file 会把特殊位一并清掉，除非写四位。所以对已有 SUID 的文件执行 chmod 755，SUID 会丢失。要保留特殊位，写 chmod 4755，或者先用符号写法只改普通位。

3.2 符号写法

符号写法是「谁 + 操作 + 权限」。谁取 u（属主）、g（属组）、o（其他）、a（全部）；操作取 +（增加）、-（删除）、=（赋值为给定集合）；权限取 r、w、x，还可写 s、t 与 X。

chmod u=rwx,g=rx,o= 项目目录/脚本.sh
chmod g+w 项目目录/数据.csv
chmod o-rwx 项目目录/配置.ini
chmod a+x 项目目录/工具.sh
chmod u+s 项目目录/程序
chmod g+s 项目目录/共享
chmod o+t 项目目录/共享

= 的行为要单独记：g=r 表示把属组位设为只读，原来有的 w、x 都被清掉；g+=r 才是在原有基础上加 r。o= 后不写权限，等于把其他位清空。

X 是条件执行位：只有当对象是目录，或对象已有任一执行位时，才加 x。批量给目录树补执行位时，chmod -R a+X 项目目录 比 a+x 安全，后者会把普通数据文件也标成可执行。

-R 递归要谨慎，它会把目录与文件一视同仁。常见错误是 chmod -R 600 项目目录，目录失去 x 后谁都进不去。正确做法是分开处理：

find 项目目录 -type d -exec chmod 750 {} +
find 项目目录 -type f -exec chmod 640 {} +

3.3 特殊位的符号与大小写

特殊位位置有执行权限无执行权限八进制
SUID属主位第三位sS4000
SGID属组位第三位sS2000
粘滞位其他位第三位tT1000

s 与 S 的区别是底下的 x 在不在：rws 是 rwx 加 SUID，rwS 是 rw- 加 SUID。t 与 T 同理。读权限串时先看字母大小写，再决定普通位该按 7 还是 6 算。

3.4 在创建时就把权限定下来

事后 chmod 会产生一个时间窗：从文件创建到改权限之间，文件按 umask 算出的权限存在。对私密文件更稳妥的做法是创建时就带 mode：

mkdir -m 2770 项目目录/共享
install -d -m 750 项目目录/归档
install -m 640 模板.csv 项目目录/数据.csv
(umask 077; touch 项目目录/私密记录)

install 与 cp 的差别值得记：install -m 直接给定目标权限，不受 umask 影响；cp 新建目标时用源文件 mode 与 ~umask 相与，只有 cp -p 才保留源文件的权限与时间戳。mkdir -m 2770 一次把 SGID 与组权限都设好，比先 mkdir 再 chmod 少一个中间态。

mktemp 创建的临时文件默认只有属主可读写，这是一条有意的安全默认；自己拼一个 /tmp/固定名 再用 > 重定向，既可能撞名，也可能被预先放好的符号链接利用。临时文件交给 mktemp，目录交给 mktemp -d。

四、umask：默认权限的按位推导

4.1 规则不是减法

新建普通文件的基准是 666，不含 x；新建目录的基准是 777。内核的做法是基准位与 umask 的按位取反相与：

$$ \text{mode}_{\text{new}}=\text{base}\ \&\ \sim\text{umask}. $$

八进制每一位独立做三位二进制运算。减法 666-umask 只在 umask 的每一位都落在基准位范围内时才碰巧相等；一旦 umask 含基准中不存在的位，例如文件基准 6 不含 x，而 umask=033 要掩 wx，减法就会多扣。

4.2 逐位复核

以 umask=033 为例，文件基准 666：

$$ 6\ \&\ \sim 3 = 110_2\ \&\ 100_2 = 100_2 = 4, $$

三位都是 6 与 3 运算，所以文件权限是 644。目录基准 777：

$$ 7\ \&\ \sim 3 = 111_2\ \&\ 100_2 = 100_2 = 4, $$

三位都是 7 与 3 运算，所以目录权限是 744。若用减法，会得到 633 与 744；文件那一项就错了。

再以 umask=027 为例：

位文件 6 与 ~umask目录 7 与 ~umask
属主位，umask 06 & 7 = 67 & 7 = 7
属组位，umask 26 & 5 = 47 & 5 = 5
其他位，umask 76 & 0 = 07 & 0 = 0

所以文件 640、目录 750。这个例子说明 027 的「其他位全掩」是有效的，减法在这里也恰好成立。

4.3 常见 umask 对照

umask新文件新目录适用场景
022644755默认，团队可读
027640750同组可读、其他不可见
077600700个人私有
002664775协作目录，同组可写
033644744掩掉组与其他写、执行，文件仍是 644

umask 是 Shell 内建，设置后只影响当前进程及其子进程创建的新对象，不影响已存在文件。查看用 umask（数字）与 umask -S（符号）。要长期生效，写进 ~/.bashrc 或 /etc/profile；要让某个目录下的新文件自动带 ACL，则用默认 ACL，而不是靠 umask。

还有一个容易忽略的点：umask 只筛请求的 mode。程序调用 open(..., 0666) 时，内核再与 ~umask 相与；如果程序请求 0600，umask 022 也不会把它放宽到 644。所以「umask 决定默认权限」的准确说法是「umask 只能收紧，不能放宽」。

4.4 umask 与默认 ACL 的分工

两者都影响新建对象，但作用范围不同，混用会互相抵消预期：

需求合适手段原因
整个账户新建的东西都收紧umask 077进程级开关，覆盖所有目录
只让某个目录的新文件对组可写目录默认 ACLumask 是全局的，按目录区分只能靠 ACL
给不同具名用户不同权限目录默认 ACL传统三位放不下第四个身份
新文件默认带组继承目录 SGID 加默认 ACLSGID 管属组，ACL 管权限，各管一段

有一处交互必须说清：目录存在默认 ACL 时，新建对象的权限由继承条目与创建 mode 共同决定，umask 不再参与这一步。也就是说，在设了默认 ACL 的共享目录里改 umask 不会改变新文件的组权限，真正起作用的是 d:g:: 与 d:m:: 两行。反过来，在没设默认 ACL 的目录里，d: 条目根本不存在，只能靠 umask。排查「共享目录新文件权限不对」时，先确认这个目录到底有没有默认 ACL，再决定改哪一处。

五、SUID、SGID 与进程的四类 ID

5.1 三个特殊位各自做什么

位作用对象效果典型
SUID可执行文件执行时进程 EUID 变为文件属主 uid改密程序需要临时读写口令库
SGID可执行文件执行时进程 EGID 变为文件属组 gid需要临时获得组权限的工具
SGID目录目录内新建对象的 gid 继承目录 gid，而不是创建者主组团队共享目录
粘滞位目录目录内条目只有其属主、目录属主与 root 能删或改名/tmp 的 1777

注意 SGID 在文件与目录上是两种不同效果，这是它最容易混的地方。粘滞位对普通文件的 x 位没有额外授权作用，它只限制删除与改名。

5.2 四位八进制的换算

把权限串拆成「类型位 + 三组三位」，逐组算普通位，再看每组第三位是否有 s、S、t 或 T：

权限串普通位特殊位八进制
-rwsr-xr-x755SUID 40004755
-rwxrwsr--774SGID 20002774
drwsrw-r-t765SUID 4000 加粘滞 10005765
-rwsrwsrwt777SUID、SGID 与粘滞共 70007777
-rwSr--r--644SUID 4000，无 x4644
-rw-r-Sr--644SGID 2000，无 x2644
-rw-r--r-T644粘滞 1000，无 x1644

最后三行专门用来区分大小写：大写字母表示特殊位开了，但对应的 x 没开，普通位按 6 或 4 算，不能按 7 或 5 算。

原料在「三个特殊位叠加」的例子中把 -rwsrwsrwt 算成 7775，这是错的：其他位的 rwt 是 r+w+x 再加粘滞位，普通位是 7，特殊位是 7，合计 7777。错误来源是把小写 t 当成「占用了 x 但不给 x」，而小写 t 恰恰表示 x 仍在。

5.3 进程的 RUID、EUID、RGID、EGID

进程有四类身份：真实 ID（RUID 与 RGID）记录谁启动的，有效 ID（EUID 与 EGID）是内核做权限检查时真正使用的身份。默认二者相等；执行带 SUID 的文件时 EUID 变为文件属主 uid，执行带 SGID 的文件时 EGID 变为文件属组 gid。另有一组保存型 ID（saved set-user-ID 与 saved set-group-ID），用于 exec 后还能切回原身份；它和权限串里的 SUID 位同名但不是一回事，答题时最好写全称，避免把「位」和「进程属性」混成一个概念。

一个可复核的例子：文件属主 uid=1001、gid=1001，权限 -rwxrws-w-，即 2772；执行者 uid=500、gid=501。属主位是 rwx，没有 s，所以 EUID 不变，等于 500；属组位是 rws，有 SGID，所以 EGID 变为文件属组 1001；RUID 与 RGID 始终是 500 与 501。若权限改成 -rwsrws-w-，即 6772，EUID 才会变成 1001。

还要区分文件访问判定与进程身份：执行者能否读这个文件，只看它命中属主、属组、其他的哪一段，SGID 不会让一个不属于属组的用户突然获得属组读权限。SGID 改变的是子进程的 EGID，以及目录新建对象的属组，不是当前用户的身份。

5.4 特殊位的安全边界

  • 对脚本设置 SUID 在 Linux 上通常不生效：内核不把 #! 脚本当作可保留特权的可执行体，脚本解释器会以调用者身份运行。需要提权应使用编译型程序或受控的 sudo 规则。
  • 查找系统中的 SUID 与 SGID 文件：find / -xdev -perm -4000 -type f 与 find / -xdev -perm -2000 -type f。-xdev 避免跨文件系统扫描。
  • 挂载选项 nosuid 可以忽略该挂载点上文件的 SUID 与 SGID 位；对用户可写的分区应默认加 nosuid。
  • 共享目录用 SGID 加默认 ACL 实现「新建文件自动归组」，比把目录设成 777 安全得多。

5.5 SGID 目录的连锁效果与粘滞位的边界

SGID 目录的效果是「新建对象的属组继承目录属组」，但继承的细节要分对象看：

新建对象是否继承属组是否继承 SGID 位
普通文件是否，新文件不带 SGID
子目录是是，子目录自动带 SGID 继续往下传

第二行意味着 SGID 会沿着新建的子目录自动延续，但不会追认已有的子目录。把一个旧目录改成 2770 后，它内部已经存在的子目录仍然是原来的属组与位；要让整棵树都归组，需要对已有目录补一次：find 项目目录/共享 -type d -exec chmod g+s {} +。只改顶层而不补子目录，是共享目录「有的文件归组、有的不归组」的典型原因。

粘滞位只干一件事：限制目录内条目的删除与改名。判定删除时，内核要求调用者对目录有 w+x，并且满足三者之一——调用者是条目属主、调用者是目录属主、调用者是 root。它不限制读取，也不限制写入已有文件的内容。因此 1777 的目录仍然允许任何人读别人放进去的 644 文件，也允许任何人对别人放的 666 文件写入；粘滞位挡的是「删掉别人的文件」和「把别人的文件改名成自己的」，不是「碰别人的数据」。要真正隔离数据，得靠 700 的家目录、2770 的组目录，而不是 1777 加粘滞位。

六、ACL：给单用户开例外

6.1 为什么需要

传统模型只有三个身份槽位。若一个项目目录要让属主读写、项目组读写、另一个组的审计员只读、某个临时协作者只读，三档权限无论怎么摆都摆不下：把审计员加进项目组会给他写权限，把目录放开成 755 又会让所有其他用户可读。ACL 的做法是保留三档作为骨架，再挂若干具名条目。

类型作用范围是否被新建对象继承
访问 ACL（access ACL）单个文件或目录本身否
默认 ACL（default ACL）只对目录有意义是，目录内新建对象继承

默认 ACL 不是目录自己的权限，它只是模板。给目录设默认 ACL 不会改变目录本身的访问权限；要同时控制目录本身，还要设访问 ACL。

6.2 getfacl 的字段

getfacl 项目目录/数据.csv

输出大致是：

# file: 项目目录/数据.csv
# owner: acct_a
# group: lab
user::rw-
user:acct_b:r--
group::r--
mask::r--
other::---

逐行读：user:: 是属主条目，user:acct_b: 是具名用户条目，group:: 是属组条目，mask:: 是权限上限，other:: 是其他条目。# owner 与 # group 是注释，不是条目。

ls -l 末尾的 + 表示该文件有 ACL。没有 + 不代表一定没有 ACL：如果 ACL 条目与普通位完全一致，某些实现不会显示 +，所以判断应以 getfacl 为准。

6.3 mask 是上限，不是另一个身份

mask 只约束具名用户、具名组和属组条目，不约束属主条目与其他条目。一个条目的有效权限是条目权限与 mask 相与：

$$ \text{effective}=\text{entry}\ \&\ \text{mask}. $$

例如 user:acct_b:rwx 而 mask::r--，acct_b 的有效权限只有 r--。getfacl 会在被 mask 削减的条目后打印 # effective:r--，这是排查「明明给了 rwx 却写不进去」的第一线索。

设置或修改 ACL 时，工具默认会重新计算 mask：只要存在具名条目或属组条目，mask 会取这些条目的并集，并受普通位约束。如果不想让工具自动改 mask，用 -n。手工把 mask 设小，是「给了一批条目但只放开一部分」的常用手法。

6.4 setfacl 的常用形式

setfacl -m u:acct_b:rx 项目目录/数据.csv      # 具名用户
setfacl -m g:lab:rwx 项目目录/共享             # 具名组
setfacl -m o::- 项目目录/共享                  # 其他条目
setfacl -m m:rx 项目目录/共享                  # 手工设 mask
setfacl -x u:acct_b 项目目录/数据.csv          # 删除一条
setfacl -b 项目目录/数据.csv                   # 清空访问 ACL
setfacl -k 项目目录/共享                       # 只删默认 ACL
setfacl -R -m u:acct_b:rx 项目目录             # 递归
getfacl -R 项目目录 > acl.bak                  # 备份
setfacl --restore=acl.bak                      # 还原

-m 是修改或新增，-x 是删除指定条目，-b 是清空全部（含默认 ACL），-k 只清默认 ACL。--set 是整体替换，--set-file 从文件读。递归时 -R 会同时作用于目录与文件，若只想给目录加默认 ACL，不要加 -R，或者用 find 分开处理。

6.5 默认 ACL 与继承

给目录设默认 ACL：

setfacl -m d:u::rwx,d:g::r-x,d:o::---,d:m::r-x,d:u:acct_b:r-x 项目目录/共享

d: 前缀表示默认条目。一个完整的默认 ACL 必须包含 d:u::、d:g::、d:o::、d:m:: 四类骨架，否则 setfacl 会报缺少必需条目。新建对象时：

新对象继承什么最终权限怎么定
普通文件父目录的默认 ACL 作为访问 ACL继承条目再与创建时请求的 mode 做约束；属主与其他条目被 mode 对应位收紧，mask 重新计算
子目录父目录的默认 ACL 同时作为访问 ACL 与默认 ACL同上，且子目录继续把模板传给下一代
已存在文件不继承默认 ACL 只影响设置之后新建的对象

「文件继承后为什么没有 x」是常见疑问：默认 ACL 里即使写了 d:u::rwx，创建文件的程序通常请求 0666，属主条目的 x 会被 mode 的约束清掉；目录则通常请求 0777，x 得以保留。这不是 ACL 失效，而是默认 ACL 是模板、创建 mode 是第二道闸门。

移动与复制：mv 在同一文件系统内只改目录项，ACL 原样保留；跨文件系统 mv 退化为复制加删除，ACL 是否保留取决于工具。cp -p 会保留权限与 ACL，cp 不带 -p 时新文件按目标目录的默认 ACL 与 umask 生成，不继承源文件 ACL。备份 ACL 用 getfacl -R，还原用 setfacl --restore，不要只备份 ls -l 的输出。

6.6 ACL 的判定顺序

  1. 进程 EUID 等于文件属主：用 user:: 条目，不受 mask 约束。
  2. 否则查具名用户条目：命中则用该条目，结果与 mask 相与。
  3. 否则查属组条目与具名组条目：只要进程的 EGID 或任一附加组命中，就取所有命中组条目的并集，再与 mask 相与。
  4. 都不命中：用 other:: 条目，不受 mask 约束。

这张顺序表解释了为什么「给用户加了 rwx 但仍然不能写」：可能是命中了一个权限更小的具名组条目，或者 mask 把它压掉了。排查时先看 getfacl 的 effective: 注释，再看进程的实际 EUID 与 EGID（id），不要只看 ls -l。

原料把 ACL 描述成「属主权限 + 属组权限 + 其他权限 + FACL 权限的叠加」，这是错的。传统位与 ACL 不是相加关系，而是同一套判定链上的不同槽位；ACL 条目的作用也不是「再多给一点」，而是「换一个更具体的槽位」。若真是叠加，任何 ACL 都只能加权限、不能减权限，这与 mask 的存在矛盾。

6.7 ACL 的读写、迁移与排错

有 ACL 的文件，ls -l 的属组三位显示的是 mask，不是 group:: 条目。这一点会误导人：对一个有具名条目的文件执行 chmod g-w，改的是 mask，group:: 条目原封不动；getfacl 里会看到 mask::-w- 而 group::r-x 仍是原值。要改属组条目本身，必须用 setfacl -m g::r-x，不能用 chmod。同理，chmod 750 会把 mask 设成 5，具名条目可能一起被压掉。

ACL 存在扩展属性里，普通复制工具不一定带走：

操作ACL 是否保留说明
cp否新文件按目标目录的默认 ACL 与 umask 生成
cp -p 或 cp -a是保留权限位与 ACL
mv 同一文件系统是只改目录项，inode 未动
mv 跨文件系统取决于工具退化为复制加删除，按复制规则处理
tar需 --acls默认不归档扩展属性
rsync需 -A与 -p 配合才完整

备份与还原用 getfacl -R 项目目录 > acl.bak 与 setfacl --restore=acl.bak。--restore 按备份文件里的相对路径定位对象，所以要在当初执行 getfacl 的同一层目录下还原；换一台机器、换一个挂载点，路径对不上就会整批失败。只想删掉某一条默认条目，用 setfacl -x d:u:acct_b 项目目录/共享；-x 不带 d: 删的是访问条目，两者不要混。

常见报错有两类。setfacl: 项目目录: Operation not supported 表示底层文件系统没开 ACL 支持，本地文件系统通常默认开启，网络文件系统与某些容器挂载需要显式选项。getfacl 输出里条目后带 # effective:--- 则表示条目本身有权限、但被 mask 压成空，改 mask 而不是改条目。

七、权限继承与最小权限

7.1 共享目录的标准配方

目标：项目组内可读写、组外不可见、新建文件自动归组、新文件默认可被组内修改。

groupadd lab
usermod -aG lab acct_a
usermod -aG lab acct_b
mkdir -p 项目目录/共享
chown :lab 项目目录/共享
chmod 2770 项目目录/共享
setfacl -m d:u::rwx,d:g::rwx,d:o::---,d:m::rwx 项目目录/共享

2770 中的 2 是 SGID：目录内新建文件与子目录的属组继承 lab，而不是创建者的主组。d:g::rwx 让新文件默认对组可读写；d:m::rwx 给 mask 留出空间。若希望新文件默认对组只读，把 d:g:: 改成 r-x、d:m:: 改成 r-x。

为什么不用 777：777 让任何用户都能进来创建、删除、替换文件，粘滞位只能防删除，防不了读取与替换。共享目录的正确边界是「组内 2770 加默认 ACL」，而不是「全世界 777 加粘滞位」。

7.2 最小权限的检查清单

检查项命令判据

私钥权限ls -l ~/.ssh/id_*私钥 600，公钥 644，.ssh 700

namei -l 路径 可以逐级显示路径上每一层目录的权限与属主，是排查「文件权限对但就是进不去」的最快工具；sudo -u acct_b test -r 文件 可以以另一个身份做可读性测试，比肉眼推算可靠。

7.3 常见误判

  • 目录 755 所以别人不能写：对，但别人仍能读目录内所有可读文件。目录的 755 只挡写，不挡读。
  • 文件 644 所以别人不能删：删除看父目录的 w+x。父目录 777 时，文件 444 也能被删。
  • chmod 777 能解决所有权限问题：它同时放开了读、写、执行与目录项修改，是最小权限的反面。
  • ACL 会让权限只增不减：mask 可以削减具名条目，ACL 也可以用来收紧。
  • umask 能放宽权限：不能，它只能收紧创建 mode。

权限问题最好从报错反推，而不是凭感觉 chmod 777。下面这些提示各有明确指向：

九、总结

知识块必记结论
权限串类型位加三组三位；末尾 + 是 ACL、. 是 SELinux；s、S、t、T 看大小写
文件与目录目录 w 管目录项增删改名，目录 x 是进入与访问 inode 的通行证
身份匹配属主 → 属组 → 其他，首次命中即停，不取并集
chmod数字是整体赋值，符号是增量或赋值；X 只给目录或已有 x 的对象
umask用 base & ~umask 逐位算；033 的文件结果是 644 而非 633；只能收紧
特殊位SUID 改 EUID，SGID 改 EGID 或目录继承属组，粘滞位限制删除
四位换算特殊位在千位，普通位在百十个位；-rwsrwsrwt 是 7777
ACL访问与默认两类；mask 是具名条目的上限；默认 ACL 只对目录且只影响新建对象
继承SGID 管属组继承，默认 ACL 管权限继承，二者常配合使用
最小权限共享目录 2770 加默认 ACL；家目录 700 或 750；私钥 600；用户可写分区 nosuid

权限系统的复杂度来自一个矛盾：既要让大多数情况用三个槽位快速判定，又要让少数例外能精确表达。传统三位是快路径，ACL 是慢路径，mask 是慢路径的保险丝；把这三层分开看，就不会再把叠加当成规则，也不会把 s 与 S、t 与 T 读错。
