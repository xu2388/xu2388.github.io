一、概述：应用层在解决哪四类问题

应用层不给上层提供服务，它直接面向应用进程。它的协议看上去五花八门，其实只在回答四个问题：说什么（报文语义）、说多久（连接复用）、凭什么相信对方（身份与加密）、怎么找到对方（名字到地址）。HTTP 与邮件协议属第一类，HTTP/1.1 与 HTTP/2 的差别集中在第二类，HTTPS 与 Cookie/Session 属第三类，DNS 与 CDN 属第四类。

二、HTTP/1.1 的报文与语义

2.1 报文结构

请求报文四段：请求行、首部、空行、实体。请求行由方法、请求目标、版本三部分组成，三者以空格分隔，行尾是回车换行。响应报文对应为状态行：版本、状态码、原因短语。

GET /index.html HTTP/1.1
Host: example.org
Accept: text/html

首部字段名大小写不敏感，值的大小写敏感。空行是首部结束的标志，即使没有实体也必须保留。这一条在手工构造请求时最容易漏，漏掉后服务器会把实体首行当作首部继续解析。

2.2 方法与幂等性

方法语义安全幂等可缓存备注
GET取资源是是是参数在 URL 中，长度受限
HEAD只取首部是是是用于探测存在性与修改时间
POST提交数据、触发处理否否少数情况参数在实体中，可传文件
PUT整体替换目标资源否是否重复执行结果相同
DELETE删除目标资源否是否重复执行结果相同
OPTIONS询问支持的方法是是否跨域预检请求用它
TRACE回显请求是是否常被服务器关闭
CONNECT建立隧道否否否代理转发 HTTPS 时用

「安全」指不改变服务器状态，「幂等」指执行一次与执行多次的效果相同。两者常被混为一谈：DELETE 不安全但幂等，POST 既不安全也不幂等，所以浏览器在刷新一个 POST 结果页时会提示重新提交，而对 GET 页面只是重新取一次。

2.3 状态码

区段含义必记的几个
1xx信息，请求已收到继续处理100 继续、101 切换协议（升级到 WebSocket）
2xx成功200 正常、204 无内容、206 部分内容（断点续传）
3xx重定向或缓存命中301 永久、302 临时、304 未修改、307 临时且保持方法
4xx客户端错误400 请求有误、401 未认证、403 禁止、404 不存在、405 方法不允许、429 请求过多
5xx服务器错误500 内部错误、502 网关收到无效响应、503 暂不可用、504 网关超时

301 与 302 的差别在缓存与后续请求的地址：301 会被浏览器与搜索引擎长期记住，302 每次仍问原地址。307 与 302 语义相近，区别是 307 强制后续请求沿用原方法，避免把 POST 降级成 GET——这是历史上大量实现把 302 当 303 用留下的坑。304 是缓存协商的结果，响应不带实体，只带少量首部，因此「304 也算一次往返」在时序统计中必须计入。

2.4 关键首部

类别字段作用
内容协商Accept、Accept-Encoding、Accept-Language声明可接受的类型、压缩算法、语言
内容描述Content-Type、Content-Length、Content-Encoding实体类型、长度、压缩方式
缓存Cache-Control、ETag、Last-Modified、Expires强缓存与协商缓存的控制量

连接Connection、Keep-Alive是否复用连接

强缓存与协商缓存的分界要看有没有发起请求：Cache-Control: max-age=300 命中时浏览器在有效期内直接用本地副本，一次请求都不发；ETag 加 If-None-Match 命中时仍要发请求，服务器回 304 才省下实体传输。前者省往返，后者省带宽，两者常配合使用。no-cache 不是不缓存，而是「每次使用前必须向服务器确认」；真正禁止存储的是 no-store。这一组命名的反直觉是选择题的高频陷阱。

2.5 持久连接与管线化

HTTP/1.0 默认短连接：每个资源一次 TCP 连接，取完即关。一个含 30 张小图的页面就要 30 次握手，握手本身占掉的往返远多于图片传输。HTTP/1.1 把持久连接设为默认，响应头 Connection: keep-alive 只是 1.0 时代的兼容写法，1.1 中关闭才需要显式写 Connection: close。

管线化允许在一个连接上连续发出多个请求而不等响应，但响应必须按请求顺序返回，且中间任一响应变慢会阻塞后面所有响应——这就是应用层的队头阻塞。由于实现复杂且收益被浏览器多连接策略抵消，主流浏览器默认并不启用管线化，实际做法是对同一域名开 6 条左右的并行连接。这个「用连接数换并行度」的权宜之计，正是 HTTP/2 要解决的问题。

三、HTTP/2 的关键差别

3.1 二进制分帧层

HTTP/1.1 的报文是文本，解析靠查找分隔符，健壮性差且难以交错。HTTP/2 在应用层与传输层之间插入一个二进制分帧层，把一切通信切成帧，每帧带 9 字节首部：长度（24 位）、类型（8 位）、标志（8 位）、流标识（31 位）。常用帧类型有 HEADERS、DATA、SETTINGS、WINDOW_UPDATE、RST_STREAM、PRIORITY、PING、GOAWAY、PUSH_PROMISE。

分帧带来的第一个直接好处是交错：同一连接上不同流的帧可以任意穿插，接收方按流标识重新拼装。这就是多路复用的物理基础。

3.2 多路复用与流

一条 TCP 连接上并行承载任意多条流，每条流有独立的流标识与独立的流控窗口。一次请求响应在逻辑上仍是「请求头—数据—结束」，但物理上被切成帧与其他流共享同一条连接。这解决了 1.1 的两个顽症：连接数不再需要堆到 6 条，且一个慢响应不再阻塞其他响应。

流的生命周期由状态机管理：空闲、打开、半关闭（本地或远端）、关闭。任一端发 RST_STREAM 可单独取消一条流而不影响连接，这在 1.1 里做不到——1.1 取消一个请求要么等它传完，要么关掉整条连接。

3.3 HPACK 首部压缩

HTTP 首部高度重复：每个请求都带着几乎相同的 User-Agent、Accept、Cookie。HTTP/2 用 HPACK 压缩首部，三个手段叠加：

  1. 静态表：把 61 个常见首部名与常见「名值对」预置成编号，发送时只发编号；
  2. 动态表：把本次连接中已发过的首部加入表并分配编号，后续只发编号，两端同步维护；
  3. 霍夫曼编码：对字面量做定长码表压缩。

效果是首部从数百字节压到几十字节。但 HPACK 的动态表是有状态的，一旦某一帧丢失导致两端表不同步，整条连接报废，所以它必须跑在可靠有序的传输之上——这也是 HTTP/2 只能基于 TCP（或等价的可靠流）的原因。

3.4 流控、优先级与服务端推送

HTTP/2 的流控是信用制，且分两级：连接级与流级。接收方通过 WINDOW_UPDATE 归还额度，初始窗口为 65535 字节。这与 TCP 的接收窗口是两套独立机制，一层管端到端缓冲，一层管应用消费速度。

优先级通过流的依赖树与权重表达，理论上让关键资源先传。实际部署中依赖树过于复杂、服务器实现差异大，多数场景退化为按权重分配，效果有限。

服务端推送允许服务器在客户端请求之前主动推资源，用 PUSH_PROMISE 预告。它的设想是省掉「解析 HTML 才发现要 CSS」这一轮，但实践中推送的资源常已在客户端缓存中，白白浪费带宽，主流浏览器已移除对该特性的支持。这条历史值得记住：协议特性是否存活，取决于它能否在真实缓存状态下省钱。

3.5 仍未消除的队头阻塞

HTTP/2 把应用层的队头阻塞解决了，但所有流仍跑在一条 TCP 连接上。TCP 按序交付，一个报文段丢失会让后续所有已到达的数据卡在接收缓冲区里等重传，所有流一起停摆。丢包率越高，这个缺陷越致命。

这直接催生了 HTTP/3：把可靠传输搬到 UDP 之上（QUIC），每条流独立排序，一条流丢包不影响其他流；同时把传输握手与 TLS 1.3 握手合并，首次连接 1 个往返、恢复连接 0 个往返。所以「HTTP/3 用 UDP」不是放弃了可靠性，而是把可靠性做进了用户态，避免 TCP 的协议僵化。

四、Cookie 与 Session

4.1 无状态与状态保持

HTTP 本身无状态，一次请求结束后服务器不记得刚才发生过什么。要让「登录一次、后续请求都认得出」，只有两条路：把状态放在客户端随请求带回，或放在服务端并用一个标识去索引。前者是 Cookie，后者是 Session，两者不是替代关系而是配合关系——Session 的标识通常就存在 Cookie 里。

4.2 Cookie 的属性

服务器通过响应首部 Set-Cookie: name=value; 属性... 下发，浏览器此后对匹配的请求自动携带。属性决定作用域与安全边界：

属性作用常见误用
Domain指定可接收该 Cookie 的域，含子域设成顶级域会让所有子域共享，扩大泄露面
Path指定路径前缀设成根路径等于全站可见
Expires / Max-Age持久化有效期；不设则为会话 Cookie，关浏览器即失效Max-Age 优先于 Expires，两者冲突时以前者为准
Secure只在加密通道上发送只在 HTTPS 站点有效，HTTP 下设置会被忽略
HttpOnly禁止脚本读取可缓解跨站脚本窃取，但不防跨站请求伪造
SameSite限制跨站携带，取值 Lax、Strict、NoneNone 必须同时加 Secure，否则被拒

SameSite 的三个取值要分清：Strict 完全不带，从外站点到本站也不带，用户体验最差；Lax 允许顶级导航的 GET 携带，是主流默认值；None 显式放开跨站携带。把会话 Cookie 设成 None 而不加其他防护，等于把跨站请求伪造的大门打开。

4.3 Session 与服务端会话

浏览器首次访问时服务器创建会话对象、生成唯一标识（Java 体系常见名为 JSESSIONID），通过 Cookie 回送；此后请求携带该标识，服务器据此找到会话数据。会话数据的存放位置决定了系统的扩展方式：

存放位置优点缺点
单机内存最快、实现最简单多实例不共享，重启即丢
会话粘滞（按来源 IP 或 Cookie 固定到同一实例）不改代码即可扩展实例故障即掉线，负载不均
会话复制任一实例可服务复制风暴，实例越多开销越大
集中存储（缓存或数据库）无状态化，扩缩容自由多一次网络往返，需处理存储故障
客户端令牌（签名或加密）服务端零存储无法即时吊销，令牌体积大

最后一行就是令牌方案的取舍：把状态签进令牌交给客户端，服务端只验签不存储，横向扩展最省事，代价是「退出登录」只能等令牌过期或额外维护一张吊销表。

五、HTTPS：握手与证书链

5.1 三个目标与混合加密

HTTPS 是 HTTP 跑在 TLS 之上，要同时达成三件事：机密性（第三方看不懂）、完整性（改一个字都能发现）、身份认证（对面确实是它声称的站点）。三件事分别由对称加密、消息认证码、证书体系承担。

只用非对称加密能同时解决机密性与身份，但运算量比对称加密高几个数量级，不适合传大流量；只用对称加密快，但密钥怎么安全地送到对端又成了新问题。所以用非对称手段协商出一个对称密钥，之后的流量全部走对称加密——这就是混合加密，也是理解所有握手流程的骨架。

5.2 TLS 1.2 的两次往返

方向报文作用
客户→服务ClientHello支持的版本、密码套件列表、客户端随机数、SNI
服务→客户ServerHello选定的套件、服务端随机数
服务→客户Certificate服务器证书链
服务→客户ServerKeyExchange密钥交换参数（ECDHE 时为临时公钥）与签名
服务→客户ServerHelloDone第一飞行结束
客户→服务ClientKeyExchange客户端密钥交换参数
客户→服务ChangeCipherSpec + Finished切换加密并发送校验值
服务→客户ChangeCipherSpec + Finished握手完成

数往返：客户端发出第一飞行后要等服务端一整个飞行到达，这是 1 个往返；客户端回第二飞行后再等服务端确认，这是第 2 个往返。故 TLS 1.2 全握手为 2-RTT，加上 TCP 三次握手的 1-RTT，首次建立加密连接在发第一个 HTTP 请求之前已用掉 3 个往返。

两个细节值得单独记：其一，SNI 在 ClientHello 中以明文传输，中间人可以看见你访问哪个域名（ECH 正在解决这一点）；其二，Finished 的校验值覆盖此前所有握手报文的摘要，任何一处被篡改都会导致校验失败，这是握手本身不可被中间人改写的原因。

5.3 TLS 1.3 的一次往返

TLS 1.3 把密钥交换统一到 (EC)DHE，删掉了 RSA 密钥传输、静态 DH、CBC 模式等一批不安全或低效的选项，并把服务端的密钥交换参数提前到第一个飞行。于是客户端在收到 ServerHello 后就能算出密钥，第二飞行直接携带加密的应用数据，全握手压缩为 1-RTT。

会话恢复更进一步：客户端持有上次的恢复密钥（PSK），可在第一个飞行就加密发送应用数据，即 0-RTT。代价是 0-RTT 数据可被重放——攻击者截获后重发，服务器会再执行一次。所以 0-RTT 只应用于幂等请求，且服务端要限制其可执行的操作。

5.4 证书链的五步校验

浏览器拿到的是服务器证书（叶证书），它由中间 CA 签发，中间 CA 又由根 CA 签发。根证书预置在操作系统或浏览器的信任库中，是信任的锚点。校验按下列五步进行：

  1. 链的完整性：叶证书的签发者要与中间证书的主体一致，逐级向上直到某个受信根；
  2. 签名有效性：用上一级证书的公钥验证下一级证书的签名，逐级验到根；
  3. 有效期：每一级证书的当前时间都要落在生效与失效之间；
  4. 用途与域名：证书的扩展用途要允许服务端认证，主体备用名要包含所访问的域名（通配符只匹配一级）；
  5. 吊销状态：查 CRL 或 OCSP，确认该证书未被提前吊销。

五步里最容易被忽略的是第四步与第五步：域名不匹配的证书即便签名链完整也会被拒；而吊销检查因性能原因常被软失败处理，反而成为薄弱环节。另一条工程事实是，中间证书必须由服务器一并下发，否则客户端可能无法补全链路——这是「证书配好了但部分老旧设备报错」的常见原因。

5.5 前向安全

若密钥交换用 RSA 传输（客户端用服务器公钥加密预主密钥），攻击者只要长期录制流量、日后拿到服务器私钥，就能解出历史会话的密钥。ECDHE 每次握手生成临时密钥对，会话密钥不依赖证书私钥，事后拿到私钥也无法解密历史流量，这叫前向安全。TLS 1.3 强制使用 (EC)DHE，正是把前向安全从「可选」变成「默认」。

5.6 往返账目

口径先写明：往返时延统一记为 1 个 RTT，忽略带宽、解析与排队；DNS 未命中计 1 个 RTT（主机到本地服务器），命中计 0；HTTP 响应计 1 个 RTT。取 RTT 为 50 ms：

场景DNSTCPTLSHTTP合计折合时延
HTTP/1.0，TLS 1.2，冷启动11215250 ms
HTTP/1.1 持久连接，TLS 1.2，冷启动11215250 ms
HTTP/1.1 持久连接，TLS 1.311114200 ms
同上，会话恢复走 0-RTT01012100 ms
同一连接上的第二个资源0001150 ms

这张表解释了一个常见现象：把 TLS 从 1.2 升到 1.3 对首屏的收益是 1 个往返，对已经复用连接的后续请求收益为零。所以首屏优化的重点在减少往返次数（合并请求、预连接、预解析域名），而不在压缩已经很少的字节。

六、DNS：从名字到地址

6.1 命名空间与四类服务器

域名空间是一棵倒置的树，根在最上，往下依次是顶级域、二级域、子域，最左的一段是主机名。读法必须自右向左：www.abc.xyz.com 中 com 是顶级域，xyz.com 与 abc.xyz.com 是两级权限域，www 是主机标签。从左往右读会把层级读反，这是域名类题目最基础的错。

服务器职责是否知道最终答案
根域名服务器只知道各顶级域的服务器地址不知道，只指路
顶级域名服务器知道其下各二级域的权限服务器不知道，只指路
权限域名服务器保存某个区的权威记录知道，能给出权威答案
本地域名服务器替主机查询并缓存结果缓存命中时能给答案

根域名服务器在逻辑上是 13 个身份（编号 a 到 m），物理上通过任播部署成上千个实例，因此「13 台机器」是错的，「13 个地址身份」才对。

6.2 资源记录

类型含义典型用途
A名字到 IPv4 地址最常见的网站解析
AAAA名字到 IPv6 地址双栈站点
CNAME别名到规范名CDN 接入、多域名统一
MX邮件交换服务器，带优先级邮件路由，优先级数字越小越优先
NS该区的权威服务器委托子域
PTR地址到名字的反向解析反垃圾邮件、日志归因
SOA区的起始授权与参数定义主服务器、序列号、负缓存时长
TXT任意文本域名所有权验证、邮件发信策略

CNAME 有一条硬约束：同一个名字不能既有 CNAME 又有其他记录。这解释了为什么裸域（不带 www 的根域）通常不能直接 CNAME 到 CDN，工程上要用 A 记录或别名记录变通。

6.3 递归查询与迭代查询

区别只在「谁跑腿」：

对比项递归查询迭代查询
请求语义你替我查到最终答案你告诉我下一步该问谁
被问方的负担重，必须给结果或报错轻，给一个 referral 即可
典型使用位置主机到本地域名服务器本地域名服务器到根、顶级、权限服务器
次数一次请求一次响应逐台询问，每台一次

实际 DNS 是「主机对本地递归、本地对外迭代」的组合。之所以这样分工，是因为若让每台主机都自己迭代，根与顶级服务器要承受全网的逐台查询；把递归收敛到本地服务器，再由它统一缓存，才使这套系统可扩展。缓存不是优化项，而是 DNS 能工作的前提。

6.4 报文与传输

DNS 报文固定首部 12 字节：标识（16 位）、标志（16 位，含查询/响应、递归 desired、递归可用、权威、截断等位）、四个计数字段（问题数、回答数、授权数、附加数），其后依次是问题区、回答区、授权区、附加区。查询与响应共用同一格式，靠标志位区分。

传输默认走 UDP 53 端口，因为一次查询一问一答、开销要小。UDP 载荷历史上限 512 字节，超过则服务器置截断位，客户端改用 TCP 重查；EDNS0 把可接受的载荷长度扩展到千字节量级，减少了大响应被迫转 TCP 的情况。区域传送（主从服务器同步整个区）则始终走 TCP，因为它需要可靠的批量传输。

6.5 缓存与 TTL

每条记录都带生存时间，解析结果在 TTL 内可直接复用。缓存分布在浏览器、操作系统、本地域名服务器三级，任一级命中都能省掉后续全部查询。

用一个自算的例子说明缓存的价值：设某域名 TTL 为 300 秒、全网每秒查询 1000 次，若所有请求都落在同一台本地服务器上，则 300 秒内只需回源 1 次，回源比例约为

$$ \frac{1}{1000\times300}\approx3.3\times10^{-6}, $$

即缓存命中率在 99.9997% 量级。TTL 的取舍也在这里：调大 TTL 降低权威服务器压力、加快解析，但换 IP 时全网生效慢；调小 TTL 灵活，代价是查询量上升。CDN 与灰度发布场景普遍把 TTL 压到分钟级，就是买这份灵活性。

负缓存同样存在：查询不存在的名字时，权威服务器在 SOA 记录中给出否定回答的缓存时长，避免同一个不存在的名字被反复追问——这也是域名劫持与解析故障排查时要看 SOA 参数的原因。

6.6 一次解析的完整时序

步查询位置命中则结果未命中则
1浏览器自身 DNS 缓存直接返回下一步
2操作系统缓存与 hosts 文件直接返回下一步
3本地域名服务器缓存返回并回填上级缓存下一步
4本地服务器问根得到顶级域服务器地址继续
5问顶级域服务器得到权限服务器地址继续
6问权限服务器得到权威 A 记录报错
7逐级回填并按 TTL 缓存返回给主机—

第 1 步与第 2 步的差别常被忽略：hosts 文件优先级高于 DNS 查询，本地改 hosts 能覆盖线上解析，这也是本地调试与「某些机器能打开、某些不能」类故障的常见成因。

6.7 CDN 与域名解析的关系

CDN 不改变 HTTP，它改变的是解析结果。接入方式通常是给站点域名配一条 CNAME 指向 CDN 厂商的调度域名，于是解析链变成：站点域名 → CNAME → 调度域名 → 全局负载均衡返回某个边缘节点的 A 记录。

调度依据主要有三类：来源 IP 的所属网段与地理位置、各节点的健康与负载、以及 EDNS 客户端子网扩展带来的「真实客户端网段」信息。最后一类很关键：若只看本地域名服务器的地址，调度会把整个城域网的用户都指到同一节点，命中率与就近性都会失真。

由此推出三条工程结论：CDN 域名的 TTL 必须短，否则调度切换不生效；CNAME 链越长，首字节前的往返越多，所以要控制层数；回源失败时的降级要靠多条 CNAME 或备用 A 记录，因为解析层面没有「重试另一台」的机制。

七、邮件协议族与文件传输

7.1 三个协议的分工

协议端口方向作用
SMTP25推送服务器之间传送邮件；提交端口 587 需认证
POP3110拉取把邮件下载到本地，默认下载后删除
IMAP143拉取邮件留在服务器，支持多设备同步与部分获取

邮件系统是「推—拉」组合：发件人用 SMTP 把邮件推到自己服务器，服务器之间用 SMTP 逐跳转发，收件人再用 POP3 或 IMAP 把邮件拉下来。这也解释了一个常见误解——「收邮件用 SMTP」是错的：SMTP 只负责送，不负责取。

7.2 一封邮件的路径

  1. 发件人客户端（MUA）通过提交端口把邮件交给自己的邮件服务器（MSA/MTA），需要身份认证，防止开放中继；
  2. 发送方 MTA 查询收件域的 MX 记录，按优先级从低到高尝试连接；
  3. 对方 MTA 接收并交给投递代理（MDA），存入收件人邮箱；
  4. 收件人客户端用 IMAP 或 POP3 取信。

第 2 步把 DNS 与邮件绑在一起：MX 记录缺失或优先级配错，邮件就会退信或被投到错误主机。反垃圾的另一半也在这里——发信域的 SPF、DKIM、DMARC 三条策略都发布为 TXT 记录，收信方查 DNS 即可判断这封信是否被伪造。

7.3 MIME 与编码膨胀

SMTP 原本只能传 7 位 ASCII，二进制附件需用 base64 编码，膨胀率为 $4/3$。若再加上每 76 个字符插入一次回车换行，膨胀率约为

$$ \frac{4}{3}\times\Big(1+\frac{2}{76}\Big)\approx1.368 . $$

即 10 MB 的附件在线路上约 13.7 MB。这个数字在估算邮件大小限制、网关存储与传输时间时都要用到，而且它解释了一个现象：附件大小上限通常按编码后的体积判定，而不是原始文件大小。

7.4 FTP 的双连接

FTP 用两条 TCP 连接：控制连接（21 端口）传命令与应答，数据连接（20 端口或随机端口）传文件内容。主动模式下服务器用 20 端口主动连客户端，遇客户端在防火墙后就会失败；被动模式由客户端发起数据连接，端口由服务器临时指定，因此能穿过大多数防火墙。这也是「FTP 有两个端口」这句话必须补上模式限定的原因。

八、一次页面加载的往返统计

仍取 RTT 为 50 ms、忽略带宽与解析时间，考察 96 个同等大小的小资源（每资源需 1 个往返）：

方案连接建立资源获取合计往返折合时延
HTTP/1.1，6 条并行连接，TLS 1.26 条连接握手，按 3 个往返计（并行）每连接 16 轮，共 16 个往返19950 ms
HTTP/1.1 单连接、关闭管线化396994950 ms
HTTP/2，单连接多路复用，TLS 1.23约 1（全部请求同一飞行）4200 ms
HTTP/2 加 TLS 1.32约 13150 ms

第二行是理论上最坏的单连接串行情形，列出来只为给出量级对照：96 个资源串行要 96 个往返，这正是多连接与多路复用要解决的问题。第三行与第一行相差 15 个往返，说明 HTTP/2 的收益主要来自「把 6 条连接的握手压成 1 条」加上「把 16 轮资源获取压成 1 轮」，而不是来自首部压缩。

九、易错点

  1. 把 304 当成没发生请求。304 仍是一次完整往返，只是响应不带实体。
  2. 把 no-cache 当成不缓存。它要求每次使用前验证；禁止存储的是 no-store。
  3. 以为 HTTP/2 解决了全部队头阻塞。它只解决了应用层的，TCP 层丢包仍会阻塞所有流。
  4. 以为 Cookie 与 Session 是二选一。Session 的标识通常就存在 Cookie 中，二者配合。
  5. 把 SameSite=None 当作放宽限制的唯一动作。它必须与 Secure 同时出现才会被接受。
  6. 把 TLS 1.2 的握手记成 1 个往返。全握手是 2 个往返，1 个往返是 TLS 1.3 才有的。
  7. 以为证书链只要叶证书。中间证书必须由服务器下发，否则部分客户端无法补全链路。
  8. 从左往右读域名层级。层级自右向左，最左是主机标签。
  9. 把根域名服务器数成 13 台机器。13 是地址身份数，实例数是其上百倍。
  10. 认为收邮件用 SMTP。SMTP 只推不拉，取信靠 POP3 或 IMAP。

十、小结

知识块必记结论
HTTP/1.1文本报文；方法的安全与幂等要分开看；301 永久、302 临时、307 保方法、304 无实体；持久连接为默认
缓存强缓存不发请求（max-age），协商缓存发请求回 304（ETag/Last-Modified）；no-cache 验证、no-store 禁存
HTTP/2二进制分帧、单连接多流、HPACK（静态表 61 项加动态表）、两级信用流控；仍受 TCP 队头阻塞
HTTP/3基于 QUIC 与 UDP，流级独立排序，握手合并为 1 个往返、恢复可 0 个
Cookie/SessionCookie 六个属性决定作用域与安全边界；Session 靠标识索引服务端数据；分布式下四种扩展方案各有代价
HTTPS混合加密；TLS 1.2 为 2 个往返、1.3 为 1 个、0-RTT 有重放风险；证书链五步校验；ECDHE 提供前向安全
DNS层级自右向左；主机对本地递归、本地对外迭代；记录类型 A/AAAA/CNAME/MX/NS/PTR/SOA/TXT；UDP 53 加 TCP 回退；TTL 决定缓存收益与切换速度
CDN靠 CNAME 接入调度域，按来源网段与 EDNS 子网就近返回；TTL 必须短，CNAME 链要短
邮件与 FTPSMTP 25 推、POP3 110 与 IMAP 143 拉；base64 膨胀约 1.368 倍；FTP 控制与数据双连接，端口取决于主被动模式

应用层的所有设计都在同一条经济账上做权衡：往返次数、字节开销、状态维护成本三者此消彼长。HTTP/1.1 用多连接买并行，HTTP/2 用多路复用省连接，HTTP/3 用 UDP 换掉传输层阻塞；Cookie 用客户端存储省服务端内存，Session 用服务端存储换可控性；DNS 用缓存换查询量，CDN 用短 TTL 换调度灵活。把这条账算清，协议细节就不再是死记硬背。

十一、勘误与口径说明

序号原料表述复核结论判据
1「只有 DNS 可以是无连接的、不可靠的，HTTP、FTP、SMTP 都必须可靠」该结论只覆盖被列举的四种应用。DNS 在响应被截断时改用 TCP；同类无连接应用还有 DHCP、TFTP、SNMP 等协议栈事实；截断位触发 TCP 重查
2「FTP 控制端口 21、数据端口 20」20 端口只用于主动模式；被动模式的数据端口由服务器在高端口范围内临时指定两种模式的连接发起方不同
3「HTTP 的长连接本质是 TCP 长连接」方向正确但不完整：1.1 的持久连接还包含「同一连接上串行处理多个请求」的语义，而 HTTP/2 在同一 TCP 连接上做的是并发多流，二者不能等同单流串行与多流并发的区别
4「传输层是进程之间，网络层是主机之间」与教材一致；但需注意端口只是复用分用的标签，真正定位进程的是「IP 加端口加协议」三元组套接字定义
5DNS 迭代查询「最多 4 次」该结论针对特定域名层级，计数口径（只数本地服务器外发报文）在另一篇笔记中已固定，本文不重算层级数等于权限域层数加根一次

另有两处必须标注为本文自设口径，不能当作原料数据引用：其一，第 5.6 节与第八节的往返账目表，假设为「每个往返 50 ms、忽略带宽与解析、DNS 未命中计 1 个往返、每资源 1 个往返」，原料只描述流程顺序、未给任何时延参数，故表中数字全部按该假设算出；其二，第 6.5 节的缓存回源比例按「TTL 300 秒、每秒 1000 次查询、单台本地服务器」算出，仅用于说明量级，不代表任何真实服务的命中率。
