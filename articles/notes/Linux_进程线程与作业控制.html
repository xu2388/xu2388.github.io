操作系统/Linux · 进程、线程与作业控制

一、概述：两条线看同一个任务

进程与线程的区别，背定义容易，用起来难。真正有用的是两句话：进程是资源分配与隔离的单位，线程是 CPU 调度的单位。前者解释为什么两个进程的变量互不可见、一个进程崩溃通常不拖垮另一个；后者解释为什么同一进程内的线程切换比跨进程切换便宜、为什么多线程能并行。

本文按「模型 → 控制 → 观测 → 故障」组织：先讲资源归属与状态机，再讲 fork、exec、wait 这三个原语，然后讲会话与作业控制、信号，最后落到 ps、top、pgrep 的排查路径和 Python 多进程的实际坑。

与已有笔记的分工要先讲清。《操作系统与 Shell 脚本》按命令与考点组织，给的是「这条命令干什么、这个选项怎么选」；本文按模型与排障组织，命令只保留解释模型必需的部分，不重复命令清单。《Linux 用户权限与 ACL》讲进程凭据如何参与文件访问判定；本文只在 fork 与 exec 处提到凭据继承，不展开权限串。《Linux 本地存储管理》讲磁盘与挂载；本文提到的 /tmp、/dev/shm 只作为多进程故障的现场。

还有一层区分容易被忽略：Java 的线程状态是 JVM 定义的状态，Linux 的进程状态是内核调度器的状态，两者名字相似但不在同一层。本文在 3.4 节专门对照，避免把 RUNNABLE 直接当成 R。

二、进程与线程：资源与调度

2.1 哪些资源独有，哪些共享

同一进程内的线程共享地址空间，这是所有差异的源头。把资源逐项列开，比记「线程轻量」有用：

资源进程之间同一进程的线程之间
虚拟地址空间与页表各自独立共享
代码段、数据段、堆各自独立共享
栈主线程栈属于进程每个线程独立
寄存器与程序计数器切换时保存到内核栈每个线程独立
文件描述符表各自一张共享同一张
打开文件的偏移量各自独立共享，因为指向同一 open file description
当前工作目录、umask各自一份共享
信号处置方式进程级共享
信号屏蔽字进程有一个初值每个线程可独立设置
uid、gid 等凭据各自一份共享
调度实体线程组整体参与每个线程单独排队

两行需要特别解释。文件描述符表共享，意味着一个线程 open 的文件，其他线程立刻能用同一个编号读写；而偏移量共享，意味着两个线程各读一半会把文件读乱，除非用 pread 这类带偏移的接口。信号处置共享、屏蔽字独立，意味着一个线程把 SIGTERM 设成忽略，全进程都忽略；但一个线程屏蔽 SIGTERM，不影响其他线程接收。

2.2 内核眼里没有「进程」这个特殊结构

Linux 不给进程和线程两套结构，统一用 task_struct 描述一个调度实体。所谓线程，就是一组通过 clone 共享了地址空间、文件表、信号处置等资源的任务；所谓进程，就是共享得少、拥有独立地址空间的任务组。线程组用 tgid 标识，组内每个任务有自己的 pid。

ps -eLf | head
ls /proc/$$/task
grep -E '^(Pid|Tgid|Threads):' /proc/$$/status

/proc/<pid>/task/ 下每个子目录是一个线程，目录名就是 tid。主线程的 tid 等于 pid，tgid 对全组相同。判断一个任务是多线程还是多进程，看 tgid 与 pid 是否相等即可：相等是组长，不等是同组的线程。

2.3 切换成本差在哪里

上下文切换要保存当前任务的寄存器、栈指针、调度信息，再恢复下一个任务的。跨进程切换还多一步：换页表。页表一换，TLB 里缓存的地址翻译大多失效，随后一段时间的访存会变慢；同一进程的线程共享页表，切换时不用换，TLB 仍然有效，缓存局部性也更好。

这解释了两个工程现象。第一，大量短任务用线程池比反复 fork 划算，因为省掉地址空间与页表的建立。第二，线程并非越多越好：每个线程有独立的栈，默认栈大小通常是几 MB 量级，线程数上去后虚拟内存与内核调度开销都会成为瓶颈。

2.4 通信方式与适用边界

方式是否有亲缘要求数据边界同步典型用途
匿名管道是，父子或兄弟字节流，无消息边界内核缓冲，读写阻塞Shell 的 ``
命名管道否字节流同上无亲缘进程的简单单向传递
消息队列否有消息边界内核维护小消息、带类型分发
共享内存否由使用者约定自身不提供，必须配信号量大数据量、低延迟
信号量否计数自身即同步原语控制并发数与互斥
信号否只有信号编号，附带信息极少异步打断通知与终止
套接字否字节流或数据报协议自理跨主机、全双工

两条常见误判。共享内存不是「自带同步的队列」，它只是一块双方都能映射的内存，读写顺序要靠信号量或互斥锁；管道是字节流，写入两次 write 的数据在读取端可能一次读到，不能假设「一次写对应一次读」。

三、PCB 与状态机

3.1 task_struct 里有什么

进程控制块保存内核管理一个任务所需的全部信息：状态与调度信息、pid 与 tgid、指向地址空间的 mm、文件表 files、信号处置 sighand、凭据 cred、父子兄弟关系、CPU 时间记账、命名空间等。用户态通过 /proc/<pid>/ 看到的是这些字段的部分投影。

cat /proc/$$/status
ls -l /proc/$$/fd
readlink /proc/$$/cwd
tr '\0' ' ' < /proc/$$/cmdline; echo

status 里的 State 是状态，Threads 是线程数，VmRSS 是常驻内存；fd 目录里的符号链接指向实际打开的文件；cmdline 是以 NUL 分隔的参数字节串，直接 cat 会连成一片，需要把 NUL 换成空格或换行。

3.2 状态字母表

ps 的 STAT 列首字母是主状态，后面的小写字母是修饰符：

字母名称含义能否被信号唤醒或终止
Rrunning / runnable正在 CPU 上运行，或在运行队列里等 CPU能
Sinterruptible sleep可中断睡眠，等待事件、锁、I/O能，信号可打断
Duninterruptible sleep不可中断睡眠，通常等磁盘或网络文件系统 I/O信号要等内核路径返回才处理，SIGKILL 也无效
Tstopped被作业控制或 SIGSTOP 停止只能由 SIGCONT 继续
ttracing stop被调试器停止由调试器控制
Zzombie已退出，等待父进程回收不能，信号无意义
Iidle空闲内核线程不适用
Xdead已死亡，几乎观察不到不适用

修饰符里常见的有：s 是会话首进程，l 是多线程，+ 属于前台进程组，< 是高优先级，N 是低优先级。Ss、Rsl、S+ 这类组合读法就是「主状态加修饰」。

ps -eo pid,ppid,stat,etime,cmd --sort=-etime | head
ps -eo stat | sort | uniq -c | sort -rn

第二条命令统计各状态的任务数：S 多属正常，D 多说明存储侧卡住，Z 多说明父进程没回收。

3.3 状态迁移

起点事件终点
不存在fork 或 clone 完成就绪

运行时间片耗尽或被更高优先级抢占就绪

表里最该盯住的是第五行：阻塞结束回到就绪队列，还要再竞争一次 CPU 才能运行。把「sleep 结束就立刻继续执行」当成保证，会写出依赖时序的代码；把「阻塞结束直接回运行」写进答题，也是常见失分点。

3.4 Java 线程状态不是 Linux 状态

Java Thread.State含义在 Linux 上可能对应
NEW对象已创建，尚未 start没有对应的内核任务
RUNNABLE可运行，包含正在跑、在就绪队列、以及原生阻塞调用R 或 S
BLOCKED等待进入 synchronized 临界区通常 S
WAITINGwait、join、park 无限等待S
TIMED_WAITINGsleep、带超时的 wait 或 joinS
TERMINATEDrun 结束任务已消失

RUNNABLE 是最大的坑：JVM 把「正在 CPU 上跑」和「已经可跑、等 CPU」合并成一个状态，甚至把阻塞在 socket 读上的线程也标成 RUNNABLE。所以 jstack 里看到一片 RUNNABLE，不能推断 CPU 正在忙，要结合 top -H 与线程栈判断。反过来，Linux 的 R 也不等于 Java 的 RUNNABLE，前者是内核调度器的视角。

四、fork、exec 与 wait

4.1 fork 返回两次

pid_t pid = fork();
if (pid == 0) {
    /* 子进程：这里 pid 为 0 */
} else if (pid > 0) {
    /* 父进程：pid 是子进程号 */
} else {
    /* 失败：返回 -1，errno 有原因 */
}

fork 成功时在父进程返回子进程 pid，在子进程返回 0，所以「返回两次」；失败只返回一次，值为 -1。子进程拿到的是父进程地址空间的一份副本，但内核用写时复制推迟真正的复制：父子共享只读页面，任何一方写入触发缺页，才复制该页。于是 fork 本身很快，代价转移到写入时。

写时复制不影响语义上的独立性：子进程改变量，父进程看不到，反之亦然。但有两样东西不是复制而是共享的：打开文件描述与文件偏移。子进程继承的是文件描述符表的副本，表项指向同一个 open file description，所以父子交替写同一个文件会接着写，不会各写各的。

int fd = open("项目目录/日志.txt", O_WRONLY | O_APPEND);
pid_t pid = fork();
/* 父子都持有 fd，共享偏移；O_APPEND 让每次写都追加到末尾 */

标准 I/O 缓冲是另一个坑：fork 会把用户态缓冲区一并复制。若父进程在 fork 前用 printf 写了内容但没换行、没刷新，子进程会带着同一份缓冲，退出时再刷一次，输出就重复了。稳妥做法是 fork 前 fflush(NULL)，或者用不带缓冲的 write。

连续 fork 的进程数常被拿来出题。若每个已存在的进程都再 fork 一次，进行 \(n\) 轮后进程数为：

$$ N_n = 2^n. $$

轮数 n进程数
01
12
24
38
416

若循环里只有父进程 fork、子进程立即 break 或 exit，则是父进程加 \(n\) 个子进程，共 \(n+1\) 个。判断这类问题的关键是：fork 之后父子都从下一条语句继续，除非代码显式让某一方退出。

4.2 exec 换的是映像，不是进程

exec 系列把当前进程的代码段、数据段、堆、栈替换成新程序，PID 不变，进程号背后的「身份」不变：

属性exec 之后
PID、PPID不变
已打开的文件描述符保留，除非设了 FD_CLOEXEC
当前工作目录、umask保留
uid、gid 与附加组保留
被捕获的信号处置复位为默认
被忽略的信号保持忽略
信号屏蔽字保留
命令行参数与环境由新程序决定，环境可继承或替换
execlp("ls", "ls", "-l", "项目目录", (char *)NULL);
perror("execlp");   /* 只有失败才会执行到这里 */

exec 成功不返回，失败返回 -1 并继续执行原程序。写完 exec 不检查返回值，是脚本与 C 程序里都常见的疏漏：路径错了，程序会若无其事地往下跑。

system 与 popen 都是封装：system 等于 fork 加 exec 一个 Shell 再 wait，所以它受 Shell 元字符影响，返回值是 wait 状态的编码；popen 多建一个管道，用 pclose 回收。在多线程程序里 fork 之后、exec 之前只能调用异步信号安全函数，malloc、printf 都可能因为其他线程持有锁而死锁，这是「fork 后立刻 exec」这条规矩的由来。

4.3 wait 与退出状态

int status;
pid_t p = waitpid(pid, &status, 0);
if (p == -1) {
    perror("waitpid");
} else if (WIFEXITED(status)) {
    printf("exit=%d\n", WEXITSTATUS(status));
} else if (WIFSIGNALED(status)) {
    printf("signal=%d\n", WTERMSIG(status));
}

退出状态不是简单的整数：低八位放退出码，另外的位放终止信号与是否产生核心转储。直接打印 status 会得到奇怪的数字，必须用 WIFEXITED、WEXITSTATUS、WIFSIGNALED、WTERMSIG 解码。

wait 等任意一个子进程，waitpid 可以指定 pid；WNOHANG 让它非阻塞，没有已退出的子进程就立刻返回 0。父进程没有子进程时，wait 返回 -1，errno 为 ECHILD。这些返回值要分开处理，否则「没有子进程」会被误判成「回收失败」。

五、作业控制：会话、进程组与前后台

5.1 三个层次

作业控制建立在三个概念上：

  • 会话：一组进程组的集合，通常与一次登录或一个终端绑定，由 setsid 创建。
  • 进程组：一个作业，管道里的多条命令属于同一进程组，有共同的 PGID。
  • 控制终端：会话关联的终端设备；同一时刻只有一个前台进程组，终端的按键信号只发给它。
ps -o pid,ppid,pgid,sid,tpgid,stat,cmd -p $$

pgid 是进程组号，sid 是会话号，tpgid 是当前占用终端的前台进程组号。tpgid 等于某个进程的 pgid，说明那个组在前台。

5.2 &、Ctrl-Z、jobs、fg、bg

sleep 300 &
jobs
jobs -l
fg %1
bg %1

& 让命令在后台启动，Shell 打印作业号与 PID。jobs 列出当前 Shell 的作业表，-l 附带 PID。fg %1 把 1 号作业放到前台并继续，bg %1 让停止的作业在后台继续。

Ctrl-Z 不是终止，而是给前台进程组发 SIGTSTP，默认动作是停止；Shell 随即拿回终端，打印 Stopped。Ctrl-C 发的是 SIGINT，默认动作是终止。把这两个键当成一回事，就会误以为「按 Ctrl-Z 退出了程序」，其实进程还在，只是停在 T 状态，仍占着内存与打开的文件。

作业号是 Shell 自己维护的短编号，不是 PID。%1、%+（当前作业）、%-（上一个作业）都是作业规格；kill %1 可以按作业号发信号。换一个 Shell 或重新登录，作业表是空的，旧作业仍在系统里，只能用 ps 找。

5.3 脱离终端：nohup、disown、setsid、tmux

SSH 断开时，终端关闭，内核给会话首进程发 SIGHUP，Shell 通常再把 SIGHUP 转发给作业。要让长任务活下来，有几种层次不同的做法：

nohup python3 项目目录/train.py > 项目目录/train.log 2>&1 &

disown -h %1

setsid python3 项目目录/train.py > 项目目录/train.log 2>&1 < /dev/null &

tmux new -s train
手段做了什么边界
nohup让命令忽略 SIGHUP，stdout 是终端时重定向到 nohup.out仍在原会话，仍可能受作业控制影响
disown -h从 Shell 作业表移除，或标记为不接收 HUP只影响该 Shell 的转发
setsid新建会话，脱离控制终端失去终端交互，stdin 要重定向
tmux 或 screen由常驻服务持有会话，客户端可断开重连需要服务端进程存活

nohup 只解决 SIGHUP，不解决 stdin：后台进程若读终端，会收到 SIGTTIN 被停止。所以完整的后台启动要把三个流都安排好，< /dev/null 不能省。tmux 的优势是能重新接回交互界面，适合需要看进度、临时敲命令的训练任务；nohup 适合纯日志输出的批处理。

5.4 后台读写终端为什么会停

后台进程组读控制终端时，内核发 SIGTTIN，默认停止该进程组；若终端设了 tostop，后台写也会触发 SIGTTOU。这不是程序 bug，而是终端保护：多个作业同时抢终端输入会互相干扰。fg 把作业放回前台后，SIGCONT 让它继续，读操作才得以完成。

六、信号：异步通知

6.1 常用信号

编号在不同架构上可能不同，脚本里应写信号名而不是数字，kill -l 可以列出本机映射。SIGKILL 与 SIGSTOP 是两个例外：不能被捕获、不能被阻塞、不能被忽略，内核直接执行。

6.2 终止要留余地

kill -9 不给进程清理的机会：缓冲区不刷、临时文件不删、锁不释放、子进程可能变孤儿。正确顺序是先 SIGTERM，给一段退出时间，仍未退出再 SIGKILL：

kill -TERM <pid>
sleep 5
kill -0 <pid> 2>/dev/null && kill -KILL <pid>

kill -0 不发信号，只做存在性与权限检查：返回 0 说明进程存在且有权发信号，返回 -1 且 errno 为 ESRCH 说明不存在。用 kill -0 轮询比 ps | grep 可靠，因为不会匹配到 grep 自身。

给整个进程组发信号用负的 PGID：

kill -TERM -- -<pgid>

-- 用来结束选项解析，否则负号会被当成选项。管道启动的多个进程在同一组，这一招能一次收干净；只杀组长，组员可能继续跑。

6.3 处理函数能做什么

static volatile sig_atomic_t stop = 0;

static void on_term(int sig) {
    (void)sig;
    stop = 1;
}

signal(SIGTERM, on_term);
while (!stop) {
    /* 主循环 */
}

处理函数运行在被打断的线程栈上，必须短、可重入、只调用异步信号安全函数。write 可以，printf、malloc、free 不行——它们可能正在被主流程持有锁，重入就死锁。常见做法是只置一个 volatile sig_atomic_t 标志，或往自管道写一个字节，让主循环去处理。

signal 在不同系统上的语义有差异，正式代码用 sigaction，并按需设置 SA_RESTART：设了它，被信号打断的慢系统调用会自动重启；不设则返回 EINTR，调用方要自己重试。

SIGCHLD 的处理要配合循环回收：

while (waitpid(-1, NULL, WNOHANG) > 0) {
    /* 回收所有已退出的子进程 */
}

只调用一次 waitpid 不够：多个子进程可能几乎同时退出，而信号不排队，一次 SIGCHLD 可能对应多个已退出子进程。

6.4 两个容易踩的信号

SIGPIPE 的默认动作是终止进程。往一个对端已关闭的套接字写数据，第一次写可能成功，第二次就收到 SIGPIPE 直接死掉，看起来像「程序莫名其妙退出」。服务端通常忽略 SIGPIPE，改为检查 write 返回的 EPIPE，这样能走正常错误处理。

SIGHUP 的本意是终端挂断，守护进程把它借用来表示「重载配置」。这只是一个约定，不是内核语义；程序不捕获 SIGHUP，终端一关就退出。

七、观测与排查

7.1 ps 的几种视角

ps aux
ps -ef
ps -eo pid,ppid,pgid,sid,stat,etime,pcpu,pmem,args --sort=-pcpu | head
ps -u user -o pid,ppid,etime,stat,cmd
ps -eLf
ps -T -p <pid>

aux 是 BSD 风格，列有 USER、PID、%CPU、%MEM、VSZ、RSS、TTY、STAT、START、TIME、COMMAND；-ef 是 System V 风格，列有 UID、PID、PPID、C、STIME、TTY、TIME、CMD。两种风格不要混用选项。

-eLf 把每个线程单列一行，LWP 列是线程号；-T -p 只看指定进程的线程。查「哪个线程在吃 CPU」时，先 top -H -p <pid> 找到高占用的 TID，再到 ps -T 或线程栈里对照。

7.2 top 的几个读数

  • 负载平均值：1、5、15 分钟的平均可运行任务数加不可中断任务数。要结合 CPU 核数看；负载高而 CPU 空闲，往往是 D 状态在等 I/O。
  • %CPU：单核为 100%，多线程进程可以超过 100%，表示它同时占用了多个核。
  • VIRT 是虚拟地址空间大小，RES 是常驻物理内存，SHR 是其中可共享的部分。VIRT 很大不代表真占内存，RES 才接近实际压力。
  • S 列是状态，D 增多要去看存储。

交互键里，1 展开每核，H 切换线程视图，M 按内存排序，P 按 CPU 排序，c 显示完整命令行。批处理场景用 top -b -n 1 取一次快照写日志。

7.3 pgrep 与 pkill

pgrep -af python
pgrep -u user -f 'train.py'
pgrep -P <ppid>
pkill -TERM -u user -f 'train.py'

-f 匹配完整命令行，不加只匹配进程名。-a 同时打印命令行，-u 限定用户，-P 按父进程过滤。pkill 的匹配范围要写得足够具体：-f 'python' 会命中所有 Python 进程，-f 'train.py' 才收窄到一个项目。执行前先用 pgrep 同样的条件列一遍，确认名单再换成 pkill。

7.4 /proc 是现场

cat /proc/<pid>/status
tr '\0' '\n' < /proc/<pid>/environ
ls -l /proc/<pid>/fd
readlink /proc/<pid>/cwd
cat /proc/<pid>/io

status 看 State、Threads、VmRSS、VmSwap；environ 看启动时的环境变量，排查「为什么没读到配置」很直接；fd 数文件描述符，数量持续上涨就是泄漏；cwd 看工作目录，相对路径问题一目了然；io 看读写字节数，判断是否真的在做 I/O。

/proc/<pid>/maps 列出内存映射的库与文件，/proc/<pid>/stack 需要权限，能看到内核栈，是判断 D 状态卡在哪一层的手段之一。

7.5 文件与端口

lsof -p <pid>
lsof +D 项目目录
lsof +L1
ss -lntp
ss -tnp state established

lsof -p 列出进程打开的文件；+D 递归看目录被谁占用；+L1 找 link count 小于 1 的已删除文件。最后一条能解释「df 显示满、du 却很小」：文件被删除但仍有进程持有 fd，空间不会释放，直到那个进程关闭文件或退出。

ss -lntp 看监听端口与对应进程，-t 是 TCP，-n 不做名字解析，-p 显示进程。端口被占用的报错，先用它确认占用者，再决定改端口还是停进程。

7.6 GPU 进程

nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
nvidia-smi | grep -A 100 "Processes:"
ps -u "$(whoami)" -o pid,ppid,etime,cmd

nvidia-smi 的进程表给的是 PID 与显存占用，不直接给用户名；把它的 PID 列表与 ps -u 的结果对照，才能确认哪些是自己的。多用户服务器上，看到显存被占先确认 PID 归属，不要凭进程名猜。终止前用 ps -o pid,user,cmd -p <pid> 再核一次，避免误杀他人任务。

7.7 一条排查路径

症状先执行的命令判断依据
CPU 高top -H -p <pid>、ps -T单线程满核还是多线程分摊
内存持续上涨ps -o rss、/proc/<pid>/statusRSS 涨而业务量不涨，疑泄漏
大量 D 状态ps -eo stat,pid,cmd、dmesg存储、网络文件系统或设备卡住
端口被占ss -lntp谁在监听，是否旧进程未退
磁盘满但 du 小lsof +L1已删除文件仍被持有
进程杀不掉ps -o statD 等 I/O，Z 等父进程回收
断开 SSH 后任务没了jobs、ps -u user是否用了 nohup、tmux
显存被占nvidia-smi 加 ps 对照残留进程或他人任务

排查的顺序应是「先定位资源、再定位进程、最后定位代码」：top 或 ps 找到异常进程，/proc 与 lsof 看它在等什么、持有什么，再回到代码或配置。反过来一上来就翻日志，容易在无关的错误信息里打转。

八、僵尸与孤儿

8.1 僵尸是没被回收的退出状态

子进程退出时，内核释放它的地址空间、打开的文件等资源，但保留 PID、退出状态和记账信息，等父进程用 wait 取走。取走之前，这个任务就是僵尸：ps 的 STAT 是 Z，命令名后带 <defunct>。

ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'

僵尸不能被杀。它已经不再运行，没有任何执行流可以接收信号，kill -9 对它无效；唯一让它消失的办法是父进程调用 wait 回收，或者父进程先退出，让它被 init 或 subreaper 接管后回收。大量僵尸会耗尽 PID 表，最终导致新进程无法创建，所以「僵尸无害」的说法只在数量少时成立。

8.2 谁来回收

while (waitpid(-1, &status, WNOHANG) > 0) {
    /* 收一个算一个 */
}

父进程可以主动轮询，也可以在 SIGCHLD 处理函数里循环回收。若父进程长期运行又从不 wait，僵尸就会堆积；此时改父进程是唯一正确的修法，杀僵尸本身没有意义。

Linux 上还有两条路径。父进程退出后，孤儿被 PID 1 收养，PID 1 负责回收；容器里 PID 1 常常是应用本身，应用不回收就会积僵尸，所以容器运行时提供 --init 之类的选项，注入一个会回收的小 init。另一条是 PR_SET_CHILD_SUBREAPER，让某个进程成为子树内孤儿的接管者，适合守护进程管理自己的后代。

有一个细节常被误解：SIGCHLD 的默认处置是「忽略」，但默认忽略仍会产生僵尸；只有在进程里显式把 SIGCHLD 设为 SIG_IGN，Linux 才会自动回收子进程。这是 Linux 的行为，可移植代码不应依赖它，显式 wait 更稳。

8.3 孤儿不是故障

父进程先退出，子进程仍在运行，这就是孤儿。它被 PID 1 或 subreaper 收养，PPID 变成 1，继续正常工作。守护进程的经典做法是两次 fork：第一次让子进程成为孤儿并被收养，第二次再 setsid 脱离终端，中间进程退出，最终进程与终端彻底无关。

需要注意，孤儿与僵尸是两件事：孤儿是「活着的、被收养的」，僵尸是「已退出的、没被回收的」。一个进程可以先成为孤儿，退出后再成为僵尸，由收养者负责回收。

九、Python 多进程在 Linux 上的坑

9.1 三种启动方式

方式行为适用代价
fork直接复制父进程地址空间Linux 传统默认，启动快与线程、CUDA 共用时危险
spawn启动全新解释器，导入主模块跨平台、与 CUDA 兼容启动慢，参数必须可序列化
forkserver先起一个干净的服务器进程，再由它 fork兼顾速度与安全配置稍复杂

较新的 Python 版本正在调整 Linux 上的默认启动方式，代码不应假设默认值。显式写清楚更稳：

import multiprocessing as mp

if __name__ == "__main__":
    ctx = mp.get_context("spawn")
    with ctx.Pool(4) as pool:
        print(pool.map(工作函数, 任务列表))

get_context 返回一个使用指定启动方式的上下文，后续的 Pool、Process 都从它创建，避免全局设置影响其他库。

9.2 主模块保护不是形式

spawn 与 forkserver 会重新导入主模块，若创建进程的代码写在模块顶层，子进程导入时又会创建进程，形成递归。if __name__ == "__main__": 把入口隔开，是硬性要求。fork 方式下不写通常也能跑，但一旦换到 spawn 就报 RuntimeError，错误信息会提示引导阶段的问题。

序列化也有边界：传给子进程的函数与参数必须能被 pickle。顶层函数可以，lambda、嵌套函数、打开的文件句柄、数据库连接通常不行。报错往往出现在 Pool.map 调用处，根因却在被传对象的定义方式。

9.3 /tmp/pymp-* 与 Errno 28

多进程在传递任务与结果时会创建临时目录，名字形如 /tmp/pymp-xxxx。进程异常退出、被 SIGKILL、或父进程没清理，目录就会残留。任务量大、进程数多时，/tmp 可能被填满：

OSError: [Errno 28] No space left on device: '/tmp/pymp-un1rus4e'

这条报错说的是「创不了临时目录」，不一定是数据盘满。排查顺序：

df -h /tmp
df -i /tmp
ls -d /tmp/pymp-* 2>/dev/null | wc -l

df -h 看块空间，df -i 看 inode；大量小文件先把 inode 耗尽，块空间却还有富余。清理只动自己的残留：

find /tmp -maxdepth 1 -type d -name 'pymp-*' -user "$(id -u)" -mtime +1 -exec rm -rf {} +

更稳的办法是把临时目录迁到项目盘，并在启动脚本里固定下来：

mkdir -p 项目目录/临时
export TMPDIR=项目目录/临时

TMPDIR 会影响 tempfile 与多进程的临时目录位置，子进程继承环境变量，改一处即可。清理逻辑放在 finally 里，能覆盖异常，但覆盖不了 SIGKILL，所以定期巡检仍然必要。

/dev/shm 也会给出同样的 Errno 28。共享内存、信号量、部分张量传输都落在这里，容器默认给它的空间往往不大：

df -h /dev/shm
ls -la /dev/shm | head

9.4 信号量与共享内存泄漏

multiprocessing.Semaphore、Lock 在 Linux 上依赖命名信号量，异常退出可能留下 sem.* 节点。它们不会自己消失，长期运行的服务反复创建就会耗尽。排查时看 /dev/shm 里的残留，确认没有活着的使用者后再清理；清理他人或仍在使用的信号量会让别的进程卡死。

共享内存段同理：Pool 传递大对象时可能落到 /dev/shm，进程被强杀后段仍挂着。容器里跑大数据量任务，要给 /dev/shm 留足空间，而不是等报错再改。

9.5 CUDA 与 fork 不兼容

父进程初始化 CUDA 之后再 fork，子进程继承的是一个不可用的 CUDA 上下文，典型报错是不能再初始化 CUDA。规避方式有三条：在 CUDA 初始化之前 fork；改用 spawn 或 forkserver；把 CUDA 初始化放到每个子进程内部。

DataLoader 的 worker 也遵守这条：worker 做 CPU 侧的加载与增强，模型与张量留在主进程；pin_memory 由主进程配合，不要把已分配的 GPU 张量塞进队列传给 worker。worker 数量不是越多越好，每个 worker 都是一个进程，会占内存、文件描述符与临时目录。

9.6 Pool 的收尾

pool = mp.Pool(4)
try:
    result = pool.map(工作函数, 任务列表)
finally:
    pool.close()
    pool.join()

close 表示不再提交新任务，join 等现有任务完成；terminate 直接杀 worker，正在写的文件与共享内存可能来不及清理。用 with Pool() 时，退出上下文默认走 terminate，想要「跑完再退」仍要显式 close 加 join。守护进程属性的 worker 不能再创建子进程，嵌套并行会报错，这是防止进程树失控的保护。

9.7 清理残留进程

ps -u "$(whoami)" -o pid,ppid,stat,etime,cmd | grep -E 'python|train'
pkill -TERM -u "$(whoami)" -f 'train.py'

先列后杀，确认 PID、启动时间与命令行。pkill 的 -f 匹配范围要窄，-u 限定自己；多人服务器上误杀他人训练的代价很高。TERM 之后等几秒再检查，仍有残留再考虑 KILL；处于 D 状态的进程连 KILL 也不会立即生效，要先解决它等待的 I/O。

十一、总结

知识块必记结论
进程与线程进程是资源分配与隔离单位，线程是调度单位；线程共享地址空间、文件表与信号处置，独享栈与寄存器
状态R 运行或就绪，S 可中断睡眠，D 不可中断，T 停止，Z 僵尸；阻塞结束回就绪
fork返回两次，子进程得 0；写时复制；文件偏移共享；缓冲区会复制
exec换映像不换 PID；fd、cwd、凭据保留；捕获的信号复位
wait用宏解码状态；WNOHANG 非阻塞；没有子进程返回 ECHILD
作业控制会话管进程组，前台组收终端信号；jobs 只看当前 Shell
脱离终端nohup 挡 HUP，setsid 脱离会话，tmux 可重连；stdin 要重定向
信号KILL 与 STOP 不可捕获；先 TERM 后 KILL；处理函数只做置标志
排查ps 看状态，top 看资源，pgrep 定位，/proc 与 lsof 看现场
僵尸与孤儿僵尸等父回收，杀不掉；孤儿被 PID 1 或 subreaper 收养
Python 多进程启动方式要显式；__main__ 保护；/tmp、/dev/shm、inode 三处查；CUDA 用 spawn

进程这一章的内容多，但线索只有一条：谁持有资源、谁在等、谁负责回收。把这三问套到 fork、作业控制、信号和僵尸上，零散的命令就会落到同一个模型里；排查时也不会停留在「试试 777、试试 kill -9」这种碰运气的层面。
