# 区块链与比特币原理 · 区块结构、哈希链接与脚本系统

## 一、概述

区块链在概念层面可以概括为一句话：**所有人共同记账、且没人能偷偷改的公开分布式账本**。它不特指某个软件，而是一套"数据怎么存、共识怎么达成"的规则组合。比特币是这套规则的第一个完整落地系统：白皮书发布于 2008 年 10 月 31 日，创世区块于 2009 年 1 月 3 日（UTC）产生；"区块链（Blockchain）"这一名词，是后人对白皮书中"一串串联起来的区块（a chain of blocks）"表述的浓缩命名。

本文按"结构—链接—校验—共识—发行—应用"的顺序整理，重点是区块头字段及其相互依赖、父哈希造成的链式不可篡改、默克尔树的构造与校验用途、UTXO 与脚本的配对验证，并附减半周期推导与一次推导订正。

## 二、分布式账本：与传统数据库的差别

比特币账本不存放在中心服务器，而由全网对等节点各自冗余保存一份完整副本，交易全网广播、公开可查，并由密码学保证无法篡改、删除与伪造。需注意**去中心化一定是分布式系统，但分布式系统不一定是去中心化**，区块链只是借用了分布式架构来做账本。

二者最本质的差别在操作集合：

| 账本类型 | 支持的操作 | 权限模型 |
|---|---|---|
| 传统中心化数据库 | 增加、删除、修改、查询 | 管理员拥有最高权限，可后台改动历史数据 |
| 区块链（比特币账本） | 仅追加写入与查询 | 历史区块被密码学锁定，改一个字节即导致链条哈希断裂 |

## 三、区块结构：头体分离与区块头六字段

每个区块都是一份"账本页"，结构上严格分为**区块头（Header）**与**区块体（Body）**两部分。区块头是哈希挖矿、链式绑定与交易校验所依赖的核心数据，共 6 个字段、合计约 80 字节；区块体存放本区块打包的交易列表。

```text
   父区块 H-1            目标区块 H             子区块 H+1
  +------------+       +--------------+       +------------+
  |  区块头      |      |  区块头        |      |  区块头      |
  |  Version     |      |  Version      |      |  Version     |
  |  PrevHash    |      |  PrevHash <---|----  |  PrevHash <--|-- = Hash(H)
  |  MerkleRoot  |      |  MerkleRoot   |      |  MerkleRoot  |
  |  Timestamp   |      |  Timestamp    |      |  Timestamp   |
  |  Bits / Nonce|      |  Bits / Nonce |      |  Bits/Nonce  |
  +------------+       +--------------+       +------------+
  Hash(H-1) ----|----> |  区块体          |   |--          |
                       |  Tx0(Coinbase)  |   |  = Hash(H)  |
                       |  Tx1 ... Tx7    |   |             |
                       |  默克尔树 -> Root |   |             |
                       +--------------+       +------------+

   时间关系：t(H-1) < t(H) < t(H+1)
   逻辑关系：PrevHash(H) = Hash(H-1)，PrevHash(H+1) = Hash(H)
```

区块头字段一览：

| 数据段 | 说明 | 何时更新 | 大小 |
|---|---|---|---|
| Version 版本号 | 标示软件协议版本，表明本区块遵守的验证规则 | 版本升级时 | 4 字节 |
| Pre-block Hash 父区块哈希 | 引用父区块的哈希值 | 构建新区块时 | 32 字节 |
| Merkle Root 默克尔根 | 区块内全部交易构成默克尔树后的根哈希 | 交易列表变化时 | 32 字节 |
| Timestamp 时间戳 | 区块产生的近似时间，秒级 Unix 时间戳 | 初始构建区块时 | 4 字节 |
| Bits 难度目标 | 压缩格式存储的当前目标哈希，用于工作量证明 | 难度调整时 | 4 字节 |
| Nonce 随机数 | 32 位无符号整数，矿工穷举的唯一变量 | 共识过程不断刷新 | 4 字节 |

区块体第一笔交易固定是 **Coinbase 交易**（挖矿奖励交易）：它没有普通交易的输入，输出为矿工获得的出块奖励与手续费，在默克尔树中占据最左侧叶子，位置不能放到中间。

需要强调两点。其一，父区块哈希存放在**当前区块的区块头**中，而不是上一个区块里，画图时极易画反。其二，区块哈希与默克尔根不是一回事：默克尔根只是头中一个字段，区块哈希是对**整个区块头**做哈希：

```text
Hash = SHA256(SHA256(version + prev_hash + merkle_root + time + difficulty + nonce))
```

比特币固定做两次 SHA256（双哈希）。时间戳并不追求绝对精确，只需满足两条宽松约束：大于之前 11 个区块时间戳的**中位数**（实现里即 GetMedianTimePast，取中间值而非算术平均，因此抗单点造假），且不超过本节点当前时间两小时。由此引出课堂思考题——区块时间戳是否一定小于其子区块的时间戳？结论是只要落在允许区间内其他节点均可接受，并不保证严格单调。

## 四、哈希链接与防篡改：改一个区块为何导致后续全部失效

父哈希是整条链的"粘合剂"：每个区块写入前一个区块的哈希摘要，如同在账本每页末尾记下"上一页的指纹"，向前追溯最终到达父哈希为全 0 的创世区块。

一旦有人改动某个历史区块中的任何内容（交易、默克尔根、Nonce 或时间戳），该区块哈希立即改变；其后区块头里存的仍是**改动之前的旧哈希**，校验随即失败、链条在此断裂，断裂点之后的区块不再属于这条被改写的链。教学模拟器把这一过程做成可视化实验：每个区块展示 `hash`、前一区块哈希、`pow` 与 `nonce`，控制面板提供手动出块、调整难度与攻击模拟等入口，难度设为 4 即要求哈希前 4 位为 0；修改中间区块的交易后再校验，可直观看到默克尔根与区块哈希变化、与子区块的连接被标记为失效。

由这条实验逻辑可推演出篡改的四个阶段：

| 阶段 | 攻击者动作 | 直接结果 |
|---|---|---|
| 一、正常主链 | 无 | 每个区块的父哈希严格等于上一区块哈希，链条完整 |
| 二、只改中间区块交易 | 篡改第 3 个区块的交易数据 | 默克尔根与区块哈希随之改变，后一区块父哈希仍是旧值，两区块间校验失败、链条断裂 |
| 三、改后续区块参数 | 把后两个区块的父哈希改为新哈希，各自重新找 Nonce、重做工作量证明 | 得到哈希自洽的私有备选链，但长度与主链相同或更短，不被全网承认 |
| 四、私链超越主链 | 以超过半数算力持续私有出块 | 恶意链成为最长链，全网切换主链，篡改才被承认 |

这里的推演经历过一次订正：最初的理解停留在"把后续区块的参数一起改掉就能修复链条"，遗漏了关键约束——**参数不是随便改数字，每改动一个区块都必须重做工作量证明、找到合法 Nonce**，即便全部重算完成也只是得到一条等长私有链。共识规则以最长有效链为主链，要让改写生效必须以超过半数算力形成持续优势，即通常所称的 51% 攻击。简言之，"改得动数据"与"改得动共识"是两层问题，前者靠哈希链，后者靠算力成本。

## 五、默克尔树：从交易哈希到默克尔根

区块内可能容纳上千笔交易（现网常态，早期仅几十笔），不可能逐笔哈希后全部塞进区块头。默克尔树把每笔交易的哈希作为叶子节点，两两拼接后向上哈希、逐层压缩，最终只留一个根哈希写入区块头。记 $H(\cdot)$ 为双重 SHA256，8 笔交易 Tx0 至 Tx7 的构造过程如下（取 8 笔是因为它恰好能两两配对、便于手算）：

| 层级 | 节点数 | 节点内容 |
|---|---|---|
| 叶子层 | 8 | 8 笔交易各自的交易哈希，最左为 Coinbase 交易哈希 |
| 第 1 层 | 4 | 相邻两笔叶子哈希两两拼接后的哈希值 |
| 第 2 层 | 2 | 上一层相邻两节点再两两哈希 |
| 树根 | 1 | 默克尔根，写入区块头第 3 个字段 |

即每层把相邻两节点拼接后再做一次 $H$：`H01 = H(H(Tx0), H(Tx1))`、`H0123 = H(H01, H23)`，最终 `Merkle Root = H(H0123, H4567)`。

任何一笔交易被改动，其叶子哈希随之改变，并逐层向上污染到默克尔根，最终使区块头校验失败。补齐规则要**按层判断**：每一层若节点数为奇，就把该层最后一个节点复制一份凑成偶数再上推，而不是只看最底层的交易笔数。7 笔交易时叶子层即为奇数，需复制末笔；6 笔交易时叶子层偶数、两两合并得到 3 个父节点，父层仍是奇数，同样要在这一层复制补齐；8 笔恰好 8→4→2→1 全程无需复制。轻节点因此不必下载全量交易，只凭根值与一条自叶子到根的哈希路径即可证明某笔交易是否在本区块中，大幅节省存储与带宽。

## 六、UTXO 与脚本系统

### 6.1 UTXO：余额并不存在，存在的只是可花费的输出

比特币账本并不记录"某人的余额是多少"，而是记录一笔笔**未花费交易输出（UTXO）**：用户可支配的资产由散落在链上的多个未花费输出构成，转账时选取合适的输出加以花费、找零作为新的 UTXO 返还，每笔交易都需私钥签名验证。它与余额模型的差异如下：

| 对比项 | 账户余额模型 | UTXO 模型 |
|---|---|---|
| 账本记录对象 | 每个账户一个余额数值 | 一批未花费的交易输出 |
| 花费方式 | 在余额上做加减 | 选取输入输出，旧输出被消费、产生新输出 |
| 状态来源 | 余额字段本身 | 由全部历史交易推导而来 |
| 合法性依据 | 余额是否充足 | 是否引用真实未花费输出并通过脚本验证 |

教学模拟器初期用的正是简易余额模型，其后续升级项是替换为比特币同款 UTXO 模型。

### 6.2 锁定脚本与解锁脚本：锁与钥匙

比特币不能直接声明"这笔钱归谁"，只能用一段脚本规定"满足什么条件才能动用这笔钱"。机制因此拆成两半：

- **锁定脚本（输出脚本）**相当于锁，写在 UTXO 上，规定转移条件，例如必须用某公钥对应的私钥签名，或 N 人中至少 M 人签名；规则一经上链不再改变。
- **解锁脚本（输入脚本）**相当于钥匙，花费时提交，提供满足条件的证据，如签名与公钥。

验证顺序固定：**先执行解锁脚本，把签名、公钥压入栈中，再执行锁定脚本检查**。栈顶为真则交易合法、UTXO 可花费，为假则直接拒绝。脚本运行于基于栈的虚拟机，指令以 `OP_XXX` 表示，`OP_CHECKSIG` 核对签名是否由对应私钥所签，`OP_RETURN` 写入与花费无关的数据。

### 6.3 常见脚本类型

| 脚本类型 | 锁定脚本存放内容 | 解锁时需提供 | 典型用途与特点 |
|---|---|---|---|
| P2PK 支付到公钥 | 完整公钥 | 对应私钥的签名 | 较早方式，公钥明文上链、体积大，已近乎淘汰 |
| P2PKH 支付到公钥哈希 | 公钥哈希而非公钥本身 | 公钥与私钥签名 | 最常用；链上只见哈希更安全，数据量小因而手续费更低 |
| P2SH 支付到脚本哈希 | 一段脚本的哈希值 | 完整脚本，哈希须与锁上匹配 | 承载多重签名等复杂逻辑 |
| Null-Data 空数据脚本 | OP_RETURN 输出 | 不可花费 | 链上存证（合同、文件哈希、版权）与销毁，被视为假 UTXO |

P2PKH 的验证顺序值得细看：节点先用提交的公钥计算哈希，与锁定脚本中的哈希比对，一致后再验签名。多重签名记作 M-of-N，即 N 个私钥中至少 M 个签名才可花费，例如 2-of-3 表示三人共管、任意两人同意即可动用；一把私钥被盗时，凑不齐 M 个签名也无法转移资产。多签规则文本较长，直接写入锁定脚本既臃肿又昂贵，故打包成脚本哈希、以 P2SH 上链。

### 6.4 图灵不完备：脚本的能力边界

比特币脚本**不图灵完备**，没有循环语句，也缺少复杂条件跳转：能做的是验签名、多签判断、字符串比对与写入数据，不能做的是循环执行、递归与复杂业务逻辑。这既是功能限制也是安全取舍——校验规则越简单，越不易被构造出无法判定的执行路径。需要自动执行复杂合约的场景，交由图灵完备的以太坊虚拟机 EVM 承担。

## 七、工作量证明、难度与最长链

### 7.1 挖矿即穷举 Nonce

出块时区块头的五个参数（版本、父哈希、默克尔根、时间戳、难度目标）都已固定，矿工唯一能自由变动的是 32 位 Nonce。挖矿因此是一次暴力搜索：不断刷新 Nonce，对区块头做双重 SHA256，直到结果小于 Bits 解码出的目标哈希即为解题成功，可打包广播、由其他节点验证后上链。合格哈希表现为前导 0 足够多、数值足够小；模拟器把它直观显示为"前 N 位为 0"，N 即界面难度参数。Nonce 穷举完仍不满足时，矿工可修改 Coinbase 交易中的额外随机值，使交易哈希与默克尔根改变，在不改动交易语义的前提下重新展开遍历，故挖矿也被称为 hash puzzles。

### 7.2 Bits、目标哈希与难度三者关系

Bits 用 4 字节压缩编码代替 32 字节完整目标哈希，以节省区块空间。三者关系是：Bits 是简写，解码得到目标哈希 Target，Target 越小则难度 Difficulty 越大。换算与定义式分别为：

$$Target\_Hash = Coefficient \times 256^{(Exponent-3)}$$

$$Difficulty_{当前区块} = \frac{Target_{难度1区块}}{Target_{当前区块}}$$

其中 Exponent 取 Bits 的前 2 位十六进制，Coefficient 取后 6 位。以 Bits `0x1903a30c` 为例，指数 `0x19`、系数 `0x03a30c`，代入即可还原超长目标哈希。结论一句话：**Bits 数值越小，目标哈希越小，前导 0 越多，挖矿越难**。

### 7.3 难度自动调整：锚定 10 分钟

协议目标是长期平均每 10 分钟出一个区块；算力波动时难度必须随之变化，否则出块间隔会大幅偏离目标。调整规则为：每累计 2016 个区块（理论耗时 2016 × 10 = 20160 分钟，即两周）由全网节点各自独立按同一公式计算一次：

$$next\_difficulty = previous\_difficulty \times \frac{20160}{\text{最近 2016 个区块实际出块总时长}}$$

实际用时小于 20160 分钟说明出块过快，难度上调；大于则出块过慢，难度下调。协议还对单次调整幅度设上下限：新难度最多是旧难度的 4 倍、最少是 1/4，防止算力骤变时目标哈希被一次性拉到无法完成或形同虚设。去中心化的亮点在于**没有任何中心机构下发难度参数**，所有全节点用同一公式自算，结果天然一致。

### 7.4 记账权与最长链

交易需要有人整理、打包写入链上，抢到记账资格者获得新区块的 Coinbase 奖励与所打包交易的手续费。把"解一道耗算力的难题"设为记账门槛而非轮流记账，是因为无门槛记账让任意参与者都能伪造账本；记账权与真实算力成本绑定后，作恶成本被抬高到难以承受。共识规则承认最长有效链，这正解释了第四节中仅重算后续区块不足以篡改成功的原因。

## 八、总量与四年减半：理想模型下的推导与订正

### 8.1 减半周期从何而来

减半的触发条件与时间无关，是纯区块计数规则：**每挖出 210000 个区块，区块奖励减半一次**。所谓"四年"，是把区块数换算成日历时间的二次推导：

$$T_h = \frac{210000 \times 10}{60 \times 24 \times 365} \approx 3.9954 \text{ 年}$$

即每轮需 2100000 分钟、35000 小时、约 1458.33 天，约等于 4 年，故业界俗称"四年减半"。奖励公式中减半次数由区块高度整除 210000 得到：

```text
halvings = block_height // 210000
reward   = 50 / (2 ** halvings)
```

| 减半次序 | 年份 | 区块奖励变化（BTC） |

### 8.2 总量 2100 万的数学来源

初始奖励 50 枚、每轮 210000 个区块、奖励按 1/2 等比递减，总发行量即 $50 \times 210000 \times (1 + \frac12 + \frac14 + \cdots)$，括号内是收敛到 2 的等比级数，上限恰好卡在 2100 万枚。该数值由协议写死，修改需全网绝大多数节点同意，故实际不可超发。最小不可分单位是聪（Satoshi），1 聪 = $10^{-8}$ BTC，1 BTC 可拆为 $10^8$ 份；面额另有 cBTC、mBTC、μBTC 等称呼。

### 8.3 为何"四年"会失真

10 分钟只是出块间隔的目标值，**实际间隔由难度调整机制动态回调**：算力暴涨或回落时，2016 块的调整周期存在滞后，期间真实出块速度偏离 10 分钟，累计 210000 块所需时长必然在 4 年上下浮动。故四年减半是以理想恒定出块速率为前提的**理论标称值**，协议真正的不变量是 210000 这个区块计数，时间只是它的投影。

### 8.4 一次推导订正：2140 年是怎么来的

挖完时间的推导演算中，笔者经历过一次明显错误。第一版程序把"奖励小于 1 聪即停止"的循环终止条件写错，只累加到第 23 轮减半就退出（含初始奖励段共 24 个计时段，$24\times3.9954\approx 95.89$ 年），得出总时长约 95.89 年、结束年份约 2104.89 年，与教材通行的 2140 年对不上。订正后先解不等式：

$$50 \times \left(\frac12\right)^n < 10^{-8} \quad \Longleftrightarrow \quad 2^{n} > 5\times 10^{9} \quad \Longleftrightarrow \quad n > \log_2\!\left(5\times 10^{9}\right)\approx 32.22 .$$

即第 33 轮减半后，每块奖励首次低于 1 聪（$5\times10^{9}/2^{32}\approx 1.164$ 聪仍高于阈值，$5\times10^{9}/2^{33}\approx 0.582$ 聪才跌破）。按每轮理想时长 $\dfrac{210000\times600}{365\times86400}\approx 3.9954$ 年计，33 轮合计约 131.85 年，自 2009 年推得 **约 2140.85 年**；若改用 365.25 天的回归年（每轮 3.9927 年）则为 2140.76 年。两种口径都落在 2140 至 2141 年之间，**教科书通行的 2140 年正是这一严格推导的取整结果**，并非粗略估算。

顺带记录一次对数误算：订正过程中曾把阈值解成 $n>35.54$、进而得出 36 轮与 2152.83 年。复核发现 35.54 恰为 $\log_2(5\times10^{10})$，也就是把 1 聪当成 $10^{-9}$ BTC（正确为 $10^{-8}$）才会得到的数值；单位一错，轮数与年份随之整体偏大。这正说明此类推算必须先固定单位再取对数。

另一处可作总量校验：33 轮减半期间每块奖励之和为 $50\sum_{i=0}^{32}2^{-i}\approx 99.99999999$ 枚，乘以 210000 得累计发行约 20 999 999.9976 枚，与 2100 万上限的差仅约 24.4 万聪。可见"总量 2100 万"是等比级数的收敛上确界，而协议按聪取整的实际发行量恒略低于它。更关键的是，"挖完"不意味着比特币消失，而是区块奖励归零、此后矿工收益仅来自交易手续费。

## 九、链的分类、应用与治理

### 9.1 公有链、联盟链与私有链

按参与权限分为三类，核心差异在谁能读写、谁来共识：

| 维度 | 公有链 | 联盟链 | 私有链 |
|---|---|---|---|
| 准入 | 任何人可加入、可读写 | 若干机构成员共同维护、实名 | 单一组织内部控制 |
| 中心化程度 | 去中心化，无单一管理方 | 部分去中心化，多方共治 | 中心化程度高 |
| 共识方式 | 算力竞争（PoW 等） | 成员节点间协同共识 | 组织内部授权 |
| 典型诉求 | 公开透明、抗审查、不可篡改 | 多方对账、数据共享、合规与效率兼顾 | 内部存证与审计 |

联盟链与私有链以实名、可控、多方共用账本为特点，是产业落地中更常见的形态。

### 9.2 技术层面的应用方向

抛开货币属性，区块链可归纳为不可篡改、时间戳、分布式存证、可追溯与数字确权五种能力，对应落地方向是商品与药品溯源、政务与司法电子存证（合同、版权、证据配合时间戳固定）、供应链与票据对账、跨机构病历共享、公益资金公示、学历证书存证，以及用 `OP_RETURN` 类脚本做文件哈希上链公证。

### 9.3 治理：分工类比与 BIP

比特币网络的权力分配常被类比为三权分立：开发人员编写与维护共识协议，相当于立法；矿工以算力竞争打包交易、生成新区块，相当于行政；普通用户以私钥掌控资产、全网公开查验交易使非法交易无效，相当于司法。没有单一主体能垄断规则。

规则迭代通过 BIP（Bitcoin Improvement Proposals，比特币改进提案）完成，生命周期含草案、提议、生效或活跃，以及被驳回、撤回、暂缓、废弃等状态，提案经邮件列表与代码仓库公示并附实施方案。单个用户私改本地客户端代码无效，违规区块不被全网认可；即使开发者修改规则，节点也保有拒绝升级的选择权。官方核心实现以 C++ 编写，仓库地址：https://github.com/bitcoin/bitcoin

## 十、常见误区

1. **把父区块哈希画反**：前一区块哈希存放在**当前**区块头，而非父区块里。
2. **把默克尔根当区块哈希**：区块哈希是对整个区块头做双重 SHA256，默克尔根只是头中一个字段。
3. **以为改完交易再改后面的数字就能篡改成功**：被改动的每个区块都要重做工作量证明、找到合法 Nonce，且仍需让恶意链成为最长链。
4. **把补齐当成"只看交易笔数奇偶"**：Coinbase 永远是第一笔交易、对应最左叶子；但复制补齐是按层进行的——任何一层节点数为奇就要复制该层末节点，6 笔交易在父层（3 个节点）同样需要补齐。
5. **认为 Bits 越大越难**：关系是反向的，Bits 越小、目标哈希越小、难度越高。
6. **把时间戳当成严格有序保证**：时间戳只作区间校验，不保证父块严格小于子块。
7. **把"四年减半"当精确周期**：协议规定的是 210000 个区块，4 年由 10 分钟理想间隔换算而来，会随实际出块速度偏离。
8. **把 2140 年当成可精确到某一天的预言**：它由"恒定 10 分钟出块 + 奖励低于 1 聪即停"的理想模型严格推得（33 轮、约 131.8 年），但真实年份会随算力与难度调整浮动；把对数解错成 36 轮则会得到 2153 年，那一步的根因是把 1 聪取成了 $10^{-9}$ BTC。
9. **高估脚本能力、错认账本原语**：脚本图灵不完备，不能承担通用智能合约；链上也没有余额字段，可花费资产是 UTXO 集合。

## 十一、总结要点

区块头六个字段构成一条自洽的因果链：默克尔根压缩校验区块体交易，父哈希向前绑定上一个区块，时间戳赋予区块时序烙印，Bits 与 Nonce 共同承载工作量证明。把"改动即改哈希、哈希被子区块引用"两句连起来，即可推出不可篡改的成因，以及篡改必然演化为整链重算与算力竞争的原因。UTXO 与脚本系统回答的是"这笔钱在什么条件下可以被花"，栈式、图灵不完备的执行模型把校验能力限制在可判定、可审计的范围内。发行机制则把总量约束交给代码：210000 块一次减半、每轮理想时长约 3.9954 年、等比级数收敛到 2100 万上限，第 33 轮后每块奖励不足 1 聪，理想模型下的终点即教科书里的 2140 年；而"四年"与"2140"都依赖恒定出块速率这一前提，真实年份会随难度调整浮动。
