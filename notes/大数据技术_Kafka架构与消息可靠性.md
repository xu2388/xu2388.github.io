# 大数据技术 · Kafka 架构与消息可靠性

## 一、概述：先把 Kafka 当成一份日志

Kafka 常被归入消息队列，但它的存储模型更像一份可追加、可回溯的分区日志。理解这一点，后面的副本、offset、消费者组才有统一解释：消息不是被「消费掉」的，而是被消费者按位置读取；消息何时删除由保留策略决定，不由读取动作决定。也正因为如此，Kafka 才能支持多个消费者组各自从头读、支持故障后从 offset 续读、支持把历史数据重新灌进下游。

本文的材料是一套 Kafka 专项练习，覆盖发布订阅模型、核心组件、分区与副本、ISR、生产者分区策略、消费者组与重平衡、KRaft、零拷贝以及典型场景。材料没有给出配置默认值、性能数字、事务与幂等生产者的实现细节，也没有展开 RabbitMQ 的对比。本文按材料能支撑的范围写：机制讲透，数字不编，缺的部分在第十节明确标注为边界，而不是用通用印象补成结论。

先给一张全局表：

| 概念 | 一句话定位 | 关键约束 |
|---|---|---|
| Topic | 消息的逻辑分类 | 一个 Topic 可分为多个 Partition |
| Partition | 物理分片，并行与有序的单位 | 分区内有序，分区之间不保证顺序 |
| Replica | 分区的副本 | 副本因子不超过 Broker 数 |
| Offset | 分区内的消费位置 | 不是全局消息 ID |
| Consumer Group | 一组共享 group.id 的消费者 | 一个分区组内只给一个消费者 |
| Broker | 存储与服务的节点 | 用 broker.id 唯一标识 |
| Controller | 管理元数据与副本状态 | KRaft 下由控制器节点承担 |

## 二、架构：谁在存，谁在管，谁在读

### 2.1 发布订阅模型

Kafka 基于发布订阅模式：生产者把消息写到 Topic，消费者订阅 Topic 读取消息，两边不直接建立调用关系。生产者不知道有多少消费者，消费者也不关心生产者是谁。这种解耦带来两个直接好处：新增下游不必改上游；上游短时洪峰可以由 Kafka 先接住，下游按自己的能力消费。

但「发布订阅」不等于「广播给所有人」。广播语义只在消费者组之间成立：不同组各自维护自己的 offset，都能读到全量消息；同一组内则是分工，一条消息只交给组内一个消费者。把这两层混在一起，就会误以为「多加消费者就能让每个消费者都收到同一条消息」。

### 2.2 核心组件

| 组件 | 职责 | 备注 |
|---|---|---|
| Producer | 决定消息写入哪个分区，批量发送 | 分区策略见第五节 |
| Consumer | 按 offset 拉取消息并提交位置 | 组内分工，组间独立 |
| Broker | 存储分区副本，处理读写请求 | 集群横向扩展的单位 |
| Topic | 逻辑分类 | 业务上按模块或事件类型划分 |
| Partition | Topic 的物理分片 | 并行读写与顺序保证的最小单位 |
| Replica | 分区的副本 | 分为 Leader 与 Follower |
| Controller | 维护元数据、监听 Broker、触发选主 | 旧架构依赖 ZooKeeper，新架构用 KRaft |
| Consumer Group | 消费者集合 | 共享 group.id，组内负载均衡 |

`broker.id` 是 Broker 在集群中的唯一标识，不能重复。它决定元数据里如何指认节点，也影响副本分布与运维定位。KRaft 模式下，Kafka 服务器可以配置为 Controller、Broker，或者同时具备两种角色；小集群用合并角色省节点，大集群通常分离，避免元数据工作与数据读写互相争抢资源。

### 2.3 一条消息的路径

```
Producer
   │  按 key 或轮询选分区
   ▼
Broker A: Partition 0 (Leader)  ──同步──>  Broker B: Partition 0 (Follower)
   │
   ▼
Consumer Group A: C1 读 P0，C2 读 P1、P2
Consumer Group B: C3 读 P0、P1、P2
```

生产者只与分区的 Leader 交互；Follower 不对外提供读写，只从 Leader 拉取日志保持同步。消费者只读 Leader（副本机制正常时），读到什么位置由自己维护的 offset 决定。Controller 站在更高一层，负责感知 Broker 上下线、维护 ISR、在 Leader 失效时挑选新 Leader。

这张图里有三个「单点」需要区分：Leader 是分区级的单点，某个 Leader 失效只影响该分区，其他分区照常；Controller 是集群管理级的单点，KRaft 用控制器选举与元数据副本消除它；Broker 是存储级的节点，单台宕机由副本接管。排障时先确认是哪一层出了问题，才不会把「某个分区不可用」误判成「整个集群挂了」。

## 三、分区与日志：顺序从哪里来

### 3.1 分区是并行与有序的最小单位

Topic 只是逻辑名字，真正落盘的是分区。每个分区是一条有序、不可变的消息序列，以日志文件形式追加写入。新消息只会加到末尾，已有位置的内容不会被改写；消费者按 offset 从前向后读，也可以重置到更早的位置重读。

不可变带来两个性质。第一，顺序是天然的：同一分区内，offset 小的消息先写入，读的时候也先读到。第二，回溯是廉价的：历史消息还在文件里，换个 offset 就能重读，不需要生产者重发。消息最终会被保留策略清理，但清理按时间或大小成段进行，不是「读一条删一条」。

### 3.2 offset 不是消息 ID

offset 是消息在分区内的位置编号，单调递增。它只在分区内有意义：Partition 0 的 offset 5 与 Partition 1 的 offset 5 是两条完全不同的消息。把 offset 当成全局唯一 ID，会在跨分区去重、跨分区查询时出错。

| 概念 | 作用范围 | 是否唯一 |
|---|---|---|
| offset | 单个分区 | 分区内唯一，跨分区会重复 |
| key | 由生产者给定 | 不要求唯一 |
| timestamp | 消息字段 | 不唯一，可能相同 |

示例：某 Topic 有两个分区，消息按 key 落入不同分区，offset 各自从自己的起点递增。

| 分区 | key | offset | 说明 |
|---|---|---|---|
| P0 | order-A | n | P0 的第一条 |
| P0 | order-C | n+1 | 同分区，排在 A 之后 |
| P1 | order-B | m | P1 自己的起点，与 P0 无关 |
| P1 | order-A | m+1 | 同 key 再次出现，仍落 P1 |

同一个 key 的消息会落到同一分区，因此 order-A 的两条消息在 P1 内保持先后；order-B 与它们不在同一分区，跨分区的先后无法由 offset 比较。这就是「分区内有序、分区之间无序」的具体含义。

### 3.3 分区数决定并行上限

消费者组内，一个分区只能分配给一个消费者。于是组内真正干活的消费者数不会超过分区数：

$$
\text{并行度} \le \min(\text{消费者数},\ \text{分区数}).
$$

多出来的消费者处于闲置状态，不报错，也不提升吞吐。反过来，消费者少于分区时，一个消费者会分到多个分区，按顺序处理它们。设计时要先估算目标并行度，再定分区数；分区数定得太小，后来加消费者也扩不上去；定得太大，元数据、文件句柄、选主与重平衡的负担都会增加，具体上限取决于集群规模与运维能力，材料没有给出数字，本文也不编一个。

分区数还会影响 key 的映射。Kafka 对 key 做哈希后对分区数取模：

$$
p = \operatorname{hash}(key) \bmod n.
$$

分区数 \(n\) 一变，同一个 key 算出的分区可能变化。变化期间，同一 key 的新旧消息可能落在不同分区，依赖「同 key 同分区」的顺序保证会被打破。需要严格顺序的业务，扩分区要选在低峰并接受一段过渡，或者用其他方式保证消费侧的顺序。

### 3.4 热点分区

按 key 哈希的均匀性取决于 key 的分布。如果大量消息用同一个 key，或者 key 的哈希值集中在少数分区，就会出现热点：少数分区写满，其他分区空闲。增加分区数不一定能解决，因为热点来自 key 本身，重新哈希也可能仍落在同一批分区。

处理热点有几种思路：给 key 加随机后缀打散，代价是同一业务键不再保证顺序；把热点 key 拆成多个逻辑子键，消费侧再做合并；或者单独为热点业务建 Topic，避免影响其他业务。选择哪种，取决于「顺序」与「均匀」哪个更重要。

## 四、副本、ISR 与故障转移

### 4.1 AR 与 ISR

分区的所有副本统称为 AR（Assigned Replicas，分配副本），其中与 Leader 保持同步的副本集合称为 ISR（In-Sync Replicas，同步副本集）。ISR 是 AR 的子集：所有副本都被分配了，但不是每个副本都跟得上。

| 集合 | 含义 | 用途 |
|---|---|---|
| AR | 分区分配到的全部副本 | 描述副本布局 |
| ISR | 与 Leader 保持同步的副本 | 选主范围、acks=all 的确认范围 |
| 非 ISR 副本 | 落后太多的副本 | 不参与选主，恢复后追赶 |

Leader 对外提供读写，Follower 只同步数据。Follower 持续向 Leader 拉取新日志，落后超过一定限度就会被移出 ISR；追上之后重新加入。这个「一定限度」由服务端配置决定，材料没有给出具体值，本文不写。

### 4.2 故障转移的四步

材料给出的流程可以拆成四步：

1. Controller 监听 Broker 存活状态，发现某个 Leader 所在 Broker 下线。
2. Controller 从该分区的 ISR 中挑选一个同步完成的 Follower，提升为新 Leader。
3. 更新集群元数据，把新 Leader 的地址通知生产者和消费者。
4. 下线的 Broker 恢复后作为 Follower，从新 Leader 同步缺失数据，重新加入 ISR。

这四步里有三个细节值得注意。选主范围限定在 ISR，意味着落后太多的副本没有资格，避免把旧数据当成新数据；选主由 Controller 发起，客户端不参与投票，客户端只负责在收到元数据更新后改连新 Leader；恢复的旧 Leader 不再特殊，它按 Follower 的规则追赶，追上后才能回到 ISR。

如果 ISR 只剩 Leader 自己，选主就无从谈起。此时若允许非 ISR 副本当选，可用性恢复了，但可能丢数据；若不允许，分区要等原 Leader 恢复或等待管理员处理。材料只描述了「从 ISR 中选」的干净路径，没有展开非 ISR 选举的取舍，本文把它标为边界，不当作默认行为。

### 4.3 副本因子与 Broker 数

创建 Topic 时，副本因子应小于等于可用的 Broker 数量。副本要分散到不同 Broker 才有意义；副本因子大于 Broker 数，必然有 Broker 承载多个副本，单台宕机可能同时带走 Leader 和它的多个候选，容错效果大打折扣。单 Broker 集群只能把副本因子设为 1，此时没有故障转移能力，只能算单机持久化。

副本因子不是越大越好。每个副本都要占磁盘、网络与同步开销，写入还要等 ISR 确认；副本因子提高，可靠性与成本一起上升。材料没有给出「应该设几」的结论，本文也不替读者拍一个数字，只给判断依据：能容忍几台 Broker 同时故障，就至少要有相应数量的副本分散在不同节点。

### 4.4 acks=all 到底保证了什么

材料只出现了 `acks=all` 这一种生产者确认配置。它的语义是：Leader 写入后，还要等 ISR 中的副本都确认收到，生产者才认为这条消息发送成功。配合「只有 ISR 能当选 Leader」，它把「已确认」与「至少留在一批同步副本上」联系起来。

但 `acks=all` 不是「绝对不丢」的同义词。若 ISR 因为副本落后而收缩到只剩 Leader，确认范围也随之缩小，此时 Leader 一旦损坏，消息仍可能丢失。要让「all」真正有意义，服务端还要对最小同步副本数做约束：ISR 小于该阈值时拒绝写入，用可用性换一致性。这个阈值是独立的服务端配置，材料没有给出名称与取值，本文只讲机制，不写具体参数。

与之对照，还存在更弱的确认级别：不等待任何确认就认为成功，或者只等 Leader 本地写入就认为成功。前者在 Broker 故障时直接丢，后者在 Leader 故障且消息尚未复制时丢。材料没有给出这些级别的配置取值，本文只用它们说明「all 的代价与收益」：确认范围越大，延迟越高，丢失窗口越小。

## 五、生产者：分区策略与重复

### 5.1 三种分区策略

材料列出三种：顺序轮询、随机轮询、key 哈希。

| 策略 | 怎么选分区 | 优点 | 代价 |
|---|---|---|---|
| 顺序轮询 | 按顺序依次分配 | 分布均匀，实现简单 | 不保证同 key 同分区 |
| 随机轮询 | 随机挑一个分区 | 写入分散 | 分布有随机波动，顺序无保证 |
| key 哈希 | 对 key 取模 | 同 key 同分区，保顺序 | key 分布不均会热点 |

没有 key 时，生产者在轮询与随机之间选择，具体取决于客户端实现与版本；有 key 时，按哈希取模，同一 key 稳定落到同一分区。所谓「顺序轮询」也不是严格的一条一条轮转，批量发送会把一批消息按分区聚合，实际的分配粒度是批次，而不是单条消息。这一点在观察分区流量时容易误判。

### 5.2 顺序保证的边界

Kafka 只保证分区内有序。想要「同一业务实体的消息按发生顺序处理」，就把该实体的 ID 作为 key，让它稳定落入同一分区；想要「全局有序」，只能把 Topic 设成单分区，代价是失去并行度。两者不可兼得，这是分区模型的硬约束，不是配置能绕过的。

生产者重试也会影响顺序。若开启了重试，而前一批消息失败、后一批成功，重发的前一批可能落到后面，造成乱序。要严格顺序，通常要限制未确认请求的数量，让失败时整批重发；这会牺牲吞吐。材料没有展开这一层，本文只指出「重试与顺序存在取舍」，不给出具体参数。

### 5.3 重复从哪里来

生产者发送成功但没收到确认，于是重试，Broker 可能已经写入第一次，于是产生重复。这是「至少一次」的典型来源。若生产者不重试，可能丢消息，变成「至多一次」。要逼近「精确一次」，需要幂等生产者与事务机制，让 Broker 能识别重复写入并把一批写入作为一个原子单元提交。

材料没有展开幂等与事务的实现细节，本文不编造其配置与适用范围。只强调一条边界：即使 Kafka 内部做到了精确一次，消费者把结果写到外部数据库、调用外部接口时，仍可能重复；外部副作用需要幂等键或去重表来兜底。把「Kafka 精确一次」当成「端到端绝不重复」，是常见的过度承诺。

### 5.4 批量与吞吐

生产者不是来一条发一条，而是按分区攒批再发。批量越大，网络往返与磁盘写入的次数越少，吞吐越高；但消息在客户端等待凑批，端到端延迟上升。这是吞吐与延迟的经典取舍，具体批量上限与等待时间由客户端配置决定，材料没有给值。

批量还影响顺序与重复的判断：一批消息在同一分区内按顺序写入，批与批之间才需要比较先后；重试的单位是批，重复也以批为粒度出现。理解这一点，调试「为什么消费者看到重复」时就会先看生产端重试，而不是只怀疑消费端提交。

## 六、消费者组：分工、offset 与重平衡

### 6.1 组内分工，组间独立

消费者组是一组共享同一个 `group.id` 的消费者。组内，一个分区只能分配给一个消费者；组间，各自维护 offset，互不影响。于是同一 Topic 可以被多个业务组同时消费：风控组读全量做实时规则，数仓组读全量做入库，两边进度不同，互不阻塞。

消费者数量与分区数的关系在 3.3 节已经给出：并行度取两者较小值。多出来的消费者闲置，不会自动「分担」已有消费者的工作。要让新消费者真正参与，只能增加分区，或者等现有消费者退出触发重平衡。

### 6.2 offset 提交决定语义

消费者唯一需要维护的元数据是 offset，用于标识消费位置。它定期提交到 Kafka 侧保存，重启后从上次提交的位置继续。提交时机与业务处理的先后，决定了消息语义：

| 处理与提交的顺序 | 中途崩溃的后果 | 语义 |
|---|---|---|
| 先提交 offset，再处理消息 | 消息未处理但位置已前进，重启后跳过 | 至多一次 |
| 先处理消息，再提交 offset | 处理可能完成但位置未前进，重启后重复 | 至少一次 |
| 处理与提交在同一事务边界内 | 边界内不重不漏 | 精确一次，材料未展开 |

自动提交属于「先提交后处理」的风险模式：提交周期到了就前进，不管业务是否处理完。对可靠性要求高的场景，应在处理完成后手动提交，并让处理逻辑幂等，接受「至少一次」带来的重复。对可以容忍丢失的监控指标，至多一次反而更简单。

### 6.3 重平衡的触发与代价

材料给出三类触发场景：消费者上下线、Topic 新增分区、消费者组订阅的 Topic 变更。重平衡的过程是暂停所有消费者读取，重新计算分区与消费者的映射，再恢复消费。

| 阶段 | 发生什么 | 业务感受 |
|---|---|---|
| 触发 | 成员变化或分区变化 | 尚未中断 |
| 暂停 | 所有消费者停止拉取 | 消费停顿 |
| 重新分配 | 按策略把分区分给成员 | 映射变化 |
| 恢复 | 消费者从各自提交的 offset 继续 | 可能重复或延迟 |

负面影响有三条：重平衡期间不能消费，造成业务中断；分区换手后，未提交的进度会重放，造成重复；频繁重平衡让消费始终停在「暂停与恢复」之间，表现为延迟上升。生产环境要尽量避免频繁重平衡：滚动重启要一批一批来，消费者不要因为单条消息处理过久而脱离组，订阅关系不要频繁改动。

这里有一条常被忽略的因果：消费者处理一条消息太久，心跳跟不上，会被组判定为失效并踢出，触发重平衡；重平衡又把分区转给别人，别人从头重放，延迟进一步上升。表现是「越忙越乱」，根因却在处理逻辑的耗时，而不在 Kafka 本身。

### 6.4 消费积压

积压是「最新消息的 offset」与「消费者已提交 offset」之间的差距。它不一定是故障：上游洪峰、下游变慢、消费者重启都会造成积压。判断要看趋势：积压持续扩大，说明消费能力不足；积压突然跳变，可能是重平衡或消费者掉线；积压缓慢下降，说明只是暂时落后。

处理积压的手段有增加消费者（受分区数限制）、提高单条处理效率、把耗时操作异步化、增加分区。前两个不改变分区布局，后两个会触发重平衡或改变 key 映射，要安排窗口。

## 七、零拷贝与吞吐的来源

材料把零拷贝列为 Kafka 高吞吐的原因之一，并说它避免内核切换。准确地说，零拷贝减少的是数据在用户态与内核态之间的复制次数，以及由此带来的上下文切换。

传统读取并发送的路径是：磁盘数据进入内核页缓存，复制到用户缓冲区，再从用户缓冲区复制到套接字缓冲区，最后交给网卡。数据在用户态走了一趟，CPU 参与了两次复制。零拷贝的做法是让内核直接把页缓存中的数据送到网卡，应用只下命令，不搬运数据。

| 路径 | 数据是否经过用户态 | CPU 复制次数 | 上下文切换 |
|---|---|---|---|
| 传统读写 | 是 | 多 | 多 |
| 零拷贝 | 否 | 少 | 少 |

Kafka 的消费读取适合这条路：消息已经在页缓存里，消费者要的是原样字节，不需要在应用层加工。生产写入则不同，消息要追加到日志、可能要校验，仍要经过内核与磁盘，零拷贝主要优化的是读路径。

吞吐还来自另外两件事：顺序写与批量。顺序追加避免了随机寻道，批量发送减少了每次请求的固定开销。零拷贝、顺序写、批量三者叠加，才是材料所说「高吞吐」的来源；单独把零拷贝说成万能原因，会忽略磁盘与网络的实际瓶颈。

## 八、KRaft：把元数据也做成日志

旧架构里，Kafka 依赖 ZooKeeper 保存元数据、做 Controller 选举。KRaft 模式把这部分收回到 Kafka 自身：控制器节点组成一个元数据仲裁组，用一条元数据日志复制状态，选出活跃 Controller；Broker 向 Controller 注册，Controller 负责分区 Leader 的选举与变更通知。

| 维度 | 旧架构 | KRaft |
|---|---|---|
| 元数据存储 | 外部 ZooKeeper | Kafka 内部的元数据日志 |
| Controller 选举 | 依赖 ZooKeeper | 控制器仲裁组选举 |
| 部署组件 | Kafka 加 ZooKeeper | 只需 Kafka |
| 角色 | Broker 与 Controller 分离 | Controller、Broker 或两者合一 |
| 运维 | 两套系统分别维护 | 一套系统统一管理 |

KRaft 的收益主要是运维简化与元数据路径缩短：不必再维护 ZooKeeper 集群，Controller 失效后的切换不必跨系统协调。材料只给出角色配置这一层，没有展开仲裁组规模、迁移步骤与兼容性限制；这些属于部署细节，本文不编。

需要区分「Controller 角色」与「Broker 角色」：前者管元数据与选主，后者存数据、服务读写。合并角色适合小集群，分离角色适合大规模部署，选择依据是元数据负载与故障域的隔离需求，而不是一个固定节点数。

## 九、典型场景与可靠性设计

材料列出五类场景：流量削峰、系统解耦、实时日志收集、实时数据同步、异步通知与事件溯源。把它们与 Kafka 的机制对应起来，才知道为什么是 Kafka 而不是别的队列：

| 场景 | 用到的机制 | 设计要点 |
|---|---|---|
| 流量削峰 | 持久化缓冲、按能力消费 | 估算峰值与消费速率，留出积压空间 |
| 系统解耦 | 发布订阅、多消费者组 | 事件格式要稳定，避免上游字段随意变更 |
| 日志收集 | 高吞吐、顺序写、批量 | 下游按至少一次处理，重复要可去重 |
| 数据同步 | 分区顺序、offset 回溯 | 按主键做 key，保证同一行有序 |
| 事件溯源 | 不可变日志、历史重放 | 保留策略要覆盖回溯窗口 |

可靠性不是单一开关，而是一组选择：

- 副本因子大于 1，且小于等于 Broker 数，副本分散在不同节点。
- 生产者用 `acks=all`，并配合服务端的最小同步副本约束，避免 ISR 收缩后确认失去意义。
- 消费者在处理完成后提交 offset，处理逻辑幂等，接受至少一次。
- 监控 ISR 收缩、离线分区、未充分复制分区与消费积压，而不是只看 Broker 是否存活。
- 重平衡要少发生：滚动重启分批、处理逻辑不长时间阻塞心跳、订阅关系稳定。

这套组合的目标是「可接受的重复 + 不丢已确认数据」，而不是追求一个不存在的绝对保证。材料里的场景描述偏向能力列举，没有给出容量规划与压测方法；实际部署要按消息大小、保留时长、副本数、网络与磁盘做测算，这些数字必须来自自己的环境，不能从文章里抄。

## 十一、常见误记与原料勘误

| 原料或常见表述 | 问题 | 本文口径 |
|---|---|---|
| Kafka 支撑百万级消息每秒 | 缺少消息大小、副本数、硬件与批量条件，不能当设计指标 | 吞吐由顺序写、批量、零拷贝与硬件共同决定，不给统一数字 |
| 分区内有序，所以 Topic 全局有序 | 分区之间不保证顺序 | 只有分区内有序，全局有序需单分区 |
| 消费者越多，消费越快 | 组内并行度受分区数限制 | 超出分区数的消费者闲置 |
| 重平衡期间仍可继续消费 | 重平衡会暂停所有消费者 | 暂停、重分配、再恢复 |
| offset 是消息的唯一 ID | offset 只在分区内唯一 | 跨分区会重复，不能当全局 ID |
| `acks=all` 等于绝对不丢 | ISR 收缩时确认范围也缩小 | 还需最小同步副本约束 |
| 副本因子可以大于 Broker 数 | 会造成副本堆叠，失去故障分散 | 副本因子小于等于 Broker 数 |
| Kafka 只能做日志收集 | 材料列出削峰、解耦、同步、事件溯源等 | 日志只是场景之一 |
| 同一 Topic 的消费者都能收到同一条消息 | 同组是分工，不同组才是各自全量 | 广播只在组间成立 |

## 十二、总结

| 知识块 | 必记结论 |
|---|---|
| 模型 | 发布订阅；消息是分区日志中的不可变记录，读取不删除 |
| Topic 与 Partition | Topic 逻辑分类，Partition 物理分片；分区内有序，分区间无序 |
| offset | 分区内位置，不是全局 ID；消费者靠它续读与回溯 |
| 并行度 | 组内并行度不超过分区数；多出的消费者闲置 |
| 副本 | AR 是全部副本，ISR 是同步子集；只有 ISR 能当选 Leader |
| 故障转移 | Controller 检测下线，从 ISR 选新 Leader，更新元数据，旧 Leader 追赶 |
| 生产者 | 轮询、随机、key 哈希；同 key 同分区；重试会带来重复 |
| acks | `acks=all` 等 ISR 确认；ISR 收缩会削弱保证，需最小同步副本约束 |
| 消费者组 | 组内一分区一消费者，组间独立；offset 提交顺序决定至少一次或至多一次 |
| 重平衡 | 成员或分区变化触发；期间暂停消费，带来重复与延迟 |
| 零拷贝 | 减少用户态复制与上下文切换，主要优化读路径 |
| KRaft | 元数据用内部日志与控制器仲裁，去掉 ZooKeeper 依赖 |

Kafka 的概念很多，但主线只有一条：分区决定并行与顺序，副本决定可用与持久，offset 决定消费进度，消费者组决定分工。把这条主线记住，再去看 acks、ISR、重平衡，它们都能落到「在哪个环节、用什么代价、换什么保证」上；遇到材料没写的参数与数字，也知道该去查官方文档或做压测，而不是凭印象补一个。
