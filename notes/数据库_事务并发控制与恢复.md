# 数据库 · 事务、并发控制与恢复

## 一、概述：事务为什么是恢复与并发的共同单位

事务（transaction）是用户定义的一个数据库操作序列，这些操作**要么全做，要么全不做**，是一个不可分割的工作单位。这个定义是全部讨论的起点：正因为「不可分割」，才需要日志在崩溃后把做了一半的动作补完或撤掉；也正因为多个事务可以交错执行，才需要封锁与多版本机制把交错约束成等价于串行的效果。

DBMS 的数据控制功能包含安全性、完整性、**并发控制**与**数据库恢复**四项。事务正好横跨后两项：并发控制管「同时跑不乱」，恢复管「崩了能回来」，两者共用同一套日志与事务标识。理解这一点，比背下四条英文缩写更有用。

**素材边界需要先交代。** 原始对话能直接支撑的内容有四块：事务定义与 ACID 四条性质；数据一致性的三层含义（含「并发执行效果等价于串行执行」）；冲突操作与冲突可串行化的推理；故障分类中「介质故障才会直接损坏数据库文件」的判断，以及完整性检查可放在语句执行后或事务提交时的结论。至于隔离级别的完整矩阵、封锁协议、MVCC 的版本链与 ReadView、redo/undo 与 WAL 的具体流程，对话里没有展开，本文按数据库教材与 InnoDB 实现的通用口径补齐，并在涉及原料判断的地方逐条标明。凡属补齐的部分只陈述可验证的机制，不编造数字与实验结论。

## 二、事务的边界与状态迁移

### 2.1 三条显式语句

原料在项目实践里给出的写法是最小的一组事务控制语句：

```sql
BEGIN;                 -- 或 START TRANSACTION
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;                -- 两条更新一起生效
```

把 `COMMIT` 换成 `ROLLBACK`，两条更新一起作废。原料举的场景是下单时「库存扣减」与「订单插入」必须同时成功，这正是事务要解决的典型问题：**跨语句、跨表的原子性无法由单条 SQL 自己保证**。

### 2.2 五个状态

事务从开始到结束经过五个状态，状态名比定义更重要，因为恢复流程正是按状态决定「重做还是回滚」。

| 状态 | 含义 | 此时数据是否已落盘 | 崩溃后的处置 |
|---|---|---|---|
| 活动（active） | 正在执行，尚未结束 | 修改在缓冲区，日志可能已写出 | 回滚 |
| 部分提交（partially committed） | 最后一条语句已执行，尚未提交 | 修改可能仍在内存 | 回滚 |
| 提交（committed） | 提交记录已写入日志 | 日志已持久，数据页可稍后刷 | 重做 |
| 失败（failed） | 正常执行无法继续 | 不确定 | 回滚 |
| 中止（aborted） | 已回滚，数据库回到事务开始前 | 旧值已恢复 | 结束 |

两个容易忽略的点。第一，**「最后一条语句执行完」不等于「已提交」**，部分提交状态正是崩溃恢复要特别处理的位置：日志里若有提交记录就必须重做，没有就必须回滚，二者只能居其一。第二，**提交的判据是日志落盘，而不是数据页落盘**，这条把持久性从「数据文件」转移到了「日志文件」，是 WAL 的全部要点所在。

### 2.3 自动提交与隐式边界

多数数据库默认开启自动提交，一条语句自成一个事务。批量导入或跨语句业务必须显式开事务，否则中途失败会留下半截数据。反过来，长事务会长期持有旧版本与锁，拖慢清理并放大回滚代价，这是把事务写得越短越好的实际理由。

## 三、ACID：四条性质各自靠什么实现

### 3.1 原料的四条定义

原料给出的表述可直接用于答题：原子性指事务是原子的、不可分割；一致性指事务执行前后数据库状态保持一致；隔离性指多个事务并发执行时互不干扰；持久性指事务提交后修改永久有效、不受故障影响。

这四条不是并列的口号，而是**一条目标加三种手段**：

| 性质 | 保证的是什么 | 主要实现手段 | 失效时的表现 |
|---|---|---|---|
| 原子性 A | 要么全做要么全不做 | undo 日志回滚 | 转账只扣不加 |
| 一致性 C | 约束与业务规则始终成立 | 完整性约束 + 应用逻辑 + 其他三条共同兜底 | 余额为负、外码悬空 |
| 隔离性 I | 并发事务互不干扰 | 锁、MVCC、隔离级别 | 读到未提交值、统计前后不一致 |
| 持久性 D | 提交即永久 | redo 日志 + WAL + 刷盘策略 | 宕机后已提交数据丢失 |

一句话概括：**A 靠 undo，D 靠 redo，I 靠锁与多版本，C 是前三者加上约束体系共同维持的结果**。把一致性也当成「某种日志实现的」是常见误解——一致性没有独立的机制，它是被约束检查和应用语义守住的。

### 3.2 「一致性」的三层含义

原料把数据一致性拆成三层，这个拆法比单句定义好用：

1. **同一数据的一致性**：同一数据在库中多处出现时取值完全相同，不出现前后矛盾。典型反例是同一学生的姓名在两张表里写法不同。
2. **关联数据的逻辑一致性**：表与表、记录与记录之间符合语义规则，满足实体完整性、参照完整性与用户定义完整性。典型反例是选课表里出现学生表中不存在的学号。
3. **事务并发一致性**：多个事务并发访问时，执行效果等价于串行执行，不出现脏读、不可重复读、幻读。

第三层需要一句限定（见 §十一）：**「等价于串行执行」是最高隔离级别的性质，不是任何并发执行的普遍保证**。数据库允许在该性质与吞吐之间做取舍，取舍的刻度就是隔离级别。

### 3.3 ACID 之间的冲突

四条性质并非总能同时最大化。持久性要求每次提交都刷日志，隔离性要求加锁或多留版本，二者都在换取吞吐。真正不能放弃的是原子性与一致性：前者是「不许留半截」，后者是「不许留错数据」；隔离性与持久性则是可以用配置调节强度的。

## 四、并发异常：四张时间轴

四个异常都能用两条事务的交错时间轴说清。设账户余额初值 $A=100$。

### 4.1 丢失更新（lost update）

| 时刻 | $T_1$ | $T_2$ |
|---|---|---|
| $t_1$ | 读 $A=100$ | |
| $t_2$ | | 读 $A=100$ |
| $t_3$ | 写 $A=100+10=110$ | |
| $t_4$ | | 写 $A=100+20=120$ |

两次「读—改—写」都基于旧值 100，$T_1$ 的结果被 $T_2$ 覆盖，等于 $T_1$ 的更新从未发生。注意这不是读到脏数据，而是**写覆盖**：两个事务都合法提交，结果却少了一次修改。丢失更新是唯一一个「两个事务都没读错、却仍然出错」的异常，因此最容易被忽视。

### 4.2 脏读（dirty read）

| 时刻 | $T_1$ | $T_2$ |
|---|---|---|
| $t_1$ | 写 $A=110$（未提交） | |
| $t_2$ | | 读 $A=110$ |
| $t_3$ | 回滚，$A$ 恢复 100 | |

$T_2$ 读到了一个**从未存在过**的值。更麻烦的是 $T_2$ 可能据此做了后续写入，回滚链条会向外扩散，这就是「级联回滚」问题。

### 4.3 不可重复读（non-repeatable read）

| 时刻 | $T_1$ | $T_2$ |
|---|---|---|
| $t_1$ | 读 $A=100$ | |
| $t_2$ | | 改 $A=110$ 并提交 |
| $t_3$ | 再读 $A=110$ | |

同一事务内两次读同一行得到不同值。它违反的是「事务内视角稳定」，而不是「读到了假数据」——两次读到的都是真值，只是中间被别人改了。

### 4.4 幻读（phantom read）

| 时刻 | $T_1$ | $T_2$ |
|---|---|---|
| $t_1$ | 查「计算机系人数」得 10 | |
| $t_2$ | | 插入一名计算机系学生并提交 |
| $t_3$ | 再查得 11 | |

幻读与不可重复读的差别在**作用对象**：不可重复读针对**已存在的某一行**被改，幻读针对**结果集的行数**变了——原来没有的行「幻影般」出现。这个差别直接决定锁的形态：改一行只需锁住那一行，防幻读却要锁住「尚不存在的行」可能落入的区间，于是有了间隙锁。

### 4.5 四类异常对照

| 异常 | 读到了什么 | 责任操作 | 靠什么消除 |
|---|---|---|---|
| 丢失更新 | 无异常读取，但写被覆盖 | 两次读—改—写交错 | 一级封锁协议、行锁、乐观锁版本号 |
| 脏读 | 未提交且可能回滚的值 | 读未提交写 | 二级封锁协议、RC 及以上 |
| 不可重复读 | 同一行前后不同的真值 | 期间有提交的更新 | 三级封锁协议、RR 及以上 |
| 幻读 | 结果集行数变化 | 期间有提交的插入或删除 | 范围锁、间隙锁、Serializable |

## 五、可串行化：判断并发调度是否安全

### 5.1 冲突操作

原料的定义很清楚：**不同事务对同一数据的操作，只要其中一个是写操作，就会产生冲突**。据此，$r_1(A)$ 与 $w_2(A)$ 冲突，$w_1(B)$ 与 $r_2(B)$ 冲突；而不同事务对不同数据的操作、以及两个纯读操作，都不冲突。

冲突之所以重要，是因为**非冲突操作的相对顺序不影响结果，因而可以交换**。原料用一个调度反复交换非冲突操作，把交错的 $Sc_1$ 整理成「$T_1$ 全部在前、$T_2$ 全部在后」的串行调度 $Sc_2$，并据此判定 $Sc_1$ 可串行化。这个推理链是对的：交换只发生在非冲突对上，所以每一步都保持结果不变；整理成串行后自然与某个串行执行等价。

原料在这里有一处**结论错误**需要指出：它把「同一事务内的操作」也列为可交换的非冲突操作。同一事务内的两条操作恰恰不能随意交换，$w_1(A)$ 与 $r_1(A)$ 换个次序，事务读到的就是自己写之前的值。正确的非冲突判定只有两条：**属于不同事务且操作不同数据**，或**属于不同事务且双方都是读**。

### 5.2 冲突等价与优先图

两个调度冲突等价，指可以通过若干次非冲突相邻操作的交换互相转换。判定可串行化的标准工具是**优先图**（precedence graph）：每个事务一个结点，若 $T_i$ 的某操作与 $T_j$ 的某操作冲突且 $T_i$ 在前，则连边 $T_i \to T_j$。**优先图无环当且仅当该调度冲突可串行化**，拓扑序即等价的串行顺序。

优先图把「能不能排成串行」变成了「图里有没有环」，这比手工交换可靠得多。它也是死锁检测所用等待图的近亲：等待图有环是死锁，优先图有环是不可串行化，两者都是「环」但含义不同，不能混用。

### 5.3 可串行化不等于没有异常

一个调度可以冲突可串行化，却在执行过程中让某个事务读到中间状态。原因是可串行化只约束**最终效果**等价于某个串行顺序，不约束中间可见性。因此「可串行化」是正确性标准，「不出现脏读」是更强的可见性要求，二者不能互相替代。这也解释了为什么隔离级别要单独列一张表，而不是只说「可串行化就好」。

## 六、四级隔离级别

### 6.1 标准矩阵

SQL 标准按「允许哪些异常」划分四级隔离，级别越高、并发度越低：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 典型实现强度 |
|---|---|---|---|---|
| 读未提交 READ UNCOMMITTED | 允许 | 允许 | 允许 | 几乎不加读锁 |
| 读已提交 READ COMMITTED | 禁止 | 允许 | 允许 | 读时短锁或语句级快照 |
| 可重复读 REPEATABLE READ | 禁止 | 禁止 | 标准允许 | 事务级快照、范围锁 |
| 可串行化 SERIALIZABLE | 禁止 | 禁止 | 禁止 | 读写均加范围锁或串行化验证 |

记忆的锚点是「每升一级多禁一种异常」，顺序固定为脏读、不可重复读、幻读。**没有「禁止丢失更新」这一列**，因为标准假定写操作必须持排他锁，丢失更新在任何级别都不该发生；现实中它仍会出现，原因是应用层先读后写、锁没有覆盖整个读—改—写区间。

### 6.2 MySQL 的实际行为

InnoDB 的默认级别是 REPEATABLE READ（可重复读），比标准要求更严：它用**快照读**为整个事务固定一个 ReadView，使同一事务内的普通 `SELECT` 反复看到同一版本；又用**间隙锁**与 next-key 锁封锁索引区间，使当前读也难以插入新行。因此在 InnoDB 上，RR 常常表现出「幻读也不出现」的效果。

这个「常常」有两处例外，必须记住：

- **快照读与当前读混用**。事务先做普通查询（快照），再用 `SELECT ... FOR UPDATE` 或 `UPDATE`（当前读），后者看到的是最新已提交数据，两者的结果可能不一致，表现为「查不到却改得动」。
- **不同索引路径的加锁范围不同**。范围锁只锁走到的索引区间，若查询未命中索引而全表扫描，锁的范围会退化为扫描过的全部记录，既可能锁得过多，也可能因执行计划变化而出现间隙。

### 6.3 级别选择的实际考虑

读已提交的并发度明显高于可重复读，许多互联网系统把它作为默认：每次查询拿新快照，长事务不会长期占用旧版本，清理压力小。代价是同一事务内的两次统计可能不一致，需要应用层接受或用一次性快照查询规避。可串行化只在强一致账务、库存扣减等场景使用，且通常配合重试机制，因为它更容易因冲突而失败。

## 七、封锁：从 S/X 到两段锁

### 7.1 两种基本锁与相容矩阵

| 请求方 \ 持有方 | 共享锁 S | 排他锁 X |
|---|---|---|
| 共享锁 S | 相容 | 冲突 |
| 排他锁 X | 冲突 | 冲突 |

读加 S 锁，写加 X 锁；S 与 S 可并存，其余组合互斥。矩阵只有四个格子，但所有封锁协议都由它推出。

### 7.2 三级封锁协议

| 协议 | 加锁规则 | 解锁规则 | 能防住 |
|---|---|---|---|
| 一级 | 修改前必须加 X 锁 | 事务结束才释放 | 丢失更新 |
| 二级 | 一级 + 读前加 S 锁 | 读完即可释放 S 锁 | 丢失更新、脏读 |
| 三级 | 一级 + 读前加 S 锁 | 事务结束才释放 S 锁 | 丢失更新、脏读、不可重复读 |

三者的差别只在**读锁持有多久**：一级不管读，所以读到的可能是别人未提交的值；二级读完就放，所以两次读之间别人可以改；三级持有到事务结束，读的稳定性才成立。三级协议仍防不住幻读，因为新插入的行不在已加的锁范围内。

### 7.3 两段锁协议

两段锁（2PL）把每个事务的锁操作分成两段：**增长期只加锁不解锁，收缩期只解锁不加锁**。定理是：**若所有事务都遵守 2PL，则任何并发调度都是冲突可串行化的**。

证明思路即优先图：设 $T_i$ 与 $T_j$ 冲突且 $T_i$ 先动，则 $T_i$ 必须在 $T_j$ 拿到冲突锁之前持有该锁，而 $T_i$ 解锁只能发生在自己的收缩期，晚于它取得全部锁；由此冲突边的方向与「拿到锁的先后」一致，若图中有环就会要求某个事务在自己解锁之后再加锁，与两段性矛盾。

2PL 的三条推论要分清：

- **2PL 保证可串行化，但不保证不出现死锁**。两段性只约束加锁与解锁的次序，不约束加锁的方向，交叉等待照样成环。
- **可串行化不要求 2PL**。存在不遵守两段性却仍冲突可串行化的调度，2PL 是充分条件而非必要条件。
- **严格 2PL** 要求所有锁持有到提交或回滚，避免「读未提交」与级联回滚，代价是并发度更低。多数数据库实现的是严格 2PL 的变体。

### 7.4 封锁粒度与意向锁

封锁对象可以是行、页、表。粒度越细并发越高，但锁的数量与检查开销越大。多粒度封锁的做法是**分层加锁**：对某行加锁前，先在该行所属的表上加一把「意向锁」，表示表内有行被锁。

| 意向锁 | 含义 | 与 S | 与 X | 与 IS | 与 IX |
|---|---|---|---|---|---|
| IS | 表内某些行将被加 S 锁 | 相容 | 冲突 | 相容 | 相容 |
| IX | 表内某些行将被加 X 锁 | 冲突 | 冲突 | 相容 | 相容 |
| SIX | 表级 S + 行级 X 意向 | 冲突 | 冲突 | 相容 | 冲突 |

意向锁的作用是让「表级请求」不必逐行检查：想给整表加 X 锁的事务只需看表上有没有 IS/IX，就能判断是否与行锁冲突。这是典型的「用少量粗粒度标记换取检查效率」的设计。

### 7.5 间隙锁与插入意向锁

幻读的根源是「尚不存在的行无法加行锁」。InnoDB 在可重复读下使用三种区间锁：

- **记录锁**：锁住索引中的一条记录。
- **间隙锁**：锁住两条记录之间的开区间，阻止其他事务在该间隙插入。
- **next-key 锁**：记录锁加其前面的间隙锁，锁住「左开右闭」的一段。

插入时则申请**插入意向锁**，它也是一种间隙锁，多个插入意向锁在同一间隙内互不冲突，只有当间隙已被 next-key 锁覆盖时才会等待。这解释了为什么两个事务同时向同一区间插入不同值通常不阻塞，而一个范围查询却能让插入排队。

间隙锁的代价是**锁范围随索引而变**：同样的 `WHERE` 条件，走唯一索引等值查询时只需记录锁，走普通索引或范围条件时就要锁一段间隙；若没有可用索引而全表扫描，则可能锁住大量间隙，显著降低并发。这是「索引设计影响并发」的直接证据。

### 7.6 死锁

死锁的四个必要条件（互斥、持有并等待、不可剥夺、循环等待）在数据库里全部可能满足。工程上的处置有三条路：

| 策略 | 做法 | 代价 |
|---|---|---|
| 预防 | 约定加锁顺序，按主键升序更新；缩短事务 | 需要改造业务代码 |
| 检测 | 维护等待图，发现环即回滚代价较小的事务 | 检测开销，牺牲一个事务 |
| 超时 | 等待超过阈值即放弃 | 阈值难定，可能误杀长事务 |

死锁不是 bug 而是并发系统的常态，应用必须能识别「死锁或锁等待超时」并重试整个事务，而不是重试最后一条语句——因为事务已被整体回滚。

## 八、MVCC：版本链与 ReadView

### 8.1 行上的三个隐藏字段

InnoDB 的聚簇索引记录带有隐藏列：`DB_TRX_ID` 记录最后修改该行的事务号，`DB_ROLL_PTR` 指向 undo 日志中该行的上一个版本，若无主键还有 `DB_ROW_ID`。三者合起来把「一行」变成「一条版本链」：

$$
\text{当前行} \xrightarrow{\text{roll\_ptr}} \text{旧版本}_1 \xrightarrow{\text{roll\_ptr}} \text{旧版本}_2 \to \cdots
$$

每个版本都带自己的 `DB_TRX_ID`。所谓「读旧版本」，就是沿着这条链往回走，直到找到一个「对当前事务可见」的版本。这就是 MVCC（多版本并发控制）的全部骨架：**写不覆盖旧值，而是把旧值挂到链上；读不等待写，而是按可见性规则挑一个版本**。

### 8.2 ReadView 的四个字段

快照的本质是一个 ReadView，包含四个量：

| 字段 | 含义 |
|---|---|
| `m_ids` | 生成快照时仍活跃（未提交）的事务号集合 |
| `min_trx_id` | `m_ids` 中的最小值 |
| `max_trx_id` | 生成快照时应分配给下一个事务的编号 |
| `creator_trx_id` | 创建该 ReadView 的事务自身编号 |

可见性判断按以下次序进行，任一步得出结论即停止：

1. 版本的事务号等于 `creator_trx_id`：**可见**（事务能看到自己的修改）。
2. 小于 `min_trx_id`：**可见**（快照之前已提交）。
3. 大于或等于 `max_trx_id`：**不可见**（快照之后才开始的事务）。
4. 落在 `m_ids` 中：**不可见**（生成快照时尚未提交）。
5. 其余：**可见**（在 `min_trx_id` 与 `max_trx_id` 之间且不在活跃集合中，说明快照前已提交）。

不可见时沿 `DB_ROLL_PTR` 取下一条版本，重复上述判断；链走到头仍不可见，说明该行对当前快照不存在。

### 8.3 RC 与 RR 的差别只在一处

两个隔离级别用的是同一个算法，差别是 **ReadView 的生成时机**：

- **读已提交（RC）**：每条 `SELECT` 都新建一个 ReadView。因此同一事务的两次查询之间若有别的事务提交，第二次就能看到新值——这正对应「不可重复读」。
- **可重复读（RR）**：只在事务内第一次快照读时建一个 ReadView，后续查询复用。因此整个事务看到的是同一时刻的数据库，重复读自然成立。

这个对比把「隔离级别」从一个抽象名词变成了一个具体动作：**建快照的频率**。理解了频率，就不必背「RR 防不可重复读」这句话。

### 8.4 快照读与当前读

| 读法 | 语句形态 | 读什么 | 加锁 |
|---|---|---|---|
| 快照读 | 普通 `SELECT` | ReadView 判定的可见版本 | 不加锁 |
| 当前读 | `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT` | 最新已提交版本 | 加 X 或 S 锁，RR 下含间隙锁 |

快照读让「读不阻塞写、写不阻塞读」成立，这是 MVCC 最大的收益。但**当前读必须看最新值并加锁**，否则更新会基于过期版本，丢失更新重新出现。同一个事务里混用两种读法，就会出现「快照里没有、当前读里却有」的错觉，这是业务代码里最常见的 MVCC 陷阱。

### 8.5 MVCC 解决不了什么

MVCC 只处理**读—写**冲突，不处理**写—写**冲突：两个事务同时改同一行，仍然要靠行锁排队，后到者等待。它也不能替代唯一性约束检查——唯一索引的冲突检测必须看最新数据，因此插入重复键时加的是当前读而非快照读。把 MVCC 当成「万能的无锁并发」是另一处常见误解。

## 九、日志：redo、undo 与 WAL

### 9.1 redo：把已提交的修改重放一遍

redo 日志记录的是「在某页的某偏移处做了什么修改」，属于**物理逻辑日志**：物理到页，逻辑到页内操作。它顺序追加写入一组固定大小的文件，写满后循环覆盖，因此必须配合检查点来界定「哪些日志还能被覆盖」。

关键机制是 **LSN（日志序列号）**：每次修改产生递增的 LSN，数据页头部记录自己最后一次被修改的 LSN。崩溃恢复时，从检查点记录的 LSN 开始向后扫描，若某条日志的 LSN 大于页上的 LSN，说明该修改尚未落到数据页，需要重做；否则跳过。**重做是幂等的**，因为「页 LSN 已不小于日志 LSN」时不再重复应用，这使恢复可以中断后重来。

### 9.2 undo：回滚与旧版本

undo 日志记录的是「如何把这条修改撤掉」：插入对应删除，删除对应一条插入，更新对应把旧值写回。它承担两项职责：

1. **回滚**：事务中止或恢复时，逆序应用 undo，把修改撤掉。
2. **MVCC**：为快照读提供旧版本，沿 `DB_ROLL_PTR` 找到的历史版本就存放在 undo 里。

undo 不能像 redo 那样立刻丢弃：只要还有快照可能需要某个旧版本，它就必须保留。后台的 purge 线程在确认没有任何 ReadView 需要该版本后才清理。这解释了一个常见现象——**长事务会拖住 undo 清理，导致历史版本链变长、占用空间持续上涨**。

### 9.3 WAL：日志先行

WAL（Write-Ahead Logging）的规则只有一条：**修改数据页之前，必须先把对应的日志写到持久存储**。它带来两个直接后果：

- 数据页可以延迟刷盘，随机写被合并成批量写，I/O 效率提高；
- 崩溃后只要日志在，就能重放出已提交的修改，数据页丢失不致命。

提交时的持久性由刷日志策略决定：每次提交都把 redo 刷到磁盘，持久性最强、延迟最高；交给后台周期性刷，吞吐高但崩溃可能丢最后若干秒的已提交事务。这正是「持久性可调」的含义——ACID 不是开关，而是有强度的。

### 9.4 检查点与恢复三步

检查点的作用是缩短恢复时需要扫描的日志范围：把「此刻所有脏页的修改都已安全记录」这一位置写进日志，恢复便不必从头扫描。检查点分两类：一次性把全部脏页刷盘的强检查点会长时间阻塞；分批推进、允许恢复时继续重做的模糊检查点开销小，是现代系统的主流。

崩溃恢复按三步推进：

| 阶段 | 做什么 | 目的 |
|---|---|---|
| 分析（analysis） | 从最后一个检查点向后扫描，确定崩溃时哪些事务已提交、哪些未结束、哪些脏页未刷 | 划出重做起点与待回滚事务集合 |
| 重做（redo） | 从起点重放所有日志（含未提交事务的修改） | 恢复到崩溃前的物理状态 |
| 回滚（undo） | 逆序撤销未提交事务的修改 | 消除半截事务，回到一致状态 |

**重做阶段故意连未提交事务的修改一起重放**，再在回滚阶段撤销。这个「先全做再撤掉」的顺序不是浪费：它让重做只需顺序扫描、无需判断事务状态，而撤销可以按事务逆序精确执行，整体代价更低且可中断。

### 9.5 故障分类与对策

原料在故障题里给出的判断是：**介质故障（如磁盘损坏）会直接破坏物理数据文件，是最严重的故障；输入错误数据属于用户操作错误，程序故障与事务内部故障不会直接破坏物理存储**。据此可把故障与对策对应起来：

| 故障类型 | 破坏对象 | 对策 |
|---|---|---|
| 事务内部故障 | 单个事务的中间状态 | undo 回滚该事务 |
| 系统故障（宕机、断电） | 内存中的缓冲区 | redo 重放 + undo 回滚 |
| 介质故障 | 数据文件本身 | 备份加日志重做，需独立存储 |
| 计算机病毒、误操作 | 数据或结构 | 权限控制、备份、审计 |

介质故障是唯一需要「备份」这一层额外手段的故障：日志和数据文件同在一块坏盘上时，redo 也无从重放。这条把「恢复」从单机机制扩展到了运维策略。

### 9.6 两阶段提交：redo 与 binlog 的配合

开启二进制日志后，一次提交要写两份日志：存储引擎的 redo 与服务器的 binlog。二者若不一致，主从复制或按时间点恢复就会出错。InnoDB 用**内部两阶段提交**解决：先把 redo 置为 prepare 并写入事务号，再写 binlog，最后把 redo 置为 commit。崩溃恢复时，若 redo 已是 commit 则直接确认；若处于 prepare，则检查 binlog 中是否有对应事务——有则提交，无则回滚。

这段机制解释了「为什么 binlog 必须与 redo 同序」：binlog 是复制与审计的事实来源，redo 是页恢复的事实来源，两者只能有一个判定标准，否则恢复出的库与从库会分叉。

## 十、易错点

1. **把「部分提交」当成「已提交」**。判据是日志中的提交记录，不是语句执行完。
2. **以为一致性有独立实现**。一致性由约束、应用逻辑与 A、I、D 共同维持，没有「一致性日志」这种东西。
3. **把可串行化当成「不出现任何异常」**。它只约束最终效果等价于串行，不约束中间可见性。
4. **以为 2PL 能防死锁**。两段性约束的是加锁与解锁的先后，不约束加锁方向。
5. **以为 RR 一定没有幻读**。标准 RR 允许幻读；InnoDB 靠间隙锁在多数当前读场景下抑制，但快照读与当前读混用、执行计划变化时仍会出现不一致。
6. **混淆快照读与当前读**。普通 `SELECT` 读快照，`FOR UPDATE` 与写语句读最新值。
7. **以为 MVCC 能解决写—写冲突**。写—写仍靠行锁排队；唯一约束检查也必须走当前读。
8. **忽视长事务的代价**。它长期持有锁与旧版本，拖住 purge，放大回滚与空间开销。
9. **把「日志先落盘」理解成「数据页也立刻落盘」**。WAL 恰恰允许数据页延迟写。
10. **恢复时先回滚再重做**。正确次序是分析、重做、回滚，重做必须包含未提交事务的修改。

## 十一、勘误与限定

| 序号 | 原料表述 | 问题 | 本文处理 |
|---|---|---|---|
| 1 | 「同一事务内的操作，顺序可以交换而不影响结果」 | 同一事务内的读写次序恰恰影响结果，$w_1(A)$ 与 $r_1(A)$ 交换后语义改变 | 非冲突只保留两种情形：不同事务不同数据、不同事务均为读 |
| 2 | 「多个事务并发执行时，执行效果等价于串行执行，不出现脏读、不可重复读、幻读」 | 这是可串行化（最高隔离级别）的性质，被写成了并发的普遍保证 | 限定为「最高隔离级别下的目标」，并给出四级隔离矩阵说明取舍 |
| 3 | 「一致性：事务执行前后数据库状态保持一致」 | 表述过弱，易被理解为「值不变」 | 补为「从一个满足约束的一致状态转移到另一个一致状态」，并给出三层含义 |
| 4 | 故障题只区分「介质故障」与「其他故障」 | 未覆盖系统故障与事务故障的处置差异 | 补一张故障—破坏对象—对策对照表，保留原料「介质故障最严重」的结论 |
| 5 | 完整性检查「在语句执行后或事务提交时」 | 结论正确，但未说明与事务状态的关系 | 明确延迟检查只能推到提交点，提交前必须完成，否则会破坏原子性语义 |

第 5 条的展开：把外码或 `CHECK` 检查推迟到提交时，是为了允许事务内部出现短暂的不一致（先插子行、后插父行）。但推迟有边界——**检查必须发生在提交判定之前**，否则提交记录一旦写下，再发现违约就只能回滚一个「已提交」的事务，破坏持久性。这也说明完整性检查与事务状态机是耦合的，不是两套独立机制。

## 十二、小结

| 知识块 | 必记结论 |
|---|---|
| 事务定义 | 不可分割的操作序列，要么全做要么全不做；判据是日志中的提交记录 |
| 状态迁移 | 活动、部分提交、提交、失败、中止；部分提交是恢复的分叉点 |
| ACID | A 靠 undo、D 靠 redo、I 靠锁与多版本、C 由约束与应用逻辑加前三者共同维持 |
| 并发异常 | 丢失更新是写覆盖；脏读读到未提交值；不可重复读是行值变；幻读是行数变 |
| 可串行化 | 冲突操作定义、优先图无环即冲突可串行化；可串行化不保证中间可见性 |
| 隔离级别 | 四级依次禁脏读、不可重复读、幻读；InnoDB 默认 RR，快照读加间隙锁抑制幻读 |
| 封锁 | S/X 相容矩阵；三级协议差别在读锁持有时长；2PL 保证可串行化但不防死锁 |
| 多粒度 | 意向锁 IS/IX/SIX 让表级请求免于逐行检查；间隙锁与 next-key 锁封锁「尚不存在的行」 |
| MVCC | 隐藏事务号加回滚指针构成版本链；ReadView 四字段五步判定；RC 每语句建快照、RR 每事务建一次 |
| 日志 | redo 物理逻辑、幂等重放；undo 支持回滚与旧版本；WAL 日志先于数据页 |
| 恢复 | 分析、重做（含未提交）、回滚；检查点缩短扫描范围；介质故障需备份兜底 |

把全文压成一条线：事务给出「不可分割」的边界，ACID 说明这个边界要维护哪四件事；并发异常说明边界被同时执行破坏的四种方式；可串行化给出正确性标准，隔离级别是标准与吞吐之间的刻度；封锁与 MVCC 是达到该刻度的两条技术路线，前者用等待换取顺序，后者用空间换取并行；日志则在两条路线之下兜底，保证无论怎么并发、怎么崩溃，最终都能回到一个一致状态。原料提供了这条线的起点（定义、一致性三层、冲突可串行化、故障分类），其余环节按通用机制补齐并标注口径——把「哪句来自对话、哪句来自教材」分开，比把两者混成一段更难被记错。
