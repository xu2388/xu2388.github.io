# 数据库 · 关系代数与 SQL 互译

## 一、概述：形式层与实现层

同一句「查出选修了 1 号课程的学生姓名」，在关系代数里写作投影与连接的复合，在 SQL 里写作 `SELECT` 与 `JOIN`。两者不是两套知识，而是同一件事的两个层次：关系代数给出**语义**（结果应当是什么集合），SQL 给出**可执行的表达**（用哪些子句拼出来）。把两者对齐，查询题就不再需要「凭感觉写」，而可以按规则逐步翻译。

翻译之所以能机械化，是因为两边的构造几乎一一对应：选择对 `WHERE`、投影对 `SELECT`、笛卡尔积对 `FROM` 的多表并列、连接对 `JOIN ... ON`、并对 `UNION`、差对「不在」类子查询。真正需要动脑的只有三处：**集合语义与多重集语义的落差**、**空值让比较变成三值逻辑**、**除运算没有直接的 SQL 关键字**。

有人会问：既然 SQL 能直接写，为什么还要绕一层代数？理由有三。第一，代数是**无歧义的语义定义**，它明确规定了结果集合里应当有哪些元组，而 SQL 语句「能跑通」并不等于「语义正确」——漏写一个连接条件，语句照样执行，只是结果悄悄变成笛卡尔积的子集。第二，代数是**优化的对象**，查询优化器在内部把 SQL 解析成算子树，再按等价变换重排，理解这些变换才能判断改写是否安全。第三，代数题是**考试里唯一能给出确定答案的形式**，答案不依赖某个数据库的方言与实现细节。

**素材边界。** 原始对话支撑的内容包括：SPJ 供应库上的五个查询及其关系代数表达；除运算的语义与结果；连接运算从笛卡尔积、θ 连接、等值连接到自然连接的分类与列数计算；并相容性与各表达式的最大、最小元组数推导；投影优化中「保留最终属性与连接属性」的原则；聚合函数忽略空值的规则；以及用 `UNION`、`OR`、`ORDER BY` 加 `LIMIT`、窗口函数四种方式求最值的对照。其中两处代数式缺少等值连接条件，本文在 §十 显式勘误，正文只给修正后的写法。

## 二、五种基本运算与派生运算

### 2.1 基本运算只有五个

关系代数以集合运算为基础，被称为**基本运算**的只有并、差、笛卡尔积、选择、投影五个，判据是「不能被其他运算推导出来」。交不是基本的，因为它可以由差导出：

$$
R \cap S = R - (R - S).
$$

先取「在 $R$ 而不在 $S$」的元组，再从 $R$ 中减掉它，剩下的恰是共有部分。连接也不是基本的，θ 连接由笛卡尔积与选择复合而成：

$$
R \bowtie_{\theta} S = \sigma_{\theta}(R \times S).
$$

自然连接在此基础上多一步投影，去掉重复的同名列，因此同样不是基本运算。除运算更复杂，它需要「对全部」的语义，只能由基本运算组合表达。

| 运算 | 记法 | 作用 | 是否基本 | 结果目数 |
|---|---|---|---|---|
| 并 | $R \cup S$ | 纵向合并并去重 | 是 | 与原关系相同 |
| 差 | $R - S$ | 取在 $R$ 不在 $S$ 的元组 | 是 | 与原关系相同 |
| 笛卡尔积 | $R \times S$ | 行与列同时扩展 | 是 | 两者目数之和 |
| 选择 | $\sigma_{F}(R)$ | 按条件筛行 | 是 | 不变 |
| 投影 | $\pi_{A}(R)$ | 按属性筛列并去重 | 是 | 属性组的大小 |
| 交 | $R \cap S$ | 取共有元组 | 否，由差导出 | 不变 |
| θ 连接 | $R \bowtie_{\theta} S$ | 笛卡尔积后按条件筛 | 否 | 两者目数之和 |
| 自然连接 | $R \bowtie S$ | 同名属性等值并去重列 | 否 | 两者目数之和减公共属性数 |
| 除 | $R \div S$ | 按「全部」语义筛选 | 否 | $R$ 的目数减 $S$ 的目数 |

### 2.2 并相容性：什么条件下并、交、差合法

并、交、差要求两个关系**并相容**：目数相同，且对应属性来自相同的域。这条判据里**没有「属性名相同」这一项**。原料在处理一组 $S(A,B,C,D)$ 与 $T(C,D,E,F)$ 的题目时，先断言「属性名不同所以不能做并交差」，随后又用「题目默认并相容」把这个矛盾绕过去。正确的说法是：属性名可以不同，只要按位置对应的域一致，运算就合法；题目给出「在使表达式有意义的情况下」，正是把这个前提交给解题者自行假定。

这个细节在考试里常被用作陷阱：判据是「同目且对应属性同域」，不是「同名」。反过来，若两个关系目数不同，即使属性名高度重合也不能做并运算。

### 2.3 元组数的上下界

原料对八个表达式逐一给出最大、最小元组数，这套推导是估算中间结果规模的基础。设 $S$ 有 $N_1$ 个元组、$T$ 有 $N_2$ 个元组，且 $N_2 > N_1$：

| 表达式 | 目数 | 最大元组数 | 最小元组数 | 极值场景 |
|---|---|---|---|---|
| $S \cup T$ | 4 | $N_1+N_2$ | $N_2$ | 无重复元组取和；$S \subseteq T$ 时取 $N_2$ |
| $S \cap T$ | 4 | $N_1$ | $0$ | $S \subseteq T$ 时取 $N_1$；无共同元组为 0 |
| $S - T$ | 4 | $N_1$ | $0$ | 无共同元组取 $N_1$；$S \subseteq T$ 时为 0 |
| $S \times T$ | 8 | $N_1 N_2$ | $N_1 N_2$ | 恒定，与内容无关 |
| $\sigma_{A=10}(S)$ | 4 | $N_1$ | $0$ | 全部满足或全部不满足 |
| $\pi_{A,B}(S)$ | 2 | $N_1$ | $1$ | $(A,B)$ 全不重复取 $N_1$；全相同去重为 1 |
| $S \bowtie T$ | 6 | $N_1 N_2$ | $0$ | 公共属性全匹配取乘积；全不匹配为 0 |
| $\pi_{C,D}(S) \times T$ | 6 | $N_1 N_2$ | $N_2$ | 投影后最多 $N_1$ 个、最少 1 个 |

三处容易推错的地方。第一，**投影的最小值不是 0 而是 1**：投影去重后至少留下一行，前提是 $S$ 非空；若 $S$ 为空，结果才是空集。第二，**自然连接的最大值可以达到 $N_1N_2$**，只要所有元组在公共属性上取值相同——这说明「连接一定比笛卡尔积小」是错的，连接只是笛卡尔积的子集，上界相同。第三，**笛卡尔积的元组数恒定**，与有没有重复元组无关，这是它与其他运算最不一样的地方。

## 三、从代数式到 SQL 的机械规则

### 3.1 一张对照表

| 代数构造 | SQL 落点 | 备注 |
|---|---|---|
| $\sigma_{F}(R)$ | `WHERE F` | 条件里的属性要能追溯到 `FROM` |
| $\pi_{A}(R)$ | `SELECT A` | 关系代数去重，SQL 默认不去重，需 `DISTINCT` |
| $R \times S$ | `FROM R, S` | 必须补连接条件，否则是纯笛卡尔积 |
| $R \bowtie_{\theta} S$ | `JOIN S ON θ` | 或 `FROM R, S WHERE θ` |
| $R \bowtie S$ | `NATURAL JOIN` 或 `JOIN ON` 全部同名列 | 显式写法更安全 |
| $R \cup S$ | `UNION` | `UNION` 去重，`UNION ALL` 不去重 |
| $R - S$ | `EXCEPT`、`NOT EXISTS`、左外连接加空值判断 | MySQL 不支持 `EXCEPT` |
| $R \cap S$ | `INTERSECT`、`IN`、`EXISTS` | MySQL 不支持 `INTERSECT` |
| $R \div S$ | 双重 `NOT EXISTS`，或 `GROUP BY` 加 `HAVING` 计数 | 无直接关键字 |
| 分组聚集 $\gamma$ | `GROUP BY` 加聚合函数 | 无分组时整表为一组 |

### 3.2 三条必须先处理的落差

**其一，集合语义与多重集语义。** 关系是元组的集合，投影自动去重；SQL 的表是多重集，`SELECT` 默认保留重复行。翻译 $\pi$ 时必须自问「结果是否可能出现重复」，可能就要加 `DISTINCT`。反过来，若业务需要保留重复（例如统计选课记录条数），就不能照搬关系代数的去重语义。

**其二，空值。** 关系代数里元组的每个分量都有确定值，SQL 允许 `NULL`，而 `NULL` 参与比较得到的是 UNKNOWN，不是真也不是假。这会让「差运算」的直译出现偏差：`NOT IN` 在子查询含空值时可能整体为空，而集合差在数学上不会。凡涉及差与「不存在」的翻译，优先用 `NOT EXISTS`。

**其三，属性名的作用域。** 代数式里属性名全局唯一，SQL 里多表并列后同名列必须加表名前缀限定。$S(A,B,C,D)$ 与 $T(C,D,E,F)$ 做连接时，`C`、`D` 在两个关系中同名，写 `WHERE C = C` 会被解析成同一列自比，永远为真，等价于没有条件。这是把代数式直译成 SQL 时最常见的静默错误：语句能跑，结果错了。

### 3.3 一次逐步翻译

以一个复合式子为例，看规则如何串联。设要查「计算机系学生选课后的姓名与课程号」：

$$
\pi_{Sname,Cno}\Big(\sigma_{Sdept='CS'}(Student) \bowtie SC\Big).
$$

第一步落选择：$\sigma_{Sdept='CS'}$ 对应 `WHERE Sdept = 'CS'`。第二步落连接：两关系的公共属性是 `Sno`，自然连接对应按 `Sno` 等值匹配，并只保留一份 `Sno`。第三步落投影：外层只保留 `Sname`、`Cno` 两列。逐层写成 SQL 是

```sql
SELECT st.Sname, sc.Cno
FROM Student st
JOIN SC sc ON st.Sno = sc.Sno
WHERE st.Sdept = 'CS';
```

若照抄代数式的括号结构先做投影再连接，就会得到 `SELECT Sname FROM Student WHERE ...` 与 `SC` 的连接——两侧已无公共属性，连接条件无从写起。因此翻译时必须**先判断每一步的输入输出属性集**，再决定投影放在哪一层。这也是 §7.3 那条「投影保留连接属性」规则在实际翻译中的用法：先连接、后投影永远安全，先投影后连接必须核对公共属性是否还在。

## 四、连接族：从笛卡尔积到自然连接

### 4.1 四层包含关系

原料把连接收成一条链，这个层级关系值得记住：

| 层次 | 定义 | 列数 | 是否去重列 |
|---|---|---|---|
| 广义笛卡尔积 | 无条件拼接所有元组组合 | $m+n$ | 否 |
| θ 连接 | 笛卡尔积后按任意比较条件筛选 | $m+n$ | 否 |
| 等值连接 | θ 取等号的特例 | $m+n$ | 否 |
| 自然连接 | 按全部同名属性等值匹配，并去掉重复列 | $m+n-k$ | 是 |

$k$ 是公共属性个数。原料的算例中 $S(A,B,C,D)$ 与 $T(C,D,E,F)$ 的公共属性为 $C$、$D$，故自然连接列数为 $4+4-2=6$，结果为 $(A,B,C,D,E,F)$。这个减法很直观，但它同时意味着**自然连接会把所有同名列都纳入匹配条件**：若两张业务表都带 `create_time`，自然连接就要求创建时间也相等，行会莫名其妙地消失。

### 4.2 外连接与空值

内连接只保留能匹配上的组合，外连接把匹配不上的行也留下，缺失一侧补空值。左外保留左表全部行，右外保留右表全部行，全外两侧都保留。MySQL 没有全外连接语法，需用左外与右外的并集模拟。

```sql
-- 保留所有学生，未选课的显示为空
SELECT s.Sno, s.Sname, sc.Cno
FROM Student s
LEFT JOIN SC sc ON s.Sno = sc.Sno;
```

外连接最容易出错的地方是**过滤条件写在哪**。写在 `ON` 里只影响匹配，写在 `WHERE` 里会过滤掉补出来的空值行，从而把外连接退化成内连接：

```sql
-- 仍是外连接：只匹配 1 号课，其他学生保留但 Cno 为空
SELECT s.Sno, sc.Cno
FROM Student s LEFT JOIN SC sc
  ON s.Sno = sc.Sno AND sc.Cno = '1';

-- 退化为内连接：Cno 为空的行被 WHERE 筛掉
SELECT s.Sno, sc.Cno
FROM Student s LEFT JOIN SC sc ON s.Sno = sc.Sno
WHERE sc.Cno = '1';
```

判断方法很简单：**针对被补空值那一侧的过滤条件，若写在 `WHERE` 且不允许空值，外连接就失效**。要保留外连接语义又过滤右表，应把条件并入 `ON`，或显式写成 `WHERE sc.Cno = '1' OR sc.Cno IS NULL`。

### 4.3 空值参与计数

外连接补出的空值行会影响聚合。统计每门课的选课人数时，若用左外连接让无人选修的课也出现，`COUNT(*)` 会把补出的那一行算成 1，而 `COUNT(SC.Sno)` 跳过空值，得到 0：

```sql
SELECT c.Cno, c.Cname, COUNT(sc.Sno) AS 人数
FROM Course c LEFT JOIN SC sc ON c.Cno = sc.Cno
GROUP BY c.Cno, c.Cname;
```

这条规则来自聚合函数对空值的统一处理：除 `COUNT(*)` 外，`SUM`、`AVG`、`MAX`、`MIN`、`COUNT(列)` 都跳过空值。因此「统计行数」与「统计某列的非空值个数」在有空值时并不等价。

### 4.4 连接、IN 与 EXISTS 的行数差别

同一个「选了 1 号课的学生」可以有三种写法，结果集的行数并不总是相同：

```sql
SELECT s.Sno, s.Sname FROM Student s JOIN SC sc ON s.Sno = sc.Sno
WHERE sc.Cno = '1';

SELECT Sno, Sname FROM Student
WHERE Sno IN (SELECT Sno FROM SC WHERE Cno = '1');

SELECT Sno, Sname FROM Student s
WHERE EXISTS (SELECT 1 FROM SC WHERE Sno = s.Sno AND Cno = '1');
```

第一种是内连接，若一个学生在 `SC` 中有多条 1 号课记录（现实中不该有，但缺少唯一约束时可能出现），该学生会被输出多次；后两种是半连接语义，只判断「有没有」，每个学生至多出现一次。关系代数一侧，连接后的结果还需要一次投影去重才能与后两者对齐：

$$
\pi_{Sno,Sname}\Big(Student \bowtie \sigma_{Cno='1'}(SC)\Big).
$$

这解释了为什么「连接再投影」与「`EXISTS`」在有无重复时结果不同：差别不在语义设计，而在 SQL 的 `SELECT` 是否去重。翻译时只要记住「投影自带去重」，就会自然地在该加 `DISTINCT` 的地方加上。

## 五、除运算的两种 SQL 写法

### 5.1 语义：象集包含

$R(X,Y) \div S(Y)$ 的结果是那些 $x$，其象集包含 $S$ 在 $Y$ 上的投影。判据是**包含**而不是相交：只要某个 $x$ 的象集少一个元素，它就不入选。这对应自然语言里的「对全部……都……」，是 SQL 里唯一没有直接关键字的一类查询。

以供应库为例：$SPJ(SNO,PNO,JNO,QTY)$、$S(SNO,SNAME,STATUS,CITY)$、$P(PNO,PNAME,COLOR,WEIGHT)$、$J(JNO,JNAME,CITY)$。「至少用了供应商 S1 所供应的全部零件的工程号」即

$$
\pi_{JNO,PNO}(SPJ) \div \pi_{PNO}\big(\sigma_{SNO='S1'}(SPJ)\big).
$$

### 5.2 双重 NOT EXISTS：把全称拆成两层否定

「工程 $J$ 用了 S1 的全部零件」等价于「不存在一个 S1 供应过的零件，是 $J$ 没有用的」。这句话里有两个否定，正好对应两层 `NOT EXISTS`：

```sql
SELECT j.JNO
FROM J j
WHERE NOT EXISTS (
    SELECT 1
    FROM SPJ s1
    WHERE s1.SNO = 'S1'
      AND NOT EXISTS (
          SELECT 1
          FROM SPJ s2
          WHERE s2.JNO = j.JNO
            AND s2.PNO = s1.PNO
      )
);
```

读法从外到内：外层遍历每个工程；第一层子查询列出「S1 供应过的零件」；第二层检查该工程是否用过这个零件。若某个零件用过，内层 `EXISTS` 为真，`NOT EXISTS` 为假，第一层的那一行不成立；只有当所有零件都被内层确认用过，第一层子查询才为空，外层 `NOT EXISTS` 为真。

这种写法的优点是**除数可以含重复、可以被任意条件筛选**，不需要额外去重。缺点是三层嵌套、可读性差，且对外层每一行都要执行一次内层查询。

### 5.3 分组计数：把「全部」变成「数量相等」

另一种思路是把全称量化转成计数比较：$J$ 用过的、属于目标集合的零件种类数，等于目标集合的零件种类数。

```sql
SELECT s.JNO
FROM SPJ s
WHERE s.PNO IN (SELECT PNO FROM SPJ WHERE SNO = 'S1')
GROUP BY s.JNO
HAVING COUNT(DISTINCT s.PNO) = (
    SELECT COUNT(DISTINCT PNO) FROM SPJ WHERE SNO = 'S1'
);
```

成立的前提必须写清：**分子与分母都要用 `DISTINCT`**，否则同一零件被同一工程多次供应会把计数抬高；除数集合为空时，等号右边为 0，而 `HAVING` 只在有分组的工程上判断，语义上「空集被全部满足」应当返回所有工程，这种写法会返回空集。这是它与双重 `NOT EXISTS` 的实质差别，不是风格差别。

### 5.4 两种写法的取舍

| 维度 | 双重 NOT EXISTS | GROUP BY 加 HAVING |
|---|---|---|
| 对除数重复的容忍 | 天然容忍 | 必须 `DISTINCT` |
| 除数为空时的语义 | 正确（全部工程入选） | 错误（返回空集） |
| 可读性 | 差，三层嵌套 | 较好，一行判断 |
| 执行方式 | 相关子查询，逐行探测 | 一次分组加一次标量子查询 |
| 适用场景 | 考试、语义严格的场合 | 数据干净、除数非空的统计场景 |

选择的原则不是「哪个快」，而是「哪个在边界条件下仍然对」。除数为空、被除数有重复、零件号可空，这三种边界只要有一种可能出现，就应当用双重 `NOT EXISTS`。

### 5.5 边界推演：除数为空

设工程表有 $J_1$、$J_2$、$J_3$ 三个工程，供应商 S1 在 $SPJ$ 中没有任何供应记录。此时除数是空集，按定义「空集被任何工程全部满足」，$R \div \varnothing$ 的结果应为全部工程，即 $\{J_1,J_2,J_3\}$。

两种写法在这个边界上分道扬镳：

| 写法 | 第一层子查询 | 结果 |
|---|---|---|
| 双重 `NOT EXISTS` | 找不到 S1 的零件，第一层为空 | 三个工程全部入选，正确 |
| 分组计数 | 外层 `WHERE PNO IN (空集)` 筛掉所有行，没有分组 | 返回空集，错误 |

分组计数之所以出错，是因为它把「全部满足」编码成了「计数相等」，而空集上的计数比较没有机会执行——`WHERE` 先把所有行筛掉了。要修补，必须额外加一个「除数非空」的分支，用 `OR NOT EXISTS` 把空集情形单独处理，写法立刻变得比双重 `NOT EXISTS` 更绕。这条推演说明：**两种写法不是同一语义的两种实现，而是同一语义在「除数非空」这一子集上的两种实现**。

## 六、聚合与分组

### 6.1 聚合函数的三条规则

| 规则 | 说明 | 例子 |
|---|---|---|
| 忽略空值 | `SUM`、`AVG`、`MAX`、`MIN`、`COUNT(列)` 跳过 `NULL` | 三行值为 80、90、`NULL`，`AVG` 得 85 而非 56.7 |
| `COUNT(*)` 计行 | 统计行数，不看列值 | 含空值行也计入 |
| 空集上的行为 | `COUNT` 返回 0，其余返回 `NULL` | 无选课记录时 `MAX(Grade)` 为 `NULL` |

第二条常被写成「`COUNT(*)` 忽略空值」，这是错的：`COUNT(*)` 数的是行，行本身不会为空。第一条才是「忽略空值」的准确表述。两者在单表统计里差别不大，在外连接补空值时就分出胜负，§4.3 的例子即是。

### 6.2 分组、过滤与排序

```sql
SELECT Sno, SUM(Grade) AS 总分, COUNT(*) AS 门数
FROM SC
WHERE Grade >= 60
GROUP BY Sno
HAVING COUNT(*) >= 4
ORDER BY 总分 DESC;
```

执行次序是 `FROM`、`WHERE`、`GROUP BY`、`HAVING`、`SELECT`、`ORDER BY`。这条次序决定了两条硬规则：**行级条件只能进 `WHERE`**（分组后已无单条记录可供判断），**聚合条件只能进 `HAVING`**（`WHERE` 里不能出现聚合函数）。把 `Grade >= 60` 写进 `HAVING` 的错误有两层：语法上 `Grade` 已不是分组后的可用列；语义上不及格记录仍会被计入总分与门数。

关系代数一侧，分组聚集通常记作 $\gamma$，`GROUP BY` 的列是分组属性，聚合函数是聚集属性。没有 `GROUP BY` 时，整张表被视为一个分组，聚合函数返回一行——这正是「`SELECT COUNT(*) FROM t` 永远返回一行」的原因，哪怕表是空的。

### 6.3 聚合结果与关系代数的对应

分组结果可以看成一个新关系：分组属性加上若干聚集值。它能继续参与连接，这也是把相关子查询改写成连接的基础。例如「成绩不低于本人平均分」的查询，可以先用分组算出每个学生的平均分，再与明细连接：

```sql
SELECT sc.Sno, sc.Cno, sc.Grade
FROM SC sc
JOIN (SELECT Sno, AVG(Grade) AS avg_g FROM SC GROUP BY Sno) t
  ON sc.Sno = t.Sno
WHERE sc.Grade >= t.avg_g;
```

这个改写把「逐行求平均」变成「先分组再连接」，在数据量大时通常更快，但它要求平均分只算一次。反过来说，若平均分的计算依赖外层某些条件，就不能这样改写。

### 6.4 聚合值参与条件

聚合值不能出现在 `WHERE` 中，要拿它做条件有两条路：`HAVING` 或子查询。前者用于「分组自身的聚合值」，后者用于「与另一个聚合值比较」：

```sql
-- 分组自身的聚合值：门数不少于 4
SELECT Sno FROM SC GROUP BY Sno HAVING COUNT(*) >= 4;

-- 与全局聚合值比较：人数高于全校平均
SELECT Sclass
FROM Student
GROUP BY Sclass
HAVING COUNT(*) > (SELECT AVG(cnt) FROM (SELECT COUNT(*) AS cnt FROM Student GROUP BY Sclass) t);
```

第二例的关键是把「每班人数」先做成一个派生表，再求它的平均。若直接写 `HAVING COUNT(*) > AVG(COUNT(*))`，聚合函数嵌套聚合函数，语法上不成立。这条限制的根源仍是执行次序：`HAVING` 在分组之后执行，此时聚合已经完成，不能再对聚合结果重新分组求平均。

## 七、多表连接的执行顺序直觉

### 7.1 逻辑顺序与物理顺序

书写顺序是「先写表、再写条件」，逻辑顺序是「先笛卡尔积、再选择、再投影」，物理顺序由优化器决定。三者可以完全不同，这是很多「按书写顺序推执行过程」的困惑的来源。

以课程库的规模为例：$Student$ 一万行、$SC$ 十万行、$Course$ 一百行。若先做三表笛卡尔积再筛选，中间结果是一万乘十万乘一百，即 $10^{11}$ 行；若先把选择与连接结合，先按学号连接 $Student$ 与 $SC$，中间结果十万行，再与 $Course$ 连接，规模不变。**同一条 SQL，中间结果的量级可以差六个数量级**，这正是优化策略要尽早做选择、把选择与笛卡尔积合并成连接的原因。

### 7.2 三种连接算法

| 算法 | 适用条件 | 代价特征 |
|---|---|---|
| 嵌套循环 | 内表连接列有索引 | 外表行数乘以内表单次探测代价 |
| 哈希连接 | 等值连接、内存足够 | 建哈希表一次，探测一次，适合大表对大表 |
| 排序合并 | 两侧已按连接列有序 | 排序代价加一次归并扫描 |

嵌套循环的关键变量是**驱动表过滤后的行数**，而不是表的原始大小。外表一万行、内表每次探测一次索引，代价约一万次索引查找；若外表能先过滤到一百行，代价降到一百次。这就是「小表驱动大表」的准确含义：小指的是**过滤后**的结果集，不是建表时的行数。

### 7.3 投影下推：少带列

原料记录了一处投影优化的算例，并同时记录了一处错误。错误写法是

$$
\pi_{Sname}(Student) \bowtie \pi_{Sno,Cno}(SC) \bowtie \pi_{Cno,Cname}(Course),
$$

第一个投影只剩姓名一列，与 $SC$ 没有任何公共属性，自然连接在定义上无法进行。正确写法必须保留连接属性：

$$
\pi_{Sname,Cname}\Big(\pi_{Sno,Sname}(Student) \bowtie \pi_{Sno,Cno}(SC) \bowtie \pi_{Cno,Cname}(Course)\Big).
$$

修正后，参与连接的列数从 $4+3+3$ 降到 $2+2+2$，第一次连接后的列数从 7 降到 4，第二次从 10 降到 6，中间结果的列数减少约四成。列数减少的直接收益是每行更短、每页容纳更多行，I/O 次数随之下降。

由此得一条硬规则：**投影时同时保留两类属性——最终结果需要的属性，以及后续连接需要的公共属性**。只保留前者，是代数题里最常见的失分点，也是 SQL 里「少写一个连接列导致条件恒真」的根源。

### 7.4 中间结果规模的估算

把上面的结论整理成一张估算表，可以据此判断一条多表查询是否「写得太重」：

| 步骤 | 输入规模 | 输出规模 | 依据 |
|---|---|---|---|
| 选择 $Sdept='CS'$ | 一万行 | 约一千行 | 系别选择性 |
| 投影到 $(Sno,Sname)$ | 一千行、四列 | 一千行、两列 | 列数减少，行数不变 |
| 与 $SC$ 自然连接 | 一千行、十万行 | 约一万行 | 人均选课数 |
| 投影到 $(Sname,Cno)$ | 一万行、多列 | 一万行、两列 | 列数减少 |

每一步的输出规模都能用上一节的元组数规则估出来。若某一步的输出突然放大到接近笛卡尔积，说明该处漏了连接条件或条件写错。这个检查比逐行读 SQL 更快发现错误：**行数异常放大就是条件缺失的信号**。反过来，若某一步输出骤减到接近零，则要怀疑条件过严，例如把 `OR` 写成了 `AND`，或把外连接写成了内连接。

## 八、五个完整对照

以下五例均基于供应库 $S(SNO,SNAME,STATUS,CITY)$、$P(PNO,PNAME,COLOR,WEIGHT)$、$J(JNO,JNAME,CITY)$、$SPJ(SNO,PNO,JNO,QTY)$，只给代数式与 SQL，不涉及题号。

### 8.1 选择与投影的组合

「给工程 J1 供应过零件的供应商号」：

$$
\pi_{SNO}\big(\sigma_{JNO='J1'}(SPJ)\big).
$$

```sql
SELECT DISTINCT SNO
FROM SPJ
WHERE JNO = 'J1';
```

`DISTINCT` 不能省：同一供应商可能给 J1 供过多种零件，`SPJ` 中会有多行，而关系代数的投影自动去重。这一例正好说明「投影对应 `SELECT`」这句翻译规则必须补上「去重」二字。

### 8.2 θ 连接

「给工程 J1 供应零件 P1 的供应商号」：

$$
\pi_{SNO}\big(\sigma_{JNO='J1' \wedge PNO='P1'}(SPJ)\big).
$$

```sql
SELECT DISTINCT SNO
FROM SPJ
WHERE JNO = 'J1' AND PNO = 'P1';
```

这一例没有跨表，两个条件都落在同一关系上，因此不需要连接。若把条件拆到两张表，就必须显式连接，否则会退化为笛卡尔积。

### 8.3 自然连接加选择加投影

「给工程 J1 供应红色零件的供应商号」。这里必须把 $SPJ$ 与 $P$ 按零件号连接，原料的写法漏掉了这个等值条件：

$$
\pi_{SNO}\Big(\sigma_{JNO='J1' \wedge COLOR='红'}\big(SPJ \bowtie P\big)\Big).
$$

```sql
SELECT DISTINCT s.SNO
FROM SPJ s
JOIN P p ON s.PNO = p.PNO
WHERE s.JNO = 'J1' AND p.COLOR = '红';
```

漏掉 `s.PNO = p.PNO` 时，语句仍能执行，但含义变成「J1 的任意供应记录与任意红色零件组合」，只要库中存在红色零件，J1 的所有供应商都会被选中。这是「语法正确、语义错误」的典型：结果行数明显偏多，却不会报错。

### 8.4 差运算

「没有使用天津供应商生产的红色零件的工程号」：

$$
\pi_{JNO}(J) - \pi_{JNO}\Big(\sigma_{CITY='天津' \wedge COLOR='红'}\big(S \bowtie SPJ \bowtie P\big)\Big).
$$

```sql
SELECT JNO FROM J
WHERE NOT EXISTS (
    SELECT 1
    FROM SPJ s
    JOIN S su ON s.SNO = su.SNO
    JOIN P p ON s.PNO = p.PNO
    WHERE s.JNO = J.JNO
      AND su.CITY = '天津'
      AND p.COLOR = '红'
);
```

代数一侧是「全集减去用过的工程」，SQL 一侧是「不存在用过的记录」。两者等价的前提是 $J$ 的工程号非空且唯一；若 $J$ 中有重复工程号，代数式先投影去重，SQL 会输出重复行，需要补 `DISTINCT`。这也是把差运算翻成 `NOT EXISTS` 时最少被检查的一处。

### 8.5 除运算

「至少用了供应商 S1 所供应的全部零件的工程号」：

$$
\pi_{JNO,PNO}(SPJ) \div \pi_{PNO}\big(\sigma_{SNO='S1'}(SPJ)\big).
$$

```sql
SELECT j.JNO
FROM J j
WHERE NOT EXISTS (
    SELECT 1 FROM SPJ s1
    WHERE s1.SNO = 'S1'
      AND NOT EXISTS (
          SELECT 1 FROM SPJ s2
          WHERE s2.JNO = j.JNO AND s2.PNO = s1.PNO
      )
);
```

等价的计数写法见 §5.3。两种写法在这一例上结果相同，因为 S1 供应的零件集合非空、零件号在 $SPJ$ 中不重复；换一组数据就可能分道扬镳，取舍依据已在 §5.4 列出。

### 8.6 交运算

「既选了 1 号课又选了 2 号课的学生学号」：

$$
\pi_{Sno}\big(\sigma_{Cno='1'}(SC)\big) \cap \pi_{Sno}\big(\sigma_{Cno='2'}(SC)\big).
$$

交集没有直接关键字时，可用两次 `IN` 表达「同时属于两个集合」：

```sql
SELECT Sno FROM SC WHERE Cno = '1'
INTERSECT
SELECT Sno FROM SC WHERE Cno = '2';
```

MySQL 不支持 `INTERSECT`，改用分组计数更简洁：

```sql
SELECT Sno
FROM SC
WHERE Cno IN ('1', '2')
GROUP BY Sno
HAVING COUNT(DISTINCT Cno) = 2;
```

两种写法都以「候选集合的大小」为判据：交集要求同时命中两个集合，计数写法要求命中数等于集合数。这个模式与除运算的分组写法同源——都是把「全部满足」翻译成「计数相等」，因此也都继承了同一个前提：**计数必须去重，且目标集合非空**。

## 九、易错点

1. **把交或连接当成基本运算**。基本运算只有并、差、笛卡尔积、选择、投影五个。
2. **用「属性名相同」判断并相容**。判据是同目且对应属性同域，属性名不参与。
3. **投影忘记去重**。关系代数去重、SQL 不去重，`SELECT` 后该加 `DISTINCT` 时要加。
4. **投影丢掉连接属性**。只留最终结果列，后续连接在定义上无法进行。
5. **自然连接按同名列全匹配**。两张表都有 `create_time` 时，行会意外消失，显式等值连接更安全。
6. **外连接的过滤条件写进 `WHERE`**。针对补空值一侧的条件会把外连接退化为内连接。
7. **`COUNT(*)` 与 `COUNT(列)` 混用**。前者计行，后者计非空值，外连接补空值时差别是 1 与 0。
8. **除法按「相交」判定**。判据是象集包含，缺少任一元素即落选。
9. **`NOT IN` 遇上空值**。子查询含空值且外层不命中非空元素时，结果整体为空。
10. **多表连接漏写等值条件**。语句能跑，结果是笛卡尔积的子集，行数偏多。
11. **把书写顺序当执行顺序**。中间结果的规模由优化器决定，不由 `FROM` 的书写次序决定。
12. **分组条件放错层**。行级条件进 `WHERE`，聚合条件进 `HAVING`。

## 十、勘误与限定

| 序号 | 原料表述 | 问题 | 本文处理 |
|---|---|---|---|
| 1 | $\pi_{SNO}(\sigma_{JNO='J1' \wedge COLOR='红'}(SPJ \times P))$ | 缺 $SPJ.PNO = P.PNO$，任意 J1 供应记录会与任意红色零件组合 | 改为自然连接 $SPJ \bowtie P$，并说明漏写后果 |
| 2 | $\pi_{JNO}(J) - \pi_{JNO}(\sigma_{CITY='天津' \wedge COLOR='红'}(S \times SPJ \times P))$ | 缺 $S.SNO = SPJ.SNO$ 与 $SPJ.PNO = P.PNO$ 两个等值条件 | 改为三表自然连接，SQL 用 `NOT EXISTS` 加显式 `ON` |
| 3 | 以「属性名不同」否定并相容性 | 并相容的判据是同目且对应属性同域，与属性名无关 | 在 §2.2 更正，并说明原料自相矛盾之处 |
| 4 | 把 $S \bowtie T$ 写作 $S \times T$ | 记号混用，自然连接被写成笛卡尔积，列数结论却是 6 列 | 统一为 $\bowtie$，列数结论按 $4+4-2=6$ 保留 |
| 5 | 「投影最小元组数为 1」 | 仅在 $S$ 非空时成立 | 补上非空前提，空关系时结果为 0 |
| 6 | 「自然连接一定比笛卡尔积小」的隐含前提 | 连接只是笛卡尔积的子集，上界同为 $N_1N_2$ | 在 §2.3 明确上界相同，仅实际结果通常更少 |

第 6 条不是原料的原话，而是其元组数表中「最大 $N_1N_2$」与常见口头结论之间的张力：既然最大值等于笛卡尔积，就不能把「连接减少行数」当成必然，只能说「连接按条件筛掉了不匹配的组合，通常更少」。这个区分在估算中间结果规模时很实际——当公共属性取值高度集中时，连接结果可能接近笛卡尔积。

## 十一、小结

| 知识块 | 必记结论 |
|---|---|
| 基本运算 | 并、差、笛卡尔积、选择、投影五个；交由差导出，连接由笛卡尔积加选择导出 |
| 并相容 | 同目且对应属性同域；属性名不参与判定 |
| 元组数 | 笛卡尔积恒定 $N_1N_2$；投影最少 1；自然连接上界同为 $N_1N_2$，下界 0 |
| 连接族 | 笛卡尔积、θ 连接、等值连接、自然连接层层特化；自然连接列数减公共属性数 |
| 翻译规则 | 选择落 `WHERE`、投影落 `SELECT`（补 `DISTINCT`）、积落多表 `FROM`、并落 `UNION`、差落 `NOT EXISTS` |
| 外连接 | 补空值；针对空值侧的 `WHERE` 条件会让它退化为内连接 |
| 除法 | 双重 `NOT EXISTS` 对应全称；分组计数须双向 `DISTINCT`，除数为空时语义出错 |
| 聚合 | 除 `COUNT(*)` 外均跳过空值；行级条件进 `WHERE`，聚合条件进 `HAVING` |
| 执行顺序 | 书写顺序不等于物理顺序；驱动表看过滤后行数；投影须保留连接属性 |

把全文压成一条翻译链：先确认运算是否合法（并相容），再确认结果的目数与元组数（估算规模），然后按对照表逐层落成 SQL 子句，最后处理三处落差——去重、空值、属性名作用域。前三步是机械的，后一步是判断的；能把这两类分开，查询题就从「凭感觉」变成了「按步骤验收」。原料提供了这条链的大部分环节与两组算例，也留下了漏写连接条件、以属性名判定相容性两处需要修正的地方——把它们标出来，比照抄一遍结论更有价值。
